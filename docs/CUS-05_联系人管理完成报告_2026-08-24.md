## 二、发现并解决的问题

1. 联系人模型缺少英文名、部门、语言、时区、主要联系人、离职日期和营销抑制字段。
2. 原 `is_key_contact` 不能代表“主要联系人”，两种业务含义已拆分。
3. 原离职接口不能处理主要联系人接替、未完成任务策略和营销抑制。
4. 批量任务无法准确回溯到联系人，现增加联系人任务关联。
5. 原页面没有结构化任职历史、真实实时查重和统一 ETag 写入处理。
6. 左侧存在独立“联系人管理”入口，与确认后的客户管理信息架构不一致。
7. 客户内联系人使用 `q` 搜索时，DRF 会把该参数先用于父级客户搜索，导致嵌套接口误返回 404。现已绕开父级搜索过滤器，并新增回归测试。
8. 初次视觉复核发现“重置”按钮边框、顶部标题和历史抽屉入场时机存在差异，均已修正。

## 三、数据库与迁移

迁移：`customers.0006_cus05_contact_employment`

- `CustomerContact` 新增英文名、部门、首选语言、时区、主要联系人、离职生效日期及营销抑制字段。
- 增加同一客户最多一个在职主要联系人的条件唯一约束。
- 增加离职日期与离职状态一致性约束。
- 新增 `CustomerContactEmploymentEvent`，保存生效日、事件类型、职位、部门、角色、主要联系人状态、变更快照、操作人与备注。
- 新增 `CustomerContactTaskLink`，用于批量任务及离职任务策略追溯。
- 写入联系人语言和时区配置字典。
- 仅为原有联系人生成初始任职快照，没有修改客户归属、联系方式或历史业务数据。
- 迁移已在真实 PostgreSQL 执行，迁移漂移检查为 `No changes detected`。

## 六、异常和权限

| 状态 | 处理方式 |
|---|---|
| 400 | 展示后端字段错误 |
| 401 | 提示登录失效，由现有登录恢复流程接管 |
| 403 | 隐藏或禁用无权限操作，并展示权限提示 |
| 409 | 展示重复或业务冲突，要求人工确认 |
| 412 | 提示数据已被他人修改，重新获取后再操作 |
| 428 | 提示缺少数据版本，要求重新打开联系人 |
| 500 | 保留表单内容并允许重试 |
| 网络异常 | 保留表单内容并提示检查服务 |

## 九、仍存在的差异与限制

1. 真实数据库的联系人数量、姓名和联系方式与 Figma 示例数据不同；这是计划允许的内容差异，没有伪造数据消除。
2. 全站已确认不显示面包屑，因此客户头部未恢复 Figma 示例中的面包屑行；这是既有全局规则，不是遗漏。
3. 计划要求保留“紧凑显示”，因此工具栏比原始桌面静态稿多一个密度切换入口；默认状态仍与 Figma 的 48px 行高一致。
4. 没有独立营销或消息模块；“移出营销名单”保存真实抑制状态，“通知相关人员”仅创建真实待办、时间线和审计记录。
5. OpenAPI 仍有 2 条项目既有的角色枚举命名警告，校验无错误。
