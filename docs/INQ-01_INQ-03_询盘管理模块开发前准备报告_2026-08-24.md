# INQ-01～INQ-03 询盘管理模块开发前准备报告

日期：2026-08-24  
项目：haiqu ERP / CRM  
范围：询盘列表、待分配队列、状态看板、多行询盘编辑、询盘详情、SLA 与状态流转  
工作边界：本轮只检查和制定开发方案，没有修改业务代码、数据库、Migration、API、路由、公共组件或样式。

## 1. 总体结论

结论：**⚠️ 询盘模块可以开始正式开发，但必须采用“后端业务基础先行、前端随后接入”的顺序，不能直接基于现有 API 开始拼 Figma 页面。**

现有代码已经具备以下基础：

- 询盘和多行明细模型。
- 客户、交易主体、联系人、负责人关联。
- 询盘编号生成。
- 基础增查改、明细增改删、附件关联、任务查询。
- ETag / `If-Match` 并发保护。
- 客户数据范围隔离、审计日志和客户时间线。
- 简单状态流转与单一 SLA 记录。
- PostgreSQL 约束、索引和跨客户一致性触发器。

但现有实现仍缺少 Figma 核心能力：

- 负责人不能为空，无法形成“待分配队列”。
- 状态模型与 PRD、Figma 均不一致。
- 没有列表指标、批量分配、标记无效、状态看板数据接口。
- 没有首响与需求确认的分阶段 SLA、超时升级和补偿任务。
- 没有询盘草稿版本、组合保存幂等和渠道事件幂等。
- 多行明细缺少期望日期、产品图片、产品匹配状态等字段。
- 没有接收时客户/联系人/来源快照。
- 没有通用安全文件上传 API；当前只能关联已经存在的文件。
- 前端只有工作台中的最小询盘创建抽屉，没有询盘路由、类型、API 客户端和正式页面。

因此，当前实现不是“前端缺页面”，而是“基础数据模型存在，但业务闭环尚未完成”。

## 3. 错误前提、逻辑跳跃与信息缺失

### 3.1 “已有询盘 API，所以只需开发页面”是错误前提

现有 API 只能完成基础 CRUD 和三段式流转，无法支撑待分配队列、完整看板、分阶段 SLA 和草稿版本。若前端先行，只能通过硬编码、字段误用或多次请求拼接，最终必然返工。

### 3.2 “Figma 状态文字可直接作为数据库状态”是逻辑跳跃

原型同时出现：

- 列表状态：待确认、待分配、需求确认、报价中、样品中、已转报价。
- 详情步骤：新询盘、已分配、已首响、需求确认、报价中、已转订单。
- PRD 状态：新询盘、分析中、待报价、报价中、已报价、跟进中、已转订单、丢单、关闭。
- 当前数据库状态：草稿、已提交、处理中、已报价、已关闭、已取消。

这些不是同一套状态。若合并成一个字段，会出现“一个询盘同时样品中又报价中”无法表达、负责人改变导致状态被覆盖、订单模块未上线却能手工标记已转订单等问题。

### 3.3 “页面倒计时就是 SLA”是错误前提

浏览器倒计时只负责显示，不能成为 SLA 事实源。真正 SLA 必须由服务端计算并持久化截止时间，还要考虑时区、工作日、策略版本、超时升级和浏览器关闭后的后台执行。

### 3.4 “附件字段存在就能上传文件”是错误前提

当前存在 `BusinessFile` 和询盘文件关联，但没有通用上传 API。缺少上传、文件签名校验、病毒扫描、失败清理和访问权限链路时，不能把附件按钮做成假成功。

### 3.5 “看板拖动等于真实状态流转”存在业务风险

Figma 已明确提示看板拖动只模拟变更，真实流转必须经过详情校验。前端不能在拖动后直接更新列位置并假定成功；服务端必须校验当前状态、必填资料、权限、ETag 和关联事实。

### 3.6 当前仍缺少的统计口径

- “今日”使用公司时区还是浏览器时区。
- “即将超 SLA”的阈值，原型示例为 30 分钟，但 PRD 未固定。
- “本月转化”的分母是本月新询盘、进入待报价询盘，还是所有进行中询盘。
- “报价中”以询盘状态为准，还是以有效报价草稿为准。

本报告给出可执行默认值，页面同时显示口径，后续可配置调整。

## 4. 建议采用的统一业务模型

### 4.1 主状态与派生状态分离

建议将询盘主状态统一为：

| API / DB Code | 中文 | 说明 |
|---|---|---|
| `DRAFT` | 草稿 | 尚未正式提交，可编辑全部草稿字段和明细 |
| `NEW` | 新询盘 | 已提交，尚未完成首次处理 |
| `ANALYZING` | 分析中 | 正在确认需求、产品或贸易条件 |
| `READY_FOR_QUOTE` | 待报价 | 已具备报价条件，等待创建报价 |
| `QUOTING` | 报价中 | 已有有效报价草稿或正在制作报价 |
| `QUOTED` | 已报价 | 已发送至少一个正式报价版本 |
| `FOLLOW_UP` | 跟进中 | 报价后持续跟进客户反馈 |
| `CONVERTED` | 已转订单 | 只能由未来订单模块的有效订单事实触发 |
| `LOST` | 已丢单 | 明确竞争失败，原因必填 |
| `CLOSED` | 已关闭 | 重复、垃圾、取消或无法处理，原因必填 |
| `CANCELLED` | 已取消 | 仅用于草稿或误建记录取消；保留审计 |

派生显示不写入主状态：

| 原型显示 | 真实来源 |
|---|---|
| 待分配 | `owner_employee_id IS NULL` 且主状态非终态 |
| 已分配 | 当前负责人存在，并有分配时间或分配记录 |
| 已首响 | 首响 SLA 已达成或存在有效首响事件 |
| 需求确认 | 主状态 `ANALYZING` 且核心需求完整，或需求确认里程碑已完成 |
| 样品中 | 存在有效、未结束的关联样品单 |
| 已转报价 | 存在已创建或已发送的关联报价，按具体标签区分 |
| SLA 正常/即将超时/已超时 | 当前运行中的 SLA 截止时间计算结果 |

### 4.2 默认统计口径

- 今日新增：公司时区当天 `received_at` 范围内的非归档询盘。
- 待分配：负责人为空，且状态属于 `NEW/ANALYZING/READY_FOR_QUOTE`。
- 即将超 SLA：运行中 SLA 距截止时间大于 0 且不超过 30 分钟。
- 报价中：主状态为 `QUOTING`；报价模块接入后同时校验存在有效草稿报价。
- 本月转化：本月接收的非无效询盘中，至少产生一个正式发送报价版本的询盘数 ÷ 本月接收的非无效询盘数。
- 页面必须显示公司时区和统计周期，不能只显示裸数字。

### 4.3 客户和负责人默认规则

- 已有客户：选择现有客户，国家、联系人、当前主要负责人自动带入。
- 新客户：按 Figma 重复客户提示，允许在询盘事务中创建最小客户档案；用户必须同时具备新增客户和新增询盘权限。
- 高风险重复：必须选择已有客户或明确确认继续创建，后端在事务内重新检查。
- 已有客户有当前主要负责人：默认建议该负责人，但用户可在权限允许时调整。
- 没有负责人或规则无法命中：询盘进入待分配队列，不伪造推荐人。
- 第一阶段不实现“按团队容量自动均分”；没有团队容量口径时，建议负责人显示“暂无推荐”。

### 4.4 产品默认规则

当前没有产品主数据模块，不能伪造产品外键。

- 保留客户原始产品描述、规格、数量、单位、目标价和期望日期。
- 产品图片通过询盘行文件关联保存。
- 增加产品匹配状态，当前可为“待匹配”。
- 产品模块上线后再增加可空产品/SKU 外键；历史原始描述和图片必须继续保留，不能被产品主数据覆盖。

### 6.3 当前查询能力

当前已有：

- `q`：编号、主题、描述、客户名称。
- `status`。
- `customer_id`、交易主体、联系人、负责人。
- 接收时间、期望时间范围。
- 排序：接收、期望、提交、创建、更新时间。
- 标准分页 20 条。

必须补充：

- `assignment_status=ASSIGNED|UNASSIGNED`。
- `source_code`。
- `product_q`。
- `sla_state=NORMAL|DUE_SOON|BREACHED|NONE`。
- `stage` 或统一后的 `status`。
- `archived`、`ordering`、`page_size` 与保存视图白名单一致。
- 当前 SavedView 中存在 `overdue`，但 InquiryFilter 没有该参数，属于文档/实现不一致，必须统一为 `sla_state` 或真正实现 `overdue`。

### 6.4 性能要求

当前 `inquiries_with_context()` 在列表也预取明细、文件、任务和 SLA，数据量增加后浪费明显。正式开发应拆分：

- `inquiries_for_list()`：只 `select_related` 客户、负责人，并注解第一产品、产品行数、当前 SLA、关联报价/样品标记。
- `inquiry_for_detail()`：详情才预取明细、文件、任务、SLA 和沟通。
- 指标使用聚合查询，不能为五张卡分别拉取完整列表。
- 看板每列独立限制条数和游标/分页，不能一次加载全部询盘。

## 7. INQ-02 多行询盘编辑准备结果

### 7.1 页面结构

- 基础信息。
- 多行产品需求。
- 补充需求、贸易条件和附件。
- 取消、保存草稿、提交并分配。
- 校验失败、疑似重复客户、保存成功 V2 三种状态。

### 7.2 推荐组合写入协议

现有头部 PATCH 与逐行明细接口会产生多次 ETag 变化，不适合一个多行表单整体保存。建议保留旧接口兼容，同时新增组合草稿接口：

- `POST /api/v1/inquiries/`：创建草稿，支持头部、`items[]`、客户模式和幂等键。
- `PATCH /api/v1/inquiries/{id}/draft/`：在一个事务内保存头部、明细增删改和附件引用。
- 请求必须带 `If-Match`。
- 请求体带 `idempotency_key`；重复提交同一请求返回同一版本，不重复创建行或文件关联。
- 服务端成功后返回完整详情、最新 ETag 和 `draft_version`。

### 7.3 建议数据库变更

#### Inquiry

- `owner_employee` 改为可空。
- 扩展统一状态枚举。
- 增加 `customer_snapshot JSONB`，保存接收时客户名称、国家和必要展示信息。
- 增加 `contact_snapshot JSONB`，只保存允许的历史显示信息；敏感值继续受权限控制。
- 增加 `source_snapshot JSONB` 和 `snapshot_schema_version`。

## 8. INQ-03 详情、SLA 与状态流转准备结果

### 8.1 Figma 尺寸基准

1920×1080：

- 询盘概况：1632×180px。
- 状态流转：1632×116px。
- 询盘内容：1070×556px。
- SLA 与协同：550×556px。

1440×900：

- 询盘概况：1328×180px。
- 状态流转：1328×116px。
- 询盘内容：850×376px。
- SLA 与协同：466×376px。

### 8.2 SLA 目标设计

当前服务只选择第一条启用策略，并在提交时创建一个“响应或解决”计时；这不能表达 Figma 的首响与需求确认。

建议：

- 同一询盘允许多条阶段 SLA：`FIRST_RESPONSE`、`REQUIREMENT_CONFIRMATION`、未来 `QUOTE_PREPARATION`。
- `InquirySlaLink` 增加 `stage_code`，并限制同一询盘同一阶段只存在一个当前有效追踪。
- 策略按来源、优先级、国家/时区匹配；无法匹配时使用默认策略。
- 截止时间由服务端生成，前端只根据服务端时间和截止时间显示倒计时。
- 后台定时任务处理超时：更新状态、通知负责人/主管、创建幂等复查任务。
- 幂等键示例：`INQUIRY_SLA_ESCALATION:{inquiry_id}:{stage_code}:{deadline_version}`。
- 延长 SLA 必须填写原因，记录旧截止时间、新截止时间、操作者和审计。
- 如果第一阶段暂不接公司工作日历，必须明确标注“自然时间”；不能页面写工作日 SLA、后台却按自然时间计算。

### 8.3 状态流转规则

- 普通 PATCH 禁止直接修改状态。
- 所有状态变化走专用 action、事务、ETag 和审计。
- `DRAFT→NEW`：至少一条有效明细、客户存在、来源存在。
- `NEW→ANALYZING`：已分配且已记录首个处理动作。
- `ANALYZING→READY_FOR_QUOTE`：核心产品、数量、单位、贸易要求满足配置。
- `READY_FOR_QUOTE→QUOTING`：只能由有效报价草稿创建事实触发。
- `QUOTING→QUOTED`：只能由正式报价版本发送事实触发。
- `QUOTED→FOLLOW_UP`：创建有效跟进动作或任务。
- `→CONVERTED`：未来只接受订单模块事件，当前人工请求返回 409。
- `→LOST/CLOSED`：原因必填；丢单额外保存竞争原因。
- 跳级必须服务端拒绝，不能只靠前端禁用按钮。

### 8.4 详情加载策略

首屏一次加载：

- 询盘头、客户/联系人摘要、明细、当前主状态。
- 当前运行 SLA 和负责人。
- 最新 3 条沟通摘要。
- 当前主要下一步任务。
- 附件摘要数量。

按需加载：

- 全部沟通记录分页。
- 全部附件和下载权限。
- 状态/审计历史。
- 全部任务。
- 报价和样品关系。

禁止把客户整个 360° 数据和所有关联对象一次性塞进询盘详情。

## 10. 权限与数据范围

### 10.1 现有事实

- 询盘数据范围继承客户可见范围。
- ViewSet 使用 Django 默认询盘权限。
- 当前没有“分配、批量操作、延长 SLA、强制流转”独立权限。
- 负责人选择目前只限制为在职员工，没有限定用户可分配的组织/团队范围。

### 10.2 建议新增权限

- `assign_inquiry`：分配或转交询盘。
- `bulk_change_inquiry`：批量分配、批量标记无效。
- `extend_inquiry_sla`：延长 SLA。
- `override_inquiry_transition`：允许受控例外流转，但仍不得伪造订单事实。
- `view_team_inquiry_metrics`：查看团队聚合指标。
- 附件继续复用文件查看/下载权限和客户数据范围。

### 10.3 权限规则

- 业务员只看自己可见客户范围内询盘。
- 主管的团队聚合权限不自动等于全部客户明细权限。
- 无敏感联系人权限时，详情返回脱敏邮箱和联系人信息。
- 推荐负责人、队列和指标不能泄露无权客户名称或员工负载明细。
- 新建最小客户时同时检查 `customers.add_customeraccount`。
- 创建报价按钮同时检查询盘变更权限和报价新增权限。

## 13. P0 / P1 / P2 问题清单

### P0 — 后端基础完成前阻塞完整页面联调

1. 负责人非空，无法保存待分配询盘。
2. PRD、Figma、Model 四套状态口径冲突。
3. 缺少接收时客户/来源快照。
4. 缺少组合草稿保存、版本和幂等。
5. 缺少行期望日期和行级图片关系。
6. 缺少批量分配、队列、看板和指标接口。
7. SLA 只能单阶段计时，没有超时升级执行。
8. 没有通用安全文件上传 API。
9. 状态 CHECK 与 PostgreSQL 触发器包含旧状态集合，变更必须同步迁移。

### P1 — 正式开发中同步解决

1. “询价/询盘”中文术语混用，界面和错误信息统一为“询盘”。
2. 询盘来源仍是自由字符串，需受控字典和显示名。
3. 列表 Selector 预取过多，需拆分列表/详情查询。
4. 保存视图的 Inquiry 白名单与真实 Filter 不一致。
5. 缺少分配、批量、SLA 例外等独立权限。
6. 联系人详情摘要和敏感信息脱敏未进入询盘 Serializer。
7. 外部事件只有来源唯一约束，没有乱序/失败补偿模型。
8. 工作台询盘指标仍为演示数据，需在本模块完成后替换。

### P2 — 开发过程中处理

1. 空数据、局部异常、403、409、412、428 和 500 状态文案。
2. 列设置、保存视图、刷新和分页细节。
3. 窄屏折叠、横向表格滚动和抽屉适配。
4. 路由懒加载和生产包拆分。
5. 看板拖动动画和键盘可访问性。

## 16. 实施默认约束与待产品复核项

为使另一边可以直接开始开发，本报告采用以下默认值：

1. 允许在询盘流程中创建最小客户，但必须具备客户新增权限并经过重复确认。
2. 即将超 SLA 的默认阈值为 30 分钟，后续放入策略配置。
3. 本月转化默认统计“本月接收询盘转正式报价”的同月队列转化率。
4. 已有客户优先建议当前主要负责人；无可靠建议时进入待分配队列。
5. 当前不建设产品主数据 FK，只保存客户原始需求和待匹配状态。
6. 当前不允许人工转订单。
7. 报价前端未上线前，创建报价按钮只展示未接入状态，不伪造成功。
8. 外部渠道未接入时不实现假同步时间；渠道事件模型只在本期确认接入真实渠道时落地。

如果产品对第 1、2、3 项有不同口径，应在后端 Migration 和 API 定稿前修改；其余约束属于数据正确性和模块边界要求，不建议放宽。

## 17. 交付结论

现有询盘后端基础可复用，但不能直接满足 INQ-01～INQ-03。正式开发方应先完成 P0 数据模型、状态、SLA、分配和上传能力，再进行 Figma 页面开发。

最终判断：**⚠️ 询盘模块可以开发，但存在必须在前端完整联调前解决的 P0 基础问题。**
