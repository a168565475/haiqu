# QUO-01～QUO-06 报价管理模块开发前准备报告

> 日期：2026-08-24  
> 性质：开发前准备与交接，不包含业务代码开发  
> 范围：报价列表、报价编辑、包装与装柜数量档、固定模板预览与发送、版本树与差异、历史价格趋势

## 1. 总体结论

结论：**报价模块可以启动开发，但不能按“已有后端，补六张前端页面”执行。必须先补齐报价领域模型、真实文件生成、真实发送语义、版本可比性和历史趋势口径，再进入 Vue 页面与 Figma 视觉还原。**

已经确认的事实：

- Figma 不是 3 张报价页面，而是 6 组完整页面：
  - `QUO-01` 报价列表。
  - `QUO-02` 报价编辑器。
  - `QUO-03` 包装与装柜数量档。
  - `QUO-04` 固定模板预览与发送。
  - `QUO-05` 报价版本树与差异。
  - `QUO-06` 历史价格趋势。
- 当前 Django 后端已经有报价、版本、报价行、普通数量阶梯、锁定、审批、正式文件登记和发送记录登记的基础骨架。
- 当前后端没有包装尺寸、箱规 CBM、装柜档、自动/人工装柜数量、产品图片快照、成本与毛利快照、父版本、稳定行血缘、版本差异和价格趋势能力。
- 当前名为 `generate-document` 的接口**不生成文件**，只是把一个已经存在且扫描为安全的 `BusinessFile` 登记成正式报价文档。
- 当前 `dispatch` 接口**不发送邮件**，只是写入 `QuotationDispatchRecord` 并把版本状态改为 `SENT`。
- 项目没有 SMTP/邮件配置，也没有 PDF/HTML 文档渲染依赖。
- 前端没有 `/quotations` 路由、页面、API 类型或报价组件；侧栏“报价管理”只有权限和图标，没有跳转地址。
- PostgreSQL 中报价、版本、行、数量档、模板、文档、发送、审批链接、任务链接均为 0 条；固定模板也是 0 条。
- 订单模块已明确延后，因此 `QUO-06` 中“最近成交价/成交趋势”当前没有可信事实源，不能拿已发送报价价冒充成交价。

本报告的独立判断：

1. **不同意先做静态六页，再补后端。** 报价金额、版本、文件和发送属于不可伪造的商业事实，静态页面会把错误契约固化到前端。
2. **不同意继续把“登记文件”叫“生成文件”、把“登记发送”叫“发送邮件”。** 这会形成审计假象：系统显示已发送，但实际可能没有对外发送。
3. **不同意把 20GP/40GP/40HQ 写成固定数据库列。** PRD 已明确它们是可配置字典，且有效容积、装载系数必须版本化。
4. **不同意现在展示真实“成交价”。** 订单模块未开发，成交事实不存在；应返回 `null` 并隐藏成交指标，或明确标记“仅报价趋势”。
5. **不同意只用行号做版本差异。** 复制、插入、删除或重排后会误配，必须给报价行增加跨版本稳定血缘标识。

交付状态判断：

- `QUO-01`：补充列表摘要、统计和派生状态后可开发。
- `QUO-02`：补充结构化条款、产品快照、草稿事务与商业快照变更检测后可开发。
- `QUO-03`：必须先新增数据库模型和计算服务。
- `QUO-04`：必须先确定固定模板、卖方主体、字体、PDF 方案和真实邮件通道。
- `QUO-05`：必须先增加父版本、行血缘、差异接口和敏感字段权限。
- `QUO-06`：可先做“正式报价趋势”；成交价等订单相关内容必须保持空值或禁用。

## 3. 错误前提、逻辑跳跃与信息缺失

### 3.1 “报价后端已经完成”是错误前提

当前后端只覆盖基础生命周期，不能支持原型中的包装、装柜数量档、固定模板真实生成、发送、差异和趋势。直接做前端会出现大量页面字段无处保存、计算口径不一致和按钮假成功。

### 3.2 “数量阶梯就是装柜数量档”是错误前提

现有 `QuotationQuantityTier` 只有：

- 最小数量。
- 最大数量。
- 单价。

而装柜档需要：

- 集装箱类型。
- 有效容积及配置版本。
- 装载系数。
- 自动装柜数量。
- 人工覆盖数量。
- 覆盖原因、依据、申请人、批准人和批准时间。
- 最终生效数量。
- 单价、贸易条款、地点和包装口径。

两者应并存，不应强行把普通数量区间模型改名冒充装柜模型。

### 3.3 “generate-document 会生成 PDF”是错误前提

现有接口接收 `file_id`，把已存在文件登记为正式文档。它没有模板渲染、PDF 生成、字体嵌入、文件保存或失败错误 ID。若前端按原型展示“生成成功”，会产生错误审计证据。

建议：

- 将现有能力明确为“登记已有正式文件”。
- 新增真正的预览和正式生成接口。
- 对旧路径保留兼容，但禁止 UI 把它解释为服务器生成。

### 3.4 “dispatch 已经发邮件”是错误前提

项目没有 SMTP 配置；当前接口只写数据库记录。必须拆分：

- 真实邮件发送。
- 人工通过其他渠道发送后的登记。

两者的状态、错误处理和审计不能共用“发送成功”。

### 3.5 “报价状态是一个枚举”是逻辑跳跃

当前至少有四个正交维度：

1. 报价结果：进行中、接受、失败、取消。
2. 版本生命周期：草稿、锁定、签发、已发送、被替代、作废。
3. 审批状态：未提交、待审批、批准、拒绝、撤回。
4. 派生状态：待发送、客户反馈中、已过期。

Figma 的单个“状态”标签应由服务端返回统一 `display_status`，不能让前端自行拼接四套状态。

### 3.6 “已发送版本不可变”目前只部分成立

现有服务禁止修改非草稿版本的版本字段、行和阶梯，这是正确基础。但仍缺少：

- 正式版本内容哈希的全量覆盖定义。
- 父版本和变更说明。
- 行跨版本血缘。
- 模板版本变化时的强制新版本规则。
- 人工装柜覆盖的审批冻结。
- 对外附件内容与发送记录绑定。

### 3.7 “版本差异按行号比较”会误导

复制版本会生成新的报价行 ID；插入、删除、重排后行号也可能变化。按 ID 或行号比较都会误判。必须新增稳定 `lineage_key`，复制版本时继承，新增行时生成。

### 3.8 “历史成交价已有数据”与已确认边界冲突

订单模块尚未开发，数据库没有可信成交价来源。替代方案：

- 本期只实现已发送报价趋势。
- API 的成交价、成交数量返回 `null`，页面隐藏相关指标并说明“订单模块尚未接入”。
- 不允许把 `WON` 的报价价自动当成交价；客户接受报价仍不等于最终订单成交价。

### 3.9 “客户 + 产品即可比较价格”是错误口径

PRD 已规定可比维度至少包括：客户、SKU、币种、贸易条款、地点、数量区间和包装口径。遗漏任何一项都可能把 FOB 与 CIF、不同包装或不同装柜档画在一条线上，产生错误决策。

### 3.10 产品主数据仍缺失

当前项目没有产品/SKU 模型。报价行只有描述快照。不能在本模块偷偷新建一个残缺产品模块。

建议本期：

- 报价行保存受控的 SKU/Item No 和产品属性快照。
- 可选关联询盘行。
- 预留未来 `product_id`，但不把不存在的产品 ID 设为必填。
- 价格趋势使用明确的临时 `comparison_key`，未来接产品模块后做可审计映射。

### 3.11 卖方主体和固定模板内容缺失

当前组织模型只是组织单元，不是可对外开具报价的法定卖方主体。数据库也没有启用中的报价模板。开发前仍缺：

- 公司中英文抬头。
- 法定地址、电话、邮箱、网站。
- Logo 和授权签字资源。
- 对外业务联系人规则。
- 付款条款、贸易条款、法律声明。
- 模板发布人和生效版本。

没有这些资料时可以做 QA 模板，但不能生成正式对外文件。

### 3.12 汇率、成本和毛利口径缺失

系统没有汇率表、成本模型、毛利公式版本和独立查看权限。`QUO-06` 的平均毛利率、折算本位币价格不能靠前端临时计算。

替代方案：

- 本期无成本/汇率来源时隐藏毛利和本位币指标。
- 若允许人工填入，必须保存来源、日期、币种、汇率、公式版本和操作者快照，并受独立权限控制。

### 3.13 导出范围未确认

Figma 列表有“导出”，但当前无报价导出 API。导出会涉及：

- 当前筛选还是勾选行。
- CSV/XLSX/PDF。
- 敏感成本、毛利、联系人和地址脱敏。
- 最大行数、审计和文件保存。

默认建议本期只导出列表摘要 XLSX，最多 5,000 条，异步能力未建立前同步生成且超限拒绝；正式报价 PDF 下载走版本文档接口，不混入列表导出。

## 4. 统一业务状态与派生口径

### 4.1 保留的数据库主状态

报价结果 `Quotation.outcome_status`：

- `OPEN`：业务仍在进行。
- `WON`：客户接受指定正式版本；不等同于订单成交。
- `LOST`：客户拒绝/失单，原因必填。
- `CANCELLED`：内部取消，原因必填。

版本状态 `QuotationVersion.status`：

- `DRAFT`：可编辑草稿。
- `LOCKED`：内容冻结，可等待审批或签发。
- `ISSUED`：正式文件前置条件满足并已签发。
- `SENT`：至少存在一条真实成功发送或经明确确认的外部发送记录。
- `SUPERSEDED`：被新正式版本替代。
- `VOID`：撤回/作废，原因和是否通知客户必填。

审批状态继续来自 `ApprovalRequest`，不复制进版本枚举。

### 4.2 统一展示状态

列表 API 返回 `display_status` 和 `display_status_label`，建议优先级：

1. `ACCEPTED`：报价结果为 WON 且当前版本为接受版本。
2. `REJECTED`：报价结果为 LOST。
3. `WITHDRAWN`：当前版本 VOID 或报价 CANCELLED。
4. `EXPIRED`：正式版本有效期早于今天，且未接受。
5. `SUPERSEDED`。
6. `CUSTOMER_FEEDBACK`：已发送且存在待处理客户反馈状态。
7. `SENT`。
8. `APPROVED`：审批通过、尚未真实发送。
9. `PENDING_APPROVAL`。
10. `READY_TO_SEND`：已签发并有正式文件、尚未发送。
11. `LOCKED`。
12. `DRAFT`。

过期是服务端按 `Asia/Shanghai` 日期派生，不建议每天批量改写历史状态。若以后需要自动通知，另由调度任务写提醒/事件。

### 4.3 发送成功定义

- SMTP/邮件服务已接受消息并返回 message id：可记 `SUBMITTED`，版本可转 `SENT`。
- 外部邮箱最终送达需要回执/退信处理；没有该能力时不得显示“已送达”。
- 人工 WhatsApp/微信/线下发送：必须使用“登记外部发送”，由用户明确确认并记录渠道、收件人、附件哈希和时间。
- 仅创建数据库记录、未调用任何通道：不能算发送成功。

## 5. 报价计算与快照规则

### 5.1 金额

- 所有金额使用 `Decimal`，禁止二进制浮点。
- `line_total = quantity × unit_price × (1 - discount_rate)`。
- 内部计算建议保留 4 位小数；显示/正式文件按币种精度与公司舍入配置。
- 同一版本的页面、API 和 PDF 必须使用同一计算服务，不能三处各算一次。
- 折扣、税、运费和附加费的含税/未税口径必须进入版本快照。

### 5.2 CBM

厘米口径：

`carton_cbm = length_cm × width_cm × height_cm ÷ 1,000,000`

规则：

- 任一尺寸缺失、为 0、负数或单位不一致时，`carton_cbm = null`，阻止完成配置。
- 单位必须显式保存；换算后同时保存原始输入和标准化厘米值。
- CBM 建议保存 6 位小数，展示 4 位；舍入规则固定。
- 手工修改 CBM 不作为常规能力；若必须覆盖，按与装柜数量相同的审批和审计规则处理。

### 5.3 装柜数量

自动箱数：

`floor(container_effective_volume × load_factor ÷ carton_cbm)`

自动件数：

`auto_quantity = auto_cartons × pieces_per_carton`

必须保存：

- 集装箱类型代码和名称快照。
- 有效容积、装载系数及其配置版本。
- 自动箱数、自动件数。
- 人工箱数/件数、原因、依据、申请人、批准人、批准时间。
- 最终生效数量。

禁止写死 28/56/68 m³。Figma 中的数值只用于视觉样例。

### 5.4 价格可比键

每条趋势点必须有服务端生成的 `comparison_key`，至少纳入：

- 客户。
- SKU/Item No 标准化值。
- 币种。
- Incoterms 规则版本、术语和地点。
- 数量档/集装箱类型。
- 计价单位。
- 包装尺寸、每箱数量和重量口径摘要。

任一关键维度缺失时只允许出现在历史明细，不能进入聚合曲线。

### 5.5 正式版本快照

锁定/签发时保存：

- 买卖方主体、地址、联系人。
- 模板、Logo、字体和条款版本。
- 产品描述、SKU、图片哈希、规格、包装、重量和 HS Code。
- 数量档和装柜计算参数。
- 币种、汇率、成本和毛利公式版本（若启用）。
- 生成文件摘要。

主数据后续变化不得反向改变历史版本。

## 8. 数据库变更建议

所有变更必须向前兼容，不删除现有模型和字段；现有数据虽为 0，也不能以此为理由做破坏性迁移。

### 8.1 `QuotationVersion` 新增

- `parent_version`：可空，自关联，版本复制来源。
- `revision_reason`：新版本原因，复制已发送/锁定版本时必填。
- `seller_entity_snapshot`：卖方主体快照。
- `incoterm_code`、`incoterm_version`、`incoterm_place`：结构化贸易条款。
- `payment_term_code`：受控付款条款代码。
- `lead_time_text`、`sample_lead_time_text`、`customization_scope`。
- `snapshot_schema_version`：快照结构版本。
- `content_hash`：锁定内容哈希。

现有 `terms_snapshot` 保留，用于完整渲染快照，但常用筛选字段不能只埋在 JSON 中。

### 8.2 `QuotationLine` 新增

- `lineage_key`：UUID，跨版本稳定。
- `source_inquiry_line_id`：可空；必须属于报价来源询盘和同一客户。
- `sku_snapshot`、`item_no_snapshot`。
- `customer_requirement_snapshot`。
- `material_snapshot`、`fabric_snapshot`、`tube_snapshot`。
- `expanded_size_snapshot`、`color_snapshot`。
- `unit_weight`、`weight_unit_code`、`hs_code_snapshot`。
- `product_image_file`：可空，关联 CLEAN 文件。
- `product_image_hash_snapshot`。
- `comparison_key`：锁定时生成。

### 8.3 新表 `QuotationLinePackaging`

建议一条报价行一个当前包装快照：

- 报价行一对一。
- 长、宽、高原始值和单位。
- 标准化厘米值。
- 每箱数量。
- 毛重、净重和单位。
- 自动 CBM、最终 CBM。
- 计算规则版本。
- 可选人工覆盖及审计字段。

### 8.4 新表 `QuotationContainerTier`

- 报价行。
- 档位序号。
- 集装箱类型代码/名称快照。
- 配置字典 ID 和版本快照。
- 有效容积、装载系数。
- 自动箱数、自动件数。
- 人工箱数、人工件数。
- 覆盖原因、依据、申请人、批准人、批准时间。
- 最终箱数、最终件数。
- 单价、计价单位、运费、附加费。
- 状态：自动、待批准、已批准、拒绝。

唯一键：报价行 + 档位序号。另加报价行 + 集装箱类型的活动唯一约束，除非业务明确允许同一箱型多个数量档。

### 8.5 成本与毛利

建议新表 `QuotationLineCostSnapshot`，不要把敏感成本混入普通报价行序列化：

- 材料/采购、包装、运费、佣金、其他成本。
- 原币、成本币种、本位币。
- 汇率、汇率日期、来源和版本。
- 单位毛利、总毛利、毛利率。
- 公式版本、计算时间和计算人。

如果本期没有正式成本来源，该表可以不启用，但前端毛利卡必须隐藏，不能填演示值。

### 8.6 文档与发送增强

`QuotationDocument` 建议增加：

- 模板发布版本。
- 渲染器版本。
- 文件内容哈希。
- 生成事件 ID。
- 生成状态、错误码和错误摘要。

`QuotationDispatchRecord` 建议增加：

- `dispatch_mode`：真实邮件 / 人工登记。
- `delivery_status`：提交、失败、退信等。
- `idempotency_key`。
- 关联正式文档及附件哈希。
- 标准化收件人摘要。
- 通道 message id。
- 失败码和失败摘要。
- 重复发送确认来源。

### 8.7 索引

- 报价：客户、负责人、结果状态、更新时间。
- 版本：报价、版本号；状态、有效期；父版本。

## 9. 目标 API

统一响应必须提供稳定错误代码、字段错误、ETag 和 `allowed_actions`。关键写操作继续使用 `If-Match`。

### 9.1 列表与汇总

- `GET /api/v1/quotations/`
  - 参数：`q、customer_id、owner_employee_id、outcome_status、display_status、currency_code、incoterm_code、valid_from、valid_to、created_from、created_to、follow_up_window、archived、ordering、page_size`。
  - 一次返回客户摘要、最新版本、币种、贸易条款、金额、有效期、负责人、最近发送、下次跟进、展示状态和 allowed_actions。
- `GET /api/v1/quotations/summary/`
  - 返回 Figma 五张指标及明确口径。
  - 不从当前分页结果统计。
- `GET /api/v1/customers/{customer_id}/quotations/`
  - 与全局列表复用筛选、分页和序列化结构。
- `POST /api/v1/quotation-exports/`
  - 本期如实现，只导出列表摘要；尊重当前筛选、数据权限和敏感字段权限。

### 9.2 报价与版本

- 保留 `POST /api/v1/quotations/`。
- 保留 `GET/PATCH /api/v1/quotations/{id}/`。
- 保留 `GET/POST /api/v1/quotations/{id}/versions/`。
- 新版本复制锁定/正式版本时，`from_version_id` 和 `revision_reason` 必填。
- `GET/PATCH /api/v1/quotation-versions/{id}/`。
- `GET /api/v1/quotation-versions/{id}/snapshot-health/`
  - 返回主数据是否变化、缺失项和是否阻断。

### 9.3 报价行、包装与档位

- 保留版本下报价行新增/列表和报价行修改/删除。
- 增加普通数量阶梯的 PATCH/DELETE。
- `GET/PUT /api/v1/quotation-lines/{id}/packaging/`。
- `GET/POST /api/v1/quotation-lines/{id}/container-tiers/`。
- `PATCH/DELETE /api/v1/quotation-container-tiers/{id}/`。
- `POST /api/v1/quotation-container-tiers/{id}/request-override/`。
- `POST /api/v1/quotation-container-tiers/{id}/approve-override/`。
- `POST /api/v1/quotation-container-tiers/{id}/reject-override/`。

包装或档位变化后，服务端统一重算 CBM、装柜数量、行金额、版本汇总并返回新 ETag。

### 9.4 锁定、审批与签发

- `POST /api/v1/quotation-versions/{id}/validate/`：只校验，不改状态。
- 保留 `lock`、`submit-approval`、`issue`。
- 锁定前至少校验客户、买卖方快照、币种、贸易条款/地点、有效期、报价行、图片要求、包装、有效档位、金额和人工覆盖审批。
- 低毛利/成本过期/人工覆盖是否触发审批由策略返回，不在前端写死。

### 9.5 预览与正式文件

- `POST /api/v1/quotation-versions/{id}/preview/`
  - 返回短时 HTML/PDF 预览，不创建正式文档。
- `POST /api/v1/quotation-versions/{id}/generate-formal-document/`
  - 幂等生成正式 PDF。
  - 同一版本、模板版本和内容哈希重复调用返回同一文档。
  - 生成失败返回稳定错误 ID，例如 `DOC-GEN-503`，不创建损坏附件。
- `GET /api/v1/quotation-documents/{id}/download/`
  - 权限校验、审计和安全响应头。
- 现有 `generate-document` 仅作为“登记已有文件”的兼容接口，前端不使用它冒充生成。

### 9.6 发送

- `POST /api/v1/quotation-versions/{id}/send-email/`
  - 收件人、抄送、主题、正文、正式文档 ID、event_id。
  - 收件人异常或近期同收件人同文档重复发送返回 409 和确认令牌。
  - 确认重发只新增发送记录，不新建版本。
- `POST /api/v1/quotation-versions/{id}/register-external-dispatch/`
  - 供 WhatsApp、微信、线下或现有外部邮箱人工登记。
- `GET /api/v1/quotation-versions/{id}/dispatches/`。

只有真实邮件服务接受，或用户明确完成外部发送登记后，版本才可显示已发送。

### 9.7 差异与趋势

- `GET /api/v1/quotations/{id}/version-tree/`。
- `GET /api/v1/quotation-versions/compare/?base_id=&target_id=`。
  - 比较版本必须属于同一报价。
  - 返回头字段、报价行、包装、档位、条款和附件变化。
  - 敏感成本/毛利差异按权限剔除，而不是先返回再前端隐藏。
- `GET /api/v1/quotation-price-trends/`
  - 参数：`customer_id、comparison_key/sku、container_type、currency_code、incoterm_code、period、formal_only`。
  - 不同币种/单位/条款不可直接聚合。
  - `won_only` 在订单模块接入前禁用或只代表客户接受报价，不能标“成交价”。

## 10. 权限与数据范围

### 10.1 数据范围

- 报价继续继承客户可见范围。
- 查看版本、文件、发送记录、差异和趋势都必须先通过报价所属客户权限。
- 越权对象返回 404 或统一不可见响应，不泄露报价编号、客户名、价格、命中与否。
- 创建/转派负责人必须拥有来源客户访问权。

### 10.2 建议新增权限

- `view_quotation_cost`：查看成本快照。
- `view_quotation_margin`：查看毛利。
- `override_quotation_container_quantity`：申请人工覆盖。
- `approve_quotation_container_override`：批准人工覆盖。
- `generate_quotation_document`：生成正式文件。
- `download_quotation_document`：下载正式文件。
- `view_quotation_history_price`：查看历史价格。
- `export_quotation`：导出列表。

保留现有：签发、发送、接受、审批等权限。

### 10.3 敏感字段原则

- 无成本权限：API 根本不返回成本字段。
- 无毛利权限：不返回毛利、毛利率和可反推成本的汇总。
- 联系人邮箱/电话：列表脱敏；发送表单只有具备联系人敏感权限时可读取完整值。
- 历史价格授权到期后立即按当前权限重新校验，不能依赖前端缓存。

### 10.4 保存视图

现有 QUOTATION 白名单只有少量字段，建议与目标筛选统一：

- `q、customer_id、owner_employee_id、outcome_status、display_status、currency_code、incoterm_code、valid_from、valid_to、created_from、created_to、follow_up_window、archived、ordering、page_size`。

列定义也必须使用报价专用白名单；不能只验证“最多 30 个字符串”。敏感成本/毛利列即使被历史视图保存，也要按当前权限剔除。

## 11. 固定模板、PDF 与邮件的前置决定

### 11.1 固定模板

本期只允许一套已发布固定品牌模板，不做动态模板设计器。模板必须版本化，正式版本保存完整模板快照。

上线前必须由业务/法务提供：

- 卖方中英文主体与地址。
- Logo 原文件和授权签字规则。
- 固定页眉页脚。
- 付款、贸易、交期、有效期和法律声明。
- 色卡/公司介绍是否作为可选附页。
- 模板发布负责人和生效日期。

### 11.2 PDF 渲染建议

建议先做一轮技术验证，再锁定渲染器。优先方案：HTML/CSS 固定模板 + WeasyPrint，并在 Docker 镜像安装所需系统库，内嵌 Noto Sans SC 字体。

风险：

- 会增加镜像体积和系统依赖。
- 字体缺失会导致中文换行和分页漂移。
- 浏览器预览与 PDF 排版引擎并非完全一致。

替代方案是 ReportLab，但复杂表格、中文字体和版式维护成本更高。无论选哪种，都必须用同一份结构化快照生成，不能截图转 PDF。

### 11.3 邮件

若本期没有可用 SMTP/企业邮件 API：

- “发送报价”按钮必须显示未接入或只允许“登记外部发送”。
- 禁止点击后直接返回假成功。

若接入真实邮件：

- 增加环境变量、超时、TLS、发件人白名单和附件上限。
- 收件人必须来自当前报价客户，手填外部地址需二次确认和审计。
- 日志不能记录邮件正文中的敏感明文。
- 同 event_id 重试不得重复发送。

## 12. 版本差异与历史趋势

### 12.1 版本树

- 每个新版本明确 `parent_version`。
- V1 无父版本；复制 V1 生成 V2 时建立父子关系。
- 同一报价允许线性修订；本期不做复杂分支合并。
- 若两个用户同时从旧版本创建新版本，服务端返回冲突并提示当前最新版本。

### 12.2 差异算法

- 报价头按字段白名单比较。
- 报价行按 `lineage_key` 匹配。
- 包装、档位、条款按结构化字段比较。
- 数值差异同时返回旧值、新值、绝对变化和百分比；旧值为 0 时百分比为 `null`。
- 缺失血缘或快照版本不兼容时返回“不足以比较”，不能强行生成差异。

### 12.3 趋势数据

仅纳入：

- 用户有权查看的客户。
- 已真实发送或明确登记外部发送的正式版本。
- comparison_key 完整且可比的档位。
- 未作废的版本；被替代版本仍可作为历史点。

不纳入：

- 草稿、锁定但未发送版本。
- 演示数据。
- 币种、单位、包装或贸易条款不一致且无可靠换算的点。
- 订单模块未接入时的所谓“成交价”。

趋势洞察只做确定性规则，例如 12 个月变化、最近三次方向、最大/最小报价；不使用没有验证的 AI 结论。
