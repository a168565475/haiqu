# TASK-01 任务中心模块开发前准备报告

> 生成日期：2026-08-24  
> 项目：haiqu ERP / CRM  
> 本文用途：交给另一开发任务直接执行  
> 本轮边界：只做开发前准备与实施提示词，不修改业务代码、不新增 Migration、不写入业务数据库

## 1. 总体结论

结论：**任务中心可以开始开发，但不能按“现有 API 已齐全，只补一个页面”理解。**

当前项目已有可复用的任务基础能力：

- PostgreSQL 中已有 `business_task` 及客户、沟通、询盘、报价版本、样品五类任务来源关系表。
- Django / DRF 已有任务列表、创建、详情、编辑、开始、完成、取消、转派接口。
- 单条写操作已使用 ETag / `If-Match` 做并发控制。
- 创建、编辑、流转、转派会写审计日志；有关联客户时会写客户时间线。
- `SavedView` 已登记 `TASK` 模块。
- 工作台已经实现基础任务加载、任务详情抽屉及开始/完成动作，可复用 API 客户端、类型和交互经验。

但 TASK-01 Figma 所需的关键能力仍缺失：

- 没有正式任务中心前端路由和页面；侧栏“任务中心”当前只有权限判断，没有跳转地址。
- 没有“我的任务 / 团队任务”可验证的数据范围协议。
- 没有五张指标卡的统一汇总接口和确定统计口径。
- 没有任务类型、阻塞、等待客户/待反馈、提醒时间、协同人、完成结果等 PRD 字段。
- 列表接口不返回关联客户名称、关联对象编号/标题和业务来源名称，前端无法直接渲染 Figma 表格。
- 没有批量完成预览、批量完成、批量转交和批量幂等能力。
- 没有定时调度进程；PRD 第 18.3 节的时间型自动提醒目前无法完整运行。
- 保存视图使用 `assignee_employee_id`，真实筛选接口使用 `assignee_id`，契约不一致。
- Figma 把“逾期、阻塞、待反馈、进行中”放在同一状态列，但这些不是同一层级的数据库状态。
- 用户已明确订单模块暂不开发，当前任务来源也不支持订单；Figma 中的订单任务只能作为视觉示例，不能接成虚假业务能力。

因此建议分为两个交付范围：

1. **TASK-01 页面闭环（本次正式开发目标）**：真实列表、指标、筛选、保存视图、新建、查看/处理、批量完成、批量转交、权限、空/异常状态、Figma 1:1。
2. **任务自动化引擎（后续独立阶段）**：定时规则、提醒、升级、冷却期、重试、对账与外部事件闭环。

如果另一边只完成第 1 项，交付名称必须写“TASK-01 任务中心页面闭环”，不能写“任务与自动提醒模块全部完成”。

## 3. 错误前提、逻辑跳跃与信息缺失

### 3.1 “已有任务 CRUD，所以只做前端”是错误前提

现有 API 适合基础单条任务，不满足 TASK-01：

- 列表只返回来源类型和 UUID，不返回客户名称、业务编号或来源名称。
- 搜索只覆盖标题、描述，不能按客户搜索。
- 没有团队范围、任务类型、关联对象类型、截止时间预设筛选。
- 没有指标汇总和批量动作。

直接让前端逐行请求客户、询盘、报价或样品会产生 N+1 请求、权限错误和闪烁，不能接受。

### 3.2 “状态列就是一个状态枚举”是逻辑跳跃

Figma 示例同时出现：

- 待处理、进行中：主流程状态。
- 逾期：由 `due_at < now` 推导的期限状态。
- 阻塞：工作受阻原因。
- 待反馈：等待外部人员或客户的协作状态。

若把这些全部塞进 `BusinessTask.status`，会造成：

- “进行中且逾期”无法同时表达。
- “等待客户但已逾期”只能保留一个信息。
- 完成率、逾期率、状态流转都会失真。

建议保留主状态，新增等待/阻塞维度，并由 API 计算展示状态。

### 3.3 “我的任务”定义目前不准确

现有 `accessible_tasks()` 返回：

`负责人是我 OR 创建人是我`

这意味着“我创建给别人处理的任务”也会进入我的任务列表。它可能适合“我可查看的任务”，但不等于 Figma 的“我的任务”。

建议区分：

- `scope=ME`：当前负责人是我。
- `scope=CREATED_BY_ME`：我创建的任务，作为保存视图或高级筛选。
- `scope=TEAM`：经过团队权限和组织范围计算的团队任务。

### 3.4 “团队任务”没有可靠前提

项目有组织树和员工当前组织归属，但没有明确的“主管—下属”关系或任务团队范围制度。

默认建议：

- 具备 `view_team_businesstask` 权限的用户，可查看本人当前主组织及其下级组织中员工负责的任务。
- 超级用户或具备 `view_all_businesstask` 可查看全部任务。
- 不得仅因为拥有 `customers.view_all_customer` 就自动获得全部任务；客户范围和人员任务范围是两种权限。

该默认值仍需业务负责人复核。如果公司组织树不是管理汇报树，应改为专用团队关系，不能强行复用组织树。

### 3.5 “订单任务可以按原型实现”与已确认边界冲突

用户已确认订单模块暂不开发；当前任务 `SOURCE_CONFIG` 也没有订单来源。

因此：

- TASK-01 不新增订单模型、订单 API 或订单路由。
- 正式页面不显示伪造订单任务。
- 新建任务的关联对象中不提供订单选项。
- Figma 的 `ORD-*` 行仅用于视觉基准；视觉测试使用隔离的前端 fixture，不写入真实数据库。
- 将来订单模块上线后再增加 `ORDER` / `ORDER_MILESTONE` 来源映射和迁移。

### 3.6 “批量操作使用 event_id + object_version”目前不是事实

Figma 异常状态写了该幂等说明，但当前实现只有：

- 单条 ETag：由 `id + updated_at` 计算。
- 自动化任务唯一键：`automation_key`。
- 自动化执行表的 `idempotency_key`，但任务批量动作没有使用它。

所以该文案目前是目标设计，不是现有能力。开发时必须真正实现，或在实现前从页面删掉该承诺；不能只保留文案。

### 3.7 “自动提醒”缺少运行基础设施

当前 Compose 没有 Celery Worker、Celery Beat、RQ Worker 或其他调度服务。依赖时间触发的报价跟进、样品签收后提醒、采购周期提醒不能靠普通 HTTP 请求自动发生。

替代方案：

- TASK-01 阶段只展示和操作已经存在的任务；事件同步创建任务可继续由各业务服务事务内完成。
- 时间型规则单独建设可靠调度器、重试、幂等、告警和对账，不能在浏览器定时器中实现。

### 3.8 Figma 缺失交互设计

已确认 Figma 只有主列表和三种状态，没有以下设计：

- 新建/编辑任务抽屉。
- 任务详情/处理抽屉。
- 单条转派与批量转派弹窗。
- 保存视图命名弹窗、列设置面板。
- 团队任务无权限、加载中、部分失败、并发冲突、批量部分无权限状态。

因此这些交互无法声称“已有 Figma 1:1 基准”。建议复用现有 Element Plus 和客户/联系人/工作台抽屉规范，视觉风格对齐主页面；如果需要严格像素验收，应先补齐 Figma 节点。

## 4. 统一业务模型建议

### 4.1 主状态

保留现有数据库值：

`PENDING → IN_PROGRESS → COMPLETED`

旁路终态：`CANCELLED`

规则：

- 普通 PATCH 不允许修改状态。
- 开始、完成、取消必须使用专用动作。
- 终态不可再次编辑或流转。
- 完成时写 `completed_at`；取消时写独立 `cancelled_at` 和原因，不能借用完成时间。

### 4.2 工作受阻/等待维度

建议新增 `work_state`：

- `NORMAL`：正常推进。
- `WAITING_CUSTOMER`：等待客户/外部反馈。
- `BLOCKED`：内部或外部阻塞。

配套字段：

- `work_state_reason`：进入等待或阻塞时必填，最大 500 字。
- `next_check_at`：等待客户时必填。
- `work_state_changed_at`。

恢复处理时清空活动中的等待/阻塞信息，但历史写入任务事件和审计日志。

“已忽略”不建议作为普通主状态。若第一阶段确实需要忽略自动提醒，使用专用 `ignore` 动作，原因必填，并明确它是任务终止还是只抑制提醒；未确认前不实现为可点击动作。

### 4.3 派生期限状态

API 按 Asia/Shanghai 计算：

- `OVERDUE`：未完成且 `due_at < now`。
- `DUE_TODAY`：未完成且截止时间位于本地当天。
- `UPCOMING`：未完成且截止时间晚于当天。
- `NO_DUE_DATE`：未完成且无截止时间。
- `NONE`：完成或取消。

### 4.4 列表“展示状态”优先级

只用于 UI 标签，不写回数据库：

1. `BLOCKED` → 阻塞。
2. `OVERDUE` → 逾期。
3. `WAITING_CUSTOMER` → 待反馈。
4. 主状态 → 待处理 / 进行中 / 已完成 / 已取消。

同一行详情中仍必须显示主状态、期限状态和等待/阻塞原因，避免优先级覆盖导致信息丢失。

### 4.5 优先级

保留数据库值：`LOW / NORMAL / HIGH / URGENT`。

Figma 使用“低 / 中 / 高”，而当前 `NORMAL` 返回“普通”。建议：

- API 业务值不变。
- 正式界面将 `NORMAL` 展示为“中”。
- `URGENT` 展示为“紧急”，颜色不得只靠红色表达，标签必须保留文字。

### 4.6 任务类型、来源与关联对象必须分开

建议新增：

- `task_type`：客户跟进、沟通跟进、询盘响应、报价跟进、样品反馈、其他。
- `origin_type`：`MANUAL / BUSINESS_EVENT / AUTOMATION / SLA`。
- `origin_code`：例如 `QUOTATION_FOLLOW_UP`、`CONTACT_REPLACEMENT`，用于展示“来源”列与规则追踪。
- `automation_key`：继续作为自动任务去重键。
- 关联对象：继续使用现有关系表；第一阶段支持客户、沟通、询盘、报价版本、样品。

不把“报价提醒”既当任务类型又当来源，也不从标题文本猜测类型。

### 4.7 联系人与协同人

PRD 有联系人、协同人，但现有模型没有。

建议：

- `contact`：可选 FK，必须属于任务关联客户且未归档；联系人离职不删除历史关系。
- `BusinessTaskCollaborator`：任务与员工多对多关系，记录加入时间和加入人。
- 第一阶段列表可不显示协同人，但详情和权限计算要预留。

如果只为 TASK-01 最小闭环，可把协同人延后；联系人字段建议本次补齐，因为它直接影响客户跟进行动。

### 4.8 完成结果、提醒与改期

建议新增：

- `completion_result`：完成动作提交，允许空但自动任务可按规则要求必填。
- `cancel_reason`：取消必填。
- `remind_at`：可选，必须早于或等于截止时间。
- `reschedule_count`：系统维护。
- 改期时 `reschedule_reason` 必填，并写任务事件。

若要实现多个提醒时间，不要在任务表堆 JSON，应新增 `TaskReminder`；TASK-01 第一阶段可只支持一个 `remind_at`。

### 4.9 历史和批量幂等

建议新增：

- `BusinessTask.version`：正整数，每次业务变更递增。
- `TaskEvent`：记录创建、编辑、开始、等待、阻塞、恢复、改期、完成、取消、转派及批量操作 ID。
- `TaskBatchOperation`：保存 `event_id`、动作、请求摘要、执行结果和操作者，`event_id` 唯一。

单条仍使用 ETag；批量请求提交每条任务的 `id + version`。服务端先锁定并完整校验，再一次性提交。相同 `event_id` 重试返回第一次结果，不重复执行。

## 5. 指标卡口径

五张卡必须由服务端基于同一数据库时刻计算，不能让前端分别请求并自行拼接。

默认时区：`Asia/Shanghai`。以后增加用户时区时，再改为用户设置。

| 卡片 | 推荐口径 |
|---|---|
| 全部任务 | 当前范围内未归档且主状态为 PENDING / IN_PROGRESS 的任务数；建议把副文案改为“未完成” |
| 今日到期 | 未完成且 `due_at` 位于本地当天；副文案显示其中 PENDING 数量 |
| 已逾期 | 未完成且 `due_at < now` |
| 未来 7 天 | 未完成且 `due_at > 今天 23:59:59` 且 `due_at <= 今天结束 + 7 天`；不含今天和逾期 |
| 本月完成 | `completed_at` 位于本地自然月；按时率分母仅含有 `due_at` 的本月完成任务，分子为 `completed_at <= due_at` |

风险提示：

- “全部任务”在 Figma 中实际展示“未完成”，名称存在歧义；本次按未完成实现。
- “容量正常”没有阈值或人员工时数据，不能真实计算。第一阶段改为“未来 7 天待办”，或暂不展示容量结论。
- 无截止时间的已完成任务不进入按时率分母；接口应返回分母数量，避免 0/0 时伪造 100%。
- 指标随“我的/团队”范围切换，但不随表格搜索词和保存视图改变，避免用户误解指标口径不断漂移。

建议接口响应同时返回 `generated_at` 和 `timezone`，便于异常状态显示最后更新时间。

2. 从确认框移除该指标，并在 Figma/产品记录中说明。

不能固定显示与选中任务数相同的假数字。

## 8. 数据库变更建议

### 8.1 `BusinessTask` 向前兼容新增

建议 Migration 只新增字段，不删除现有数据：

- `task_type`，默认 `OTHER`，先回填再收紧。
- `origin_type`，默认：有 `automation_key` 为 `AUTOMATION`，否则 `MANUAL`。
- `origin_code`，允许空。
- `contact`，允许空。
- `work_state`，默认 `NORMAL`。
- `work_state_reason`，默认空字符串。
- `next_check_at`，允许空。
- `work_state_changed_at`，允许空。
- `remind_at`，允许空。
- `completion_result`，默认空字符串。
- `cancelled_at`，允许空。
- `cancel_reason`，默认空字符串。
- `reschedule_count`，默认 0。
- `version`，默认 1。

建议约束：

- COMPLETED 时 `completed_at` 非空；非 COMPLETED 时 `completed_at` 为空。
- CANCELLED 时 `cancelled_at` 非空且 `cancel_reason` 非空。
- WAITING_CUSTOMER 时 `work_state_reason` 和 `next_check_at` 非空。
- BLOCKED 时 `work_state_reason` 非空。
- `remind_at` 为空，或 `due_at` 为空，或 `remind_at <= due_at`。
- 联系人如存在，服务层和数据库触发器共同校验其客户与任务主要客户一致。

### 8.2 新表

- `business_task_collaborator`：任务、员工、加入时间、加入人；活动关系唯一。
- `task_event`：事件类型、前后值、说明、操作者、批量操作、发生时间。
- `task_batch_operation`：`event_id` 唯一、动作、状态、请求/结果摘要、操作者。
- 可选 `task_reminder`：如果本次保留 Figma 的“自动关闭提醒”统计。

### 8.3 来源一致性

当前五张关系表无法跨表保证“一个任务只有一个主要来源”。建议增加 PostgreSQL 延迟约束触发器，或改为统一 `BusinessTaskSource` 模型。

本次优先建议保留现有关系表并增加一致性触发器，迁移成本较小；不要在同一阶段重构所有业务模块的关系表。

### 8.4 索引

在现有开放任务索引基础上增加：

- `(assignee_employee, status, due_at, id)` 活动任务部分索引。
- `(task_type, status, due_at, id)` 活动任务部分索引。
- `(work_state, status, due_at, id)` 活动任务部分索引。
- `(completed_at, id)`，条件 `status=COMPLETED`。
- `(origin_type, origin_code, created_at, id)`。
- 团队查询所依赖的员工组织活动关系索引已存在，实施时用 `EXPLAIN ANALYZE` 验证。

## 9. 目标 API

### 9.1 列表和汇总

- `GET /api/v1/tasks/`
  - `scope=ME|CREATED_BY_ME|TEAM|ALL`
  - `q`
  - `assignee_employee_id`
  - `task_type`
  - `status`
  - `display_state=PENDING|IN_PROGRESS|COMPLETED|CANCELLED|OVERDUE|BLOCKED|WAITING_CUSTOMER`
  - `priority`
  - `due_window=TODAY|THIS_WEEK|NEXT_7_DAYS|NO_DUE_DATE`
  - `due_from` / `due_to`
  - `source_type`
  - `customer_id`
  - `archived=false|true|all`
  - `ordering`
  - `page` / `page_size`
- `GET /api/v1/tasks/summary/?scope=ME|TEAM|ALL`
- `GET /api/v1/tasks/{id}/`

列表项直接返回：

- 任务主字段、主状态、工作状态、派生期限状态、最终展示状态。
- 负责人和创建人摘要。
- 客户摘要：ID、编号、名称。
- 来源摘要：类型、ID、业务编号、标题、来源显示名、可跳转 URL。
- 联系人摘要。
- `version`、`updated_at`。

列表查询必须一次完成必要的 `select_related`、`prefetch_related` 和注解，禁止前端逐行补查客户。

### 9.2 单条动作

- `POST /api/v1/tasks/`
- `PATCH /api/v1/tasks/{id}/`，要求 `If-Match`
- `POST /api/v1/tasks/{id}/start/`
- `POST /api/v1/tasks/{id}/complete/`
- `POST /api/v1/tasks/{id}/cancel/`
- `POST /api/v1/tasks/{id}/reassign/`
- `POST /api/v1/tasks/{id}/wait-customer/`
- `POST /api/v1/tasks/{id}/block/`
- `POST /api/v1/tasks/{id}/resume/`
- 可选 `POST /api/v1/tasks/{id}/reschedule/`

所有动作要求 ETag、权限、活动员工、客户数据范围和任务当前状态校验。

### 9.3 批量动作

- `POST /api/v1/tasks/bulk-complete/preview/`
- `POST /api/v1/tasks/bulk-complete/`
- `POST /api/v1/tasks/bulk-reassign/preview/`
- `POST /api/v1/tasks/bulk-reassign/`

默认规则：

- 单次最多 100 个任务。
- 去重 ID 后顺序锁定。
- 预览返回任务数、客户数、逾期数、不可操作原因；若实现提醒表，再返回将关闭的提醒数。
- 提交包含唯一 `event_id` 和每条任务的 `version`。
- 任一任务不存在、越权、终态、版本冲突或负责人无效，整批 409/412 回滚。
- 相同 `event_id` 重试返回首次结果。
- 完成后保留截止时间、来源关系、事件和审计历史。

### 9.4 对象发现

现有全局搜索不支持样品，且返回的报价 ID 是报价而任务关联要求报价版本。

建议新增任务专用只读发现接口：

- `GET /api/v1/task-source-options/?q=&source_type=&customer_id=`

它必须只返回当前用户有权访问且可创建任务的对象，并直接给出任务 API 所需真实 ID。不要让前端用全局搜索结果猜报价版本。

## 10. 权限与数据范围

### 10.1 建议权限

保留 Django 默认权限，并增加：

- `view_team_businesstask`
- `view_all_businesstask`
- `bulk_change_businesstask`
- `reassign_businesstask`
- `manage_automated_businesstask`（仅自动化阶段使用）

不新建业务角色；通过现有角色/权限治理把权限分配给真实角色。

### 10.2 查看范围

- `ME`：负责人是当前员工。
- `CREATED_BY_ME`：创建人是当前员工。
- `TEAM`：需团队查看权限，范围为当前主组织及下级组织的活动员工。
- `ALL`：需全部任务权限或超级用户。
- 有客户来源的任务还必须服从客户数据范围；无权客户不能返回客户名、对象编号或任务敏感描述。
- 无来源的个人任务只按任务范围判断。

### 10.3 写权限

- 创建人不能把有关联客户的任务分配给无该客户访问权的员工。
- 转派目标必须是活动员工，并处于操作者允许分配的人员范围。
- 自动任务可编辑哪些字段应限制；不能通过普通编辑破坏 `automation_key` 和来源关系。
- 前端按钮隐藏不是安全边界，所有规则必须后端执行。

### 10.4 已有数据兼容风险

若把“有客户来源的任务必须服从客户范围”收紧，可能使部分历史任务对当前负责人不可见。迁移前要生成只读审计报告：

- 任务负责人无关联客户权限的数量。
- 多主要来源任务数量。
- 无来源、无截止时间、无创建人的任务数量。

发现异常先修复或建立明确授权，不能静默隐藏。
