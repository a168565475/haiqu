# 全局配置按需读取与 Redis 缓存

## 当前行为

1. 前端取消配置的 30 秒轮询、页面聚焦及恢复可见时的版本检查。现有版本接口保留兼容，但前端不再调用。
2. 页面进入或代码明确调用 `load/reload` 时请求配置。同一时刻的重复请求合并，不同字典继续合并为批量接口。已打开页面保留已显示的选项，重新进入或明确重新加载时更新；并非每次展开现有下拉框都会自动请求。
3. 后端先做原有登录、员工状态和权限检查，再读取共享 Redis 数据。数据库仍是正式来源，客户端通过后端 API 获取 JSON，不直接连接 Redis。
4. 配置保存事务提交后，使对应类别的旧缓存失效。下一次读取生成新缓存。无需保存时预先生成每一种分页、筛选结果，也无需重新打包前端。
5. 邮件继续按用户隔离。管理编辑详情及其修改凭据（ETag）、询盘处理时限设置、业务提交校验继续实时读库；业务引用数量也实时计算，防止配置没变但业务关联数已经变化。

## 覆盖范围

| 内容 | 读取方式 | 何时失效 |
|---|---|---|
| 已发布字典批量接口、无历史项的单项接口 | Redis 中共享已发布选项 | 新发布提交、字典类型保存/停用/归档 |
| 字典管理、系统参数、发布记录列表 | Redis 数据缓存 | 对应模型及关联模型提交修改 |
| 基础资料、生产资料、汇率、编号规则列表 | Redis 数据缓存 | 对应模型及关联模型提交修改 |
| 字典/产品类别业务引用数 | 每次实时计算 | 无缓存 |
| 编辑详情、历史选中项、统计汇总、询盘时限设置 | 数据库 | 无新增缓存 |
| 个人邮件配置 | 原有用户隔离接口 | 未改动 |

字典草稿保存不会直接改变业务页的已发布选项，仍需按现有规则发布。缓存不改变业务生效规则，也不改变权限分配。

## 故障与事务边界

- 缓存键包含后端内部的类别标识。提交后更换标识，迟到的旧读取只能写入旧键，不会覆盖新配置。前端无版本请求或比较。
- 数据库事务内绕过缓存，防止把未提交数据写入 Redis；事务回滚不发失效通知。
- Redis 连接和读写超时设置为 0.2 秒；缓存异常时回源数据库，并短暂跳过后续缓存尝试。
- 缓存有效期为 60 秒，这是服务端过期兜底，**不会让浏览器每 60 秒发送请求，也没有定时重建任务**。过期后有实际请求才重建。
- 数据库提交成功但 Redis 失效通知失败时，不把已经成功的保存误报为失败。本进程暂时回源；其他进程可能在旧缓存剩余有效期内读到旧数据。因此不承诺故障时的强一致。
- 正常配置 API 的保存/删除会触发失效。未来若新增批量更新或直接 SQL，必须显式调用失效函数；这类操作不会触发模型保存信号。

## 环境与性能

沿用现有 `REDIS_URL`、Redis 服务及已安装的 Python Redis 依赖。独立缓存别名为 `configuration`，键前缀为 `haiqu:configuration:v1`，未新增依赖或数据库迁移。

Redis 减少重复查询和序列化，但请求网络时间、身份检查、客户业务查询和页面渲染仍然存在。不能据此声称客户页面会明显变快。

验证证据见 `qa/config_on_demand_redis_20260915/report.md`。
