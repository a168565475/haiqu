# 主订单排产数据库设计 V1

日期：2026-09-15。状态：已确认实施稿；Q4—Q7 已确认，仍未对真实业务库执行建表、排产或数据写入。

## 1. 设计结论与依据

主订单排产采用 **3 张核心表**：主计划、产品明细、产品工艺关联。它们就是委外数据库设计中的 S01–S03，同一套表只建设一次；不在委外模块重新建一套排产数据。

“订单”按已经确认的口径指生产任务单。一个销售订单可能对应多个生产任务单，因此唯一限制落在生产任务单 ID，不落在销售订单号、合同号、产品 ID 或客户 ID。

一张任务单最多一张有效主计划，一次可以选择多个产品；不做分批排产。四个车间计划是查询视图，数量、日期、工艺都来自主计划产品明细，不独立维护或重复占量。主排产数量沿用任务单产品单位；委外加工的“套”是另一个业务口径。

依据：

- [排产 PRD 修订 1](../production_scheduling_prd_v0_1_20260914.md)：Q1–Q3 已确认，数量、日期层级及四计划映射。
- [原型确认基线](../../outputs/production_prototype_20260914_v1/revision_20260915_r2/confirmed_baseline.json)：2026-09-15 已确认的 P01–P08 原型。
- [历史决策清单](../../outputs/production_review_20260915/decision_checklist.md)：未被后续回答覆盖的业务细则继续待确认；其中旧的视觉“待确认”状态已被本次原型确认替代。
- [委外数据库设计](outsourcing_database_design_v1_20260915.md)：同名主计划表、委外来源、额度和库存边界。

本文是 S01–S03 的完整定义；委外文档对应章节为关联摘要。技术字段与索引属于建议，不把数据库设计请求视为执行迁移或开放尚未确认业务动作的授权。

| 现有对象 | 已核对事实 | 设计处理 |

| 任务产品维护 | 当前已有 BOM 引用和销售来源限制，但尚未发现排产引用保护 | 后续补排产关联门禁，不能只在新表加外键后让旧页面报错 |
| 现有开工服务 | 开工核对已确认 BOM、订金或先生产说明等 | 保持原规则；保存排产不调用开工服务 |

本轮核对的是当前源码，没有连接实际数据库核查已执行迁移，也没有验证真实任务单、工艺 ID 或业务数据完整性。

## 3. 数据关系与统一约定

| 表 | 一行的含义 | 上级关系 |
| --- | --- | --- |
| S01 `production_schedule` | 一张主排产计划 | 一个 ProductionTask 可有历史计划，但最多一张 ACTIVE |
| S02 `production_schedule_product` | 本计划安排的一条任务产品 | 一个 S01 包含至少一条有效 S02 |
| S03 `production_schedule_product_craft` | 某计划产品选中的一道工艺 | 一个 S02 可关联多个厂内、厂外 Craft |

工艺资料、员工、产品、单位、图片文件和审计均复用现有表。建议新建 Django 应用 `production_scheduling`，不引入新框架。

共同字段：`id uuid PK`、`created_at timestamptz`、`updated_at timestamptz`，继承项目 TimeStampedModel。除明确可空字段外均非空；可选文字默认空字符串，JSON 默认空对象。外键使用 PROTECT，保留来源和历史。

S01 单头保存创建/更新员工，子表操作跟随单头审计，不重复为每一关联行设置独立审批人。所有业务校验以服务端为准，不接受前端传入的任意历史快照或未经校验的来源 ID。

S02/S03 预留 `removed_at timestamptz NULL`、`removed_by_employee_id FK Employee NULL`，两字段同时为空或同时非空。仅在 Q5 确认可编辑后用于移除明细：父行移除时同事务移除其有效子行。已移除行保留历史，不参与当前查询和数量汇总；有未取消委外引用的产品或相应工艺不能移除。

本设计中的“有效明细”是本行及父行均未移除；“有效计划”是 S01.record_status=ACTIVE。任务单变成暂停/完成等状态，不自动把计划改为 VOID。产品和工艺的历史移除不等于建立新的排产批次。

## 4. S01 主计划表

建议表名：`production_schedule`。

| 字段 | 类型 / 默认 | 可空 | 用途和限制 |
| --- | --- | --- | --- |
| id | uuid，服务端生成 | 否 | 主键 |
| schedule_number | varchar(50) | 否 | 唯一排产单号，服务端生成 |
| production_task_id | FK ProductionTask | 否 | 唯一来源任务单；建单后不可换成另一任务 |
| record_status | varchar(20)，ACTIVE | 否 | ACTIVE / VOID；VOID 动作开放取决于 Q5 |
| version | integer，1 | 否 | >0，任何产品/工艺修改同步递增 |
| source_snapshot | jsonb，{} | 否 | 保存时的任务/销售/客户/人员/交期参考信息 |
| source_revision_hash | varchar(64) | 否 | 服务端生成的关键来源摘要，用于检测填单期间变更 |
| client_request_id | uuid | 否 | 建单请求唯一标识，网络重试沿用 |
| request_payload_hash | varchar(64) | 否 | 原创建请求的规范化内容摘要，不随日后编辑覆盖 |
| created_by_employee_id | FK Employee | 否 | 创建人 |
| updated_by_employee_id | FK Employee | 否 | 最后更新人，首次同创建人 |
| created_at / updated_at | timestamptz | 否 | 创建/最后修改时间 |
| void_reason | text，空字符串 | 否 | 作废后必须非空 |
| voided_at | timestamptz | 是 | 作废时间 |
| voided_by_employee_id | FK Employee | 是 | 作废人 |

数据库约束建议：

- UNIQUE `schedule_number`、`client_request_id`。
- 条件 UNIQUE `(production_task_id) WHERE record_status='ACTIVE'`。限制整个任务，不是 `(任务, 产品)`，因此两人选择不同产品也不能分别生成两张有效计划。
- CHECK `record_status IN ('ACTIVE','VOID')`、`version>0`。
- ACTIVE 时作废人/时间为空且原因为空；VOID 时三项完整。VOID 不允许恢复成 ACTIVE；若允许作废重建，新建新 ID，并保留旧计划，避免复活历史造成两张有效计划。
- 提交事务时有效计划至少有一条有效产品明细。该规则需要跨表约束，不是假装一个普通 CHECK 可以检查子表数量。
- 不物理删除任何已保存计划，也不通过归档字段绕过有效计划唯一限制。

不存储独立的“已排总数量”“已完成数量”“总进度”字段。数量按产品单位查询汇总，实际生产完成不在本期。

### 4.1 单头快照结构

`source_snapshot` 固定约定以下键，所有值由后端填充：

| 键 | JSON 类型 | 来源 |
| --- | --- | --- |
| task_number / contract_number / order_number | string | 任务单对应字段；三个号分开保存 |
| sales_order_id / sales_order_number | string 或 null | 真实 sales_order 关系；历史无关联时为 null |
| customer_account_id / customer_name | string | 任务单客户；客户名称仅作展示历史 |
| salesperson | object | 员工 ID、编码、姓名 |
| followers | array of object | 多名跟单员，按稳定 ID 排序 |
| order_date / delivery_date | YYYY-MM-DD | 任务单日期 |
| planned_start_date / planned_end_date | YYYY-MM-DD 或 null | PMC 原计划日期，仅参考 |

source_snapshot 只存展示来源，不存金融报价、应付信息或新的可编辑客户。订单列表搜索任务单号可连接任务表；历史快照搜索按明确键实现，不能把整个 JSON 文本当精准订单关联。

## 5. S02 产品排产明细表

建议表名：`production_schedule_product`。

| 字段 | 类型 / 默认 | 可空 | 用途和限制 |
| --- | --- | --- | --- |
| id | uuid | 否 | 稳定明细 ID，供委外 O02 引用 |
| schedule_id | FK S01 | 否 | 主计划 |
| product_line_id | FK ProductionTaskProduct | 否 | 来源任务单的具体产品行，不是通用产品 ID |
| line_number | integer >0 | 否 | 当前计划内展示顺序 |
| planned_quantity | bigint >0 | 否 | 排产数量，单位沿用任务产品 |
| source_quantity_snapshot | bigint >0 | 否 | 本次保存时来源数量，历史参考 |
| unit_id | FK ProductionUnit | 否 | 来源单位真实引用，由后端带入，不可在排产换单位 |
| unit_name_snapshot | varchar(50) | 否 | 当时单位名称，例如件/把/套 |
| image_file_id | FK BusinessFile | 是 | 任务产品主图；无图不影响保存 |
| material_inbound_date | date | 是 | 计划材料入库日期 |
| metal_return_date | date | 是 | 计划金工回货日期 |
| sewing_return_date | date | 是 | 计划车缝回货日期，裁剪/车缝计划共用 |
| finished_inbound_date | date | 是 | 计划成品入库日期 |
| product_snapshot | jsonb，{} | 否 | 产品编号、货号、名称、规格、颜色、特殊/包装要求 |
| source_revision_hash | varchar(64) | 否 | 产品来源关键数据摘要 |
| removed_at / removed_by_employee_id | timestamptz / FK Employee | 是 | Q5 可编辑时的历史保留字段 |
| created_at / updated_at | timestamptz | 否 | 行创建/修改时间 |

`product_snapshot` 固定键：`product_id`、`product_number`、`product_code`、`item_number`、`product_name`、`specification`、`product_color_id`、`color_card`、`color_name`、`color_code`、`special_requirements`、`packaging_method`。没有图片时 image_file_id=null；不把前端占位图写进数据库。产品基础资料后续改名不静默覆盖计划快照。

约束建议：

- 对未移除行条件 UNIQUE `(schedule_id, product_line_id)` 和 `(schedule_id, line_number)`。
- CHECK `planned_quantity>0`、`source_quantity_snapshot>0`、`planned_quantity<=source_quantity_snapshot`、`line_number>0`。正整数不能输入小数、负数、0 或空值。
- 跨表检查 `product_line.production_task_id = schedule.production_task_id`；unit_id 必须等于来源产品单位。
- 保存时另检查 `planned_quantity<=当前 product_line.quantity`，不能用旧快照逃避实时上限；快照只能由服务端生成。
- 被引用后不得把本行原位改成另一个产品或另一个任务。编辑数量/日期沿用原 ID；移除再添加时使用新 ID，旧引用仍指原行。
- 调整行号用事务中的安全重排，避免更新到一半撞唯一约束；不得为重新排序删除全部产品行再重建。

Q4 已确认四日期全部必填，因此正式模型四个日期均为非空 date。不把四日期变成 timestamp，不强制材料→金工→车缝→成品严格串行。金工与车缝可能并行；不另外增加“裁剪完成日期”。

不同单位不能直接相加。例如 600 把椅子和 200 张桌子，应显示 2 个产品，按单位分别汇总，不能写成“排产总数 800 套”。一条产品同时进入四个车间列表，仍只排产一次。

## 6. S03 产品工艺关联表

建议表名：`production_schedule_product_craft`。

| 字段 | 类型 / 默认 | 可空 | 用途和限制 |
| --- | --- | --- | --- |
| id | uuid | 否 | 主键 |
| schedule_product_id | FK S02 | 否 | 计划产品 |
| craft_id | FK Craft | 否 | 真实工艺记录 |
| craft_type_snapshot | varchar(20) | 否 | INTERNAL / EXTERNAL，选择时由后端带入 |
| craft_name_snapshot | varchar(100) | 否 | 历史工艺名称 |
| plan_category | varchar(20) | 是 | METAL / CUTTING / SEWING / ASSEMBLY；其他工艺为 null |
| removed_at / removed_by_employee_id | timestamptz / FK Employee | 是 | Q5 允许时保留移除历史 |
| created_at / updated_at | timestamptz | 否 | 创建/修改时间 |

约束：

- 对未移除行条件 UNIQUE `(schedule_product_id, craft_id)`。
- CHECK 类型只能 INTERNAL / EXTERNAL；plan_category 只能上述四值或 null；EXTERNAL 必须为 null。
- 新增选择时 Craft 必须 ACTIVE，类型必须与当前资料一致。新选工艺停用或改类型时拒绝提交；已有历史工艺停用仍展示原选择和停用提示。
- 有效工艺关联不能挂在已移除产品行上。某产品工艺最少选择数依 Q6，不能未确认就硬编码“两类各一项”。
- 不保存工艺名称逗号串作为关系，不用标签颜色判断工艺类型，不从 Operation 工序推算所属计划。

### 6.1 四计划稳定映射

建议在已有 `workshop_config_craft` 增加可空 `plan_category varchar(20)`，作为厂内工艺的稳定映射。仅 INTERNAL 可填写，非空值唯一；本期只核对并绑定以下四个真实工艺 ID：

| 核对的厂内工艺 | 映射值 | 车间列表日期 |
| --- | --- | --- |
| 管材加工 | METAL | S02.metal_return_date |
| 裁剪 | CUTTING | S02.sewing_return_date |
| 车缝 | SEWING | S02.sewing_return_date |
| 装配/包装 | ASSEMBLY | S02.finished_inbound_date |

选择工艺时将 Craft.plan_category 复制到 S03.plan_category。日常查询使用 S03 的已保存映射，工艺改名不造成历史明细突然换列表。已经被排产引用的工艺类型和分类禁止普通维护直接变更；修正映射须单独评估历史影响，不批量重写已有计划。

其他有效厂内工艺可选择并保存在主计划，但不自动落入这四类。没有独立裁剪车间不影响裁剪列表。`装配/包装` 按当前明确的一道工艺核对，不擅自拆成两道。

委外设计中的 Craft.outsourcing_code 仍单独用于厂外工艺；两字段不能混用。INTERNAL 的 outsourcing_code 应为空，EXTERNAL 的 plan_category 应为空。实际 ID 尚未查询，迁移不得从模糊名称自动挑一条或偷偷创建缺失工艺。

## 7. 数量、日期及来源版本

### 7.1 不分批不等于必须排满

订单产品 1000 把，本计划填 600 把满足上限，但不能新建第二张计划补 400 把。是否在原计划增加到 1000 把由 Q5 决定；不能将“余量”做成另建计划入口。

同一任务单只安排部分产品也只能生成一张有效计划。服务不能因为另一个产品尚未选入，就让第二张计划通过。销售订单下不同任务单按各自产品数量独立校验，不按销售订单整单总量共享排产额度。

### 7.2 日期规则与待决口径

当前只确定到日期级字段。建议按所选工艺适用性填写，缺少本列表必须显示的日期时不开放相应保存；若用户选择四日期必填，统一在服务和数据库提交约束中检查非空。

选择“按适用性”后还需精确对应外协场景：厂外喷塑是否要求金工回货日期、厂外裁剪/丝印是否要求车缝回货日期，以及材料/成品日期的通用必填性，不从名称擅自扩展硬性规则。四个厂内列表的日期对应已经确认；厂外日期应用属于待细化建议。

异常顺序、超过订单交期、历史日期建议风险提示，不在数据库写四日期必须严格递增的 CHECK，不自动改日期或建立审批。原型确认不代表已经确认这些异常策略。

### 7.3 关键摘要与变更提示

source_revision_hash 建议用 SHA-256 对规范化数据计算；不把它当权限签名。单头摘要覆盖任务 ID、状态/归档、来源销售关系、交期、PMC 日期、产品 ID 集合；产品摘要覆盖身份、数量、单位、规格颜色和生产要求。稳定排序，日期使用 ISO 字符串，不把抓取时间或临时 URL 放进去。

创建表单取得摘要，提交时服务锁定来源、重新计算并比对；不一致返回具体变更，不自动换新来源。现有任务单 updated_at 不能独自代表每条子产品变化，摘要必须包含实际子行内容。

主计划版本 version 解决“计划自身被别人编辑”；来源摘要解决“任务单资料变了”，两个问题分开处理。实时任务状态单独返回，不能用历史快照冒充当前状态。

价格、无关备注等非排产关键资料不应无差别造成表单失效。已保存计划的来源冲突通过比较当前来源与快照派生，不新增一个无人可靠维护的 source_changed 状态字段。

## 8. 四计划及委外来源查询

### 8.1 查询粒度

P01 一行一张主计划，展开产品；P04 展示单头、产品和相关四计划。P05–P08 一行一条有效 S02，按指定工艺映射筛选。

筛选条件：S01 ACTIVE、S02 未移除，存在未移除的 S03，且 craft_type_snapshot=INTERNAL、plan_category 等于本列表类型。使用 EXISTS 判断工艺归属，避免连接多个工艺后让同一产品重复出现；分页和统计也不能计算 JOIN 膨胀后的条数。

来源任务已归档/取消时，建议从默认待办查看中排除，历史查询仍可见；暂停和完成以来源状态明确展示，不推定工序已经完成。该默认过滤为查询建议，不改变计划及外发记录，也不允许来源完成后再创建第二张有效计划。

四表共同列：排产号、任务单号、销售订单号（有正式关联时）、产品基础信息、planned_quantity、单位及对应日期。按日期升序、计划号、行号和 ID 稳定排序，空日期统一放末尾；不通过系统当前日期推定实际生产逾期。

### 8.2 委外真实关联

委外 O01.schedule_id → S01.id；委外 O02.schedule_product_id → S02.id。选中厂外 Craft 后，只有存在有效 S03 EXTERNAL + craft_id 的产品可选。计划其他产品未选该工艺时不得一起带入。

主计划不必提前绑定 BOM 版本：排产当前主要安排产品和工艺；委外在 O02 保存所用真实 BOM、版本和快照。这样不会因排产表没有 BOM ID 而缺少追溯，也不把“排产必须确认 BOM”变成默认门槛。

**主排产和委外额度分别校验。**例如源产品 1000 把，主计划 800 把；按先前确认口径，委外某部件最多仍为 1000 套，不改成 800 套。修改主计划或作废重建不能重置委外的“任务产品＋稳定部件＋工艺”累计额度。

## 9. 编辑、作废与上游变更保护建议

本节为 Q5 获得确认后采用的建议，不表示已授权开放所有维护动作。

| 关联情况 | 建议允许 | 建议拦截/保护 |
| --- | --- | --- |
| 无委外引用 | 同一计划调整数量、日期、工艺，增减来源产品；整单作废 | 保持来源任务不变，逐行校验数量；只保留一张有效计划 |
| 有未取消但未发料的委外 | 非破坏性日期等修改可保留版本提示 | 删除被引用产品/工艺、整单作废：先处理关联未发料外发单；不级联取消 |
| 已发料/部分回货/已回齐 | 历史查看；可否更改未来日期由维护政策确定并留痕 | 不移除被引用产品/工艺，不换任务/产品，不以作废回退出入库或释放加工额度 |
| 只有已取消委外历史 | 在规则允许时维护计划，历史 FK 仍保留 | 不删除旧 ID，不将取消单改指新计划 |

单纯修改主计划数量不得自动改委外数量，不能错误建立“计划数量不得小于委外套数”的新规则。原则上仍按来源订单上限；具体已执行后的计划改量权限待维护规则确认。

上游任务或销售来源的产品删除/替换、单位变更，必须补查有效计划与历史引用；已有计划引用时给出明确冲突，不让外键错误成为用户看到的报错。来源数量减少到低于有效 planned_quantity 时拒绝该冲突更新或先走明确调整流程；不自动截断计划。减少数量还必须同时通过委外累计额度检查。

订单取消、归档、暂停不级联作废计划、不删除产品，不回退库存；需要办理的已发外发回货继续按其历史交接依据核对，不能拿“新建排产只允许 READY”阻断历史回货。

所有允许的编辑按 ID 差异更新；不删除整个计划重建以实现普通保存。审计保留修改前后单头、产品、工艺、操作者、原因和版本；复用 AuditLog，不另建第二套操作日志表。

## 10. 事务、重复提交和数据库约束

### 10.1 建单事务

1. 校验登录、员工状态、创建权限及 accessible_production_tasks 数据范围；校验请求 UUID 和规范化内容摘要。
2. `transaction.atomic` 内锁定请求对应来源 ProductionTask，再按 ID 排序锁产品行；读取当前来源状态，但先处理下一步的成功请求重试，再判定能否新建。
3. **先查本请求是否已有成功结果。**相同 client_request_id 和原创建摘要返回原计划；内容不同返回冲突。不能先因已经有计划或任务状态变化就把正常重试判为新建失败。返回前仍须检查当前用户读取权限。
4. 对不同的新请求重新检查任务当前 READY、未归档、产品集合以及是否已有 ACTIVE 计划，再核对数量、产品归属、工艺启用及来源摘要；按稳定顺序锁相关 Craft，避免刚校验即被停用/改类型。仅接口选择器过滤不足以保护保存。
5. 一次写入 S01/S02/S03 和 AuditLog，任何一行失败全部回滚；唯一约束冲突回滚到安全事务边界后，查询既有单据并返回可读冲突。

一单唯一由任务行锁和数据库部分唯一共同保证。只对“尚不存在的计划” select_for_update 无法锁住空结果，必须锁已有任务；不同产品分别排产也共用这个任务锁。

单号使用项目既有编号分配方式或数据库序列，唯一约束兜底；不用 MAX+1。编号格式待接入编号规则核对，不创建未经确认的正式编号或样例数据。

### 10.2 编辑/作废事务

Q5 确认开放后，统一按“任务 → 产品 → 主计划 → 明细/工艺 → 被关联的委外单”等约定顺序加锁，并与委外服务保持一致；不在另一入口先锁外发单后反向锁计划。未涉及的对象不额外上锁。

锁定主计划后执行现有 If-Match 检查；任何子产品或工艺改变都必须递增 S01.version、更新 S01.updated_at，并在响应返回新的 ETag。不能只更新子行导致主计划 ETag 不变。

作废先检查 Q5、权限、版本和委外引用，记录原因/人员/时间后原子改为 VOID。日后若重建，通过原任务锁与有效唯一约束生成新计划；重新使用旧建单 request UUID 仍指旧计划，不生成新单。重建使用新的请求 UUID。

### 10.3 约束分层

| 层级 | 必须覆盖 |
| --- | --- |
| 字段及行内 CHECK | 正整数、类型/分类枚举、非空、数量不超过服务端保存的来源快照、移除/作废字段完整 |
| UNIQUE / FK | 单任务一张 ACTIVE、单号和请求唯一、计划内产品/行号不重复、产品工艺不重复、真实来源不能删除断链 |
| 服务事务 | 权限、当前 READY、当前数量上限、来源摘要、Q4/Q6、关联委外门禁和原子保存 |
| 数据库跨表兜底 | 产品必须属于计划任务；单位一致；保存来源快照不可伪造上限；新增工艺类型/分类与所引用资料一致；有效子行不得挂在已移除父行；ACTIVE 至少一条有效产品；来源减量检查 |
| 不可变保护 | 禁止改计划任务 ID、禁止把已引用产品行换身份；已引用工艺类型/映射不能普通修改；历史作废/移除与审计不可物理抹掉 |

跨表/跨行规则需新增针对性约束触发器或等价数据库保护，不能只写 Django clean() 并声称批量写入也有保障。总量/归属检查在事务正确位置运行；触发器与服务统一锁顺序，直接写表的竞争也不能绕过任务/产品锁。

任务创建条件是动作条件，不是永久要求所有 ACTIVE 计划的任务状态都为 READY；任务正常开工后计划仍存在。工艺启用校验同样针对新选择，不因为历史工艺停用就否认旧记录。

## 11. 索引及查询成本

| 位置 | 建议索引 | 目的 |
| --- | --- | --- |
| S01 | UNIQUE schedule_number、client_request_id | 单号定位、幂等 |
| S01 | 条件 UNIQUE production_task_id WHERE ACTIVE | 有效唯一与查重 |
| S01 | `(created_at DESC, id)` | 主计划默认分页 |
| S01 | `(record_status, created_at DESC, id)` | 有效/历史查询 |
| S02 | 条件 UNIQUE `(schedule_id, product_line_id)`、`(schedule_id, line_number)` | 防重复及按单取明细 |
| S02 | product_line_id 的 FK 索引 | 来源变化检查、委外产品追溯 |
| S02 | `(metal_return_date, id)`，有效行条件 | 金工日期筛选 |
| S02 | `(sewing_return_date, id)`，有效行条件 | 裁剪/车缝日期共用 |
| S02 | `(finished_inbound_date, id)`，有效行条件 | 装配日期筛选 |
| S03 | 条件 UNIQUE `(schedule_product_id, craft_id)` | 产品工艺去重 |
| S03 | `(plan_category, schedule_product_id)`，有效厂内条件 | 四计划 EXISTS 查询 |
| S03 | `(craft_id, schedule_product_id)`，有效厂外条件 | 委外候选来源 |

各 FK 使用 Django 默认索引，避免再重复建相同索引。日期索引是初步建议，正式数据量与执行计划核对后可精简；不预先给每个 JSON 键和日期组合建一套索引。

客户/产品关键词可通过明确快照键筛选；量大再评估表达式/trigram 索引。列表按完整服务端结果分页，工艺、图片、人员资料批量预取，不按每一行再查一次数据库。先分页主计划再取其产品，避免展开产品影响单据总数。
