## 1. 目标与边界

为现有 ERP 建立可维护的员工账号、角色权限和销售团队数据范围。复用现有 Django Session、CSRF、员工与角色模型、业务服务和审计，不另建认证体系。

本任务只属于 project001_haiqu_ERP_CRM，与 project008_finance_system 无接口、身份、数据库或业务关联。截图仅作为角色名称来源，不作为完整页面设计稿或权限规则来源。

范围为现有 ERP 已实现的业务功能及其权限接入；不因新增财务、出纳等角色而新增尚未实现的业务模块。现有 README、AGENTS.md 的早期 CRM 范围描述与当前源码已存在的采购、库存、生产模块有差异，本次按用户明确提及的 ERP 销售、生产权限范围开展，不扩建这些模块的业务流程。

本次明确不做：

- 企业微信实际接入、通讯录同步、消息发送或移动端重设计；仅设计后续身份绑定边界。
- 客户及关联业务转移功能的开发、修复、批量转移、历史负责人回填。
- 业务员换团队流程或历史团队归属追溯。
- 字段级价格、成本、利润等可见性控制；保留未来扩展边界，不提前实现。
- 新增业务审批层级、金额阈值或新的审批流程。
- 为目前不存在的导入、导出、打印功能补建业务能力。

### 2.1 角色名单

共 20 个业务角色：总经理、厂长、采购、金工主任、装配主任、车缝主任、仓管、跟单、品质、财务、外协、PMC、行政、技术、喷塑收发料、金工打样、布面打样、出纳、业务员、客户经理。

“查看全部权限”不是角色。admin 是超级管理员身份，不依赖这 20 个业务角色的勾选结果。

新建普通角色默认空权限，包含客户经理角色；分配客户经理查看权限时，销售数据范围默认选所管团队，不能同时自动授予团队写权限。总经理、厂长等也不根据名称自动获得全公司权限。角色名称可展示为中文，授权引用稳定标识，不依赖名称字符串。

### 3.1 转移功能的已知交界

目前询盘、报价可见性跟随客户，若未来仅改变客户负责人，可能连带改变已完成单据的可见性。因此“历史业务不转移”未来需要销售转移功能同时处理记录归属与权限查询契约，不能认为不改历史数据就自然实现历史隔离。

本次不更改转移行为或补写历史归属。阶段 1 会列出实际字段、查询依据和例外；阶段 4 仅落实本次确认的权限范围。若发现达成范围隔离必须修改转移逻辑，单独提出具体冲突，按用户要求一次只问一个问题，不自行扩大范围。

## 4. 已确认的总体权限设计（细化产物分阶段审核）

### 4.1 判断一次操作是否允许

操作必须同时满足：有效账号和员工、对应操作权限、该操作的数据范围、原有业务状态规则。

- 页面只显示实际存在的模块与操作，不提供无后端能力的“空权限”。
- 每个模块列出适用操作：查看、新增、编辑、删除、提交、审批、撤回、作废等；不强制每模块拥有同一套流程。
- 导出与打印映射到查看，导入映射到新增；覆盖更新还需编辑。批量操作逐条验证数据范围。
- 菜单可见性根据模块权限派生，不能用隐藏菜单代替后端校验。
- 未配置的普通角色不授予业务访问，复制权限不复制成员、登录密码或超级管理员身份。
- admin 不受普通角色权限和销售数据范围限制；仍遵守自审禁止、库存约束、状态门禁等业务规则。用户未提出 admin 的自审例外，本方案不增加例外。

### 4.2 权限与数据范围一起合并

授权粒度建议为“角色 + 业务资源 + 操作 + 数据范围”。同一员工多角色时，只合并同一操作所允许的数据，不能把一个角色的范围与另一个角色的操作随意组合。

例：角色甲允许编辑本人订单，角色乙允许查看团队订单。合并后只能编辑本人订单、查看团队订单；不能编辑团队订单。

销售范围第一版表达本人、所管团队、全部，未授权时为空范围。“全部”仅可由管理员显式配置，不由角色名称推断。生产按模块授权，不默认增加个人、仓库、车间隔离。

团队关系由 ERP 独立维护。计划使用独立团队与成员记录，数据库保证一位业务员仅一个团队；不借用企业微信部门关系。角色决定能做什么，团队决定销售范围，只有团队成员关系不能获得业务操作权限。

### 4.3 管理页面

建议放在系统配置下，提供：

1. 角色与权限：角色列表、创建、复制、权限勾选、销售操作范围、停用或归档。
2. 员工与账号：关联现有员工、创建登录账号、密码重置、启停、分配多个角色、查看有效权限与授权来源。
3. 销售团队：指定客户经理、添加成员、显示唯一团队归属；本次不提供换团队业务流程。
4. 授权变更记录：谁在何时修改了哪个角色、员工或团队，变更前后内容可核对；敏感登录凭据不得入审计正文。

权限矩阵以“模块为行、操作为列”，支持搜索与模块折叠；操作数据范围与对应操作一起显示。保存前显示实际变化及受影响人员，防止误授团队写权限。

阶段 1 提交页面布局供审核，遵守 DESIGN.md 第 10 章及 1920×1080 桌面基准。用户截图只用于角色名称，不能据此声称像素级复刻。

### 4.4 账号与后续企业微信

本次沿用 Django Session + CSRF，员工有各自账号。管理端维护员工与登录账号的一对一关系，不共享 admin 登录身份，不在前端保存公共登录口令。

后续接入企业微信时，以明确的外部身份映射绑定当前员工主键；不根据姓名自动合并，不复制员工档案，不重建业务归属。企业微信负责身份认证，ERP 仍负责角色、团队及数据授权。具体接口、应用配置与身份字段在未来接入阶段核对官方文档，本轮不确定供应商接口细节、不调用企业微信。

委派权限管理与普通业务权限分开，初期仅 admin。拟禁止被委派管理员设置超级管理员标记或获得超过自身委派边界的管理能力，具体页面与接口限制在阶段 1 展示。

## 6. 必测用例

- admin 可访问全部已实现模块；有效员工与操作者审计要求完整。
- 无角色员工、空角色员工不能访问业务；新角色不意外继承默认全权。
- 多角色正常合并；团队查看不放大本人编辑权限。
- 员工只能访问自己数据，经理只能访问自己的团队；替换记录 ID、关联 ID、批量 IDs 不能越权。
- 团队经理只读时，前端不提供写操作，直接调用写接口仍被拒绝。
- 查看、导出、打印范围一致；导入覆盖不能绕过编辑或越权新增负责人。
- 列表、详情、汇总数量、搜索、下拉选项、审批任务、附件链接和关联嵌套数据不泄露范围外数据。
- 创建人、销售员、跟单员、显式共享授权等旧入口有明确迁移决定和回归用例。
- 禁止申请人自审；兼任多个角色、改提交参数或直接调 API 也不能绕过。
- 角色移除、失效、停用和账号停用后，后端后续请求按新权限检查；旧页面不因缓存继续操作。
- 删除、撤回、审批等权限不绕过原有单据状态、库存事务或并发保护。
- 不修改客户转移、历史业务负责人或团队调动流程。

## 7. 数据变更与验证边界

优先使用独立测试数据库，测试不与其他任务使用相同测试库并发运行。真实开发库写入前，提供角色/账号/员工绑定清单、影响、备份与可恢复方式，按已确认授权范围执行。

计划新增前向迁移，不修改历史迁移。已有角色、直授和分组不静默清除；20 个目标角色仅补缺，遇到同名、冲突或历史权限时先展示差异。现有 admin 状态及员工档案需只读核验，不能从用户名推断超级管理员资格。

权限收紧可能使原流程缺少可用审批人；启用前列出受影响流程及可用审批者，由管理员分配权限，不临时允许自审来绕过。

每阶段按影响执行后端测试、迁移漂移检查、API 权限/CSRF/ETag 验证、前端类型检查与构建；涉及页面再做真实浏览器验收。具体运行结果在阶段报告记录，本方案不宣称上述检查已经通过。

初次方案编制仅产出此文档；后续已获授权的阶段 1 产出见顶部入口。阶段 1 未创建真实角色、账号、团队，未更改配置、业务代码或数据库，未提交、推送或部署。
