## 2. 已确认业务口径

| 事项 | 开发要求 |
| --- | --- |
| 来源 | 先选厂外工艺，再选已生成计划中含该工艺的产品；不是直接选择生产订单 |
| 单据 | 一张外发单＝一张排产计划＋一道厂外工艺，可含多个产品、多个加工厂 |
| 工艺来源 | 裁剪/车缝/丝印加工对象取 BOM 裁剪明细，材料取面料/辅料；喷塑材料取管材/五金，加工对象暂按管材待核实原始用词 |
| 数量 | 加工为正整数套；上限按来源任务产品订单数量，跨单/跨厂/跨版本稳定部件累计 |
| 分配 | 各厂分配套数合计＝加工明细总套数；不同部件不能加成成品产量 |
| 计价 | 全部工艺元/套，包括喷塑；计划金额不是应付金额，月结只是付款周期 |
| 保存 | 占用加工额度；不扣材料库存，不预占材料库存 |
| 发料 | 仓库整单一次全部发料；按真实材料来源与原单位扣库存，加工对象不重复扣料 |
| 回货 | 一批一个加工厂，多批按分配明细登记；实收＝合格＋不良 |
| 入库 | 确认本批才入账；合格入半成品可用库存，不良独立存放，不加成品库存 |
| 库存身份 | 任务产品＋稳定 BOM 部件＋已完成工艺，品质/库区分开；批次/工厂/来源保留 |
| 完成 | 所有分厂、所有明细收齐且无待处理异常；回货和完成均不释放已加工额度 |
| 修改 | 未发料可编辑取消并审计；已发/已收数量、真实接收工厂和库存流水不直接覆盖删除 |
| 图片 | 加工项、分厂加工要求、材料项、回货明细分别关联文件，不能只挂单头 |

加工数量仍沿用已确认的订单上限，不擅自缩小到排产数量。材料数量不能用成品套数作直接上限，米/千克/条等不能混加。参考需求的计算基数存在一处图文差异，见第 12 节；未答复前不把其中一种标为新确认规则。

### 3.2 通用视觉标准

- 正式基准 1920×1080、100% 浏览器缩放、DPR=1。展开侧栏 230px、顶栏 64px，布局按对应节点，不整体缩放。
- 按钮、单行输入、选择器、日期、分页控件及工具栏内外高度 32px；多行内容区域按原型，不机械压成 32px。
- 无例外的列表表头 44px、数据行 40px，单元格左右内边距 16px；W01 明确使用 48px 数据行。列宽、排序、图片、表格间距各按页面，不套客户表格列配置。
- 页面 #f6f3ec、内容 #fcfbf7、次级表面 #f0eadf；主/常规/次要/弱文字分别 #1f1d18 / #4d4c48 / #6f6a61 / #968f84。通用边框 #ddd6c9，细分隔线依节点可用 #eae4da。
- 标题 Noto Serif SC，内容 Noto Sans SC；必须检查字体加载，不能用系统回退字体冒充一致。
- 工艺 Tag 使用 Strong、24px、反白 #FAF9F5、12px/18px、500 字重、999px 圆角；车缝 Brand #C96442、裁剪 Info #3898EC、喷塑 Success #4F7D4B、丝印 Warning #B8781E。外协工艺不用灰色。待外发/已取消等状态 Tag 可按原型使用 Neutral，不能把工艺禁灰误扩展到所有状态。

- 所有样式使用 SCSS/Sass；优先复用合规组件、变量和 mixin。当前旧 `_tokens.scss` 的 36/38px 控件、52px 行和旧反白值不能直接沿用；模块内适配，不全局重构无关页面。

## 6. 后端与接口方案

保持 Python 3.13、Django 5.2、DRF、PostgreSQL 17，Session + CSRF。建议新应用 `apps.outsourcing`；半成品库存归 `inventory`，稳定部件对应归 `boms`。

拟新增/修改：

- `apps/outsourcing/models.py`、`migrations/`：工厂、外发、分配、材料、发料、回货、异常、图片关联。
- `services/` 下按工厂、外发单、发料、回货分文件；`selectors.py` 与 `api/serializers.py` / `views.py` / `urls.py`；`tests/`。
- `apps/inventory`：半成品模型/查询、材料净余额/候选批次、库区停用门禁。
- `apps/boms`：稳定部件绑定、来源适配、引用后的编辑/删除保护。
- 工艺分类编码、应用注册、API 路由和动作权限；保留现有未提交修改，只改必要连接处。

### 6.1 拟定 API

以下为开发后新增的接口建议，当前尚不存在；统一 `/api/v1/`，分页/错误结构沿用项目规则。

| 接口 | 用途 |
| --- | --- |
| GET/POST `/outsourcing-factories/` | 加工厂筛选分页/新增 |
| GET/PATCH `/outsourcing-factories/{id}/` | 工厂详情/更新，If-Match；关联外发及回齐统计来自全量查询 |
| POST `/outsourcing-factories/{id}/disable/` | 停用，新选择禁用，历史单不丢失 |
| GET `/outsourcing-options/` | 真实可用厂外工艺、工厂能力、允许参数；刺绣不可新选 |
| GET `/outsourcing-source-plans/` | craft_id 筛选可选计划及匹配产品，返回源 ID/摘要/不可选原因 |
| GET `/outsourcing-source-products/{schedule_product_id}/bom/` | 所选工艺的加工部件与材料分类、BOM 版本/绑定、图片和用量原文/解析结果 |
| GET/POST `/outsourcing-orders/` | 外发列表/创建；创建含计划、工艺、产品 BOM、加工项及分厂、材料与行级图片 |
| GET/PATCH `/outsourcing-orders/{id}/` | 外发详情/未发料编辑；包含按厂及部件进度、金额、实际发料与回单 |
| POST `/outsourcing-orders/{id}/cancel/` | 未发料取消、释放本单加工额度、审计，不退库 |
| GET `/outsourcing-orders/{id}/dispatch-context/` | 完整加工/材料明细、实际可用批次、单位及净余额，供 W02 |
| POST `/outsourcing-orders/{id}/dispatch/` | 整单唯一一次发料；请求 UUID＋版本＋全部材料实际来源数量 |
| GET `/outsourcing-returns/` | 回货批次分页；单号/工厂/日期等筛选 |
| GET `/outsourcing-orders/{id}/return-context/` | 指定 factory_id，返回该厂分配明细已回/待回、可用接收人及库区 |
| POST `/outsourcing-returns/` | W04 一次提交确认本批，合格/不良/库区/图片与库存同事务落地 |
| GET `/outsourcing-returns/{id}/` | 本批详情及实际接收人/确认人、库存来源 |
| GET `/semi-finished-inventory/` | 按任务产品/稳定部件/工艺/库区的可用库存查询 |
| GET `/semi-finished-inventory/detail/` | 传完整库存身份，返回合格/不良、来源集合及流水；不把聚合行假装成单一 lot ID |

选择加工/材料只读接口不扣额度或库存。价格/材料小数通过十进制字符串交换，后端 Decimal 校验；数量须为合法整数，不接受前端金额计算作真实账据。图片沿用现有上传 API，表单中临时行键在保存事务内映射为真实行 ID；批次失败不产生入库，只可能留下由现有文件机制处理的未关联上传。

### 6.2 权限与历史保护

建议分别配置工厂维护、外发创建/编辑取消、仓库发料、回货确认、库存查看等动作权限；实际角色授权按现有员工/组织体系核对，不默认所有计划人员都能扣库存，也不新增无需求审批流。

单据、候选、BOM、图片和库存查询均按可访问任务单范围过滤。工厂主数据权限与任务数据范围分开；知道订单/行/文件 ID 不代表有读取或修改权限。

接收人是本批业务资料，confirmed_by_employee 是当前实际操作者，二者分开保存，不能通过下拉选择他人覆盖审计身份。可选接收人员范围需要对接现有人员规则。

工厂停用阻止新分配，不阻断已发单合法回货；同理上游改名/新建 BOM 版本不改变历史交接。取消单、已执行数量及图片更正均保留来源和审计，不级联删记录。

### 6.3 回齐明细与金额

O01“加工明细/回齐明细”建议统一按有效加工项计数：分母为加工项数；一个加工项的全部分厂分配都收齐，该项才计入分子。O07 分厂进度以该厂分配行为粒度。接口需同时给出这两种口径，不能随页面随意改分母。

数量回齐与异常处理分开：某项有不良也可能实收回齐，但订单仍有未处理异常而不能完成。条形图只表达明细回齐，不冒充合格率或成品产量；该具体计数定义作为接口建议核对，不能从原型示例数字猜实际条数。

计划金额是有效分配的套数×元/套之和；移除旧行不计费，分批回货不重复加金额。保留数据库稿建议精度，页面按原型展示，不自动生成应付款、不叠加元/平方米。

## 7. 库存与并发验收重点

### 7.1 创建/编辑

同一事务锁来源任务/产品、计划与相关对象后，检查工艺匹配、BOM 归属/版本、稳定部件、多厂分配和累计加工额度；多明细全成或全败。源产品是跨计划、跨单的共同锁点，不只锁当前外发单。

client_request_id 相同且原内容相同返回原结果，换内容拒绝；编辑使用 If-Match 并重新核对来源摘要。回货不释放额度，未发料取消才释放本单占用；不能为了重做同工艺把计划或 BOM 换个 ID。

### 7.2 发料

同一外发单唯一发料记录；按真实入库批次汇总各厂各材料行本次领用，再锁后计算净库存。所有材料齐发才提交，缺料/单位不能换算全部回滚。

`批次可用量 = accepted_quantity - 已记账委外出库量`。不改原采购验收量，不重复扣已从 accepted_quantity 中扣掉的品质退货。查询先逐批次算出库再汇总，防 JOIN 放大原入库量。

若其他模块也消耗相同材料批次，必须统一余额和锁顺序；不能只对委外加锁就宣称全系统不会超领。采购到货统计仍反映采购事实，领用不变成重新待采购。

### 7.3 回货与库存

锁外发单及本厂分配，校验本批实收不超过该分配剩余，不能借其他工厂额度。实收＝合格＋不良，正数品质必须有匹配库区；当前库区是否启用锁后重查。

回货单、明细、库存批次/流水、异常记录、订单状态和审计同事务提交。重复请求只入账一次；不良也计入已经实收，不能借“不良不入可用库存”再超收一批。

半成品可用库存只含 GOOD；DEFECTIVE 保存物理结存但不放进可用量。不同部件、颜色、任务和完成工艺不混合。按多来源汇总时保留每个批次和来源版本，详情不能误选另一工艺的不良数量。

没有后续领用功能也要保留批次身份。真正退料、返工复收、报废或撤销待独立动作定义，不能用删除回货记录或随意调余额代办。

### 7.4 必须实测的并发

- 两张外发单同时占同部件额度，合计超量时仅合法提交成功。
- 两单/多厂同时取同一材料批次，不得负库存或留下半张发料单。
- 同单两个回货批次同时抢同厂同明细待回量，不超收且状态聚合正确。
- 用户连点/网络超时重试，不重复建单/扣库/入库。
- 库区停用、来源减量/BOM 改行、工厂工艺维护与业务提交竞争时，锁和校验一致。

测试使用独立连接与实际事务，并验证直接写表的关键约束；顺序调用两遍不算并发验证。服务与数据库触发器必须统一锁顺序，并加入死锁错误和安全重试边界测试。
