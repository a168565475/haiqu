本方案承接 [逐项确认记录](permissions_role_configuration_20260928.md) 和既有 [ERP 权限方案](erp_permissions_plan_20260928.md)，用于将已经确认的业务规则落实为可配置角色。19 个角色已形成初始规则，行政保留但暂不配置；“查看全部权限”不作为角色。

## 初始角色汇总

下表是便于审阅的摘要；具体允许、禁止及状态边界以逐项确认记录为准。只读不包含编辑、删除或审批；一个流程正常产生的库存变化不等于取得独立仓库写权限。

| 角色 | 初始授权重点 | 数据边界 |
| --- | --- | --- |
| 业务员 | 客户、询盘、报价、销售订单已确认操作；订单确认及确认后变更；样品申请、费用登记及减免申请、寄送、反馈、确认完成；本人任务；产品只读 | 客户当前主负责人为本人；无审批及独立生产、采购、仓库权限 |
| 客户经理 | 业务员同等操作，加报价与样品费用减免审批 | 本人及所管团队；禁止自审，仍受指定审批人规则约束 |
| 总经理 | 除权限管理以外全部现有业务操作 | 全部业务数据；个人保存视图仍限本人 |
| 厂长 | 生产相关模块、采购、仓库、外协、产品及原料全权；样品厂长审核 | 不开放独立销售模块及权限管理；样品商业费用等不因生产全权自动扩大 |
| 采购 | 采购与供应商全权；库存及出入库、产品原料、生产订单和 BOM 只读 | 模块范围 |
| 仓管 | 仓库库存全权；领料审核、样品仓库核对；采购订单、生产订单、BOM、产品原料只读 | 模块范围；审批禁止自审 |
| PMC | 生产订单、BOM、排产全权；样品 PMC 确认；采购订单、库存、外协、产品原料及全部车间报工只读 | 模块范围；无工价管理权 |
| 金工主任 | 领料与金工流转全权；工价查看、新增、编辑、提交；报工查看、新增、编辑、删除；样品金工参数维护 | 工价和报工仅金工车间；无工价审批；不开放已拒绝的生产、BOM、排产、库存及产品原料独立查看 |
| 装配主任 | 工价查看、新增、编辑、提交；报工查看、新增、编辑、删除 | 仅装配车间；无工价审批 |
| 车缝主任 | 同上述工价与报工操作；样品裁剪参数维护 | 工价报工仅车缝车间；无工价审批 |
| 跟单 | 全部销售订单及生产订单、排产、采购订单、库存、外协只读；本人跟进任务 | 从销售订单开始，无客户、询盘、报价及车间报工访问 |
| 外协 | 外协全权；生产订单、BOM、库存、产品原料只读 | 整个外协模块 |
| 技术 | 产品原料及 BOM 全权；生产订单、排产、库存、外协、全部客户样品只读 | 模块范围 |
| 品质 | 采购入库待质检查看及品质确认；采购订单、库存、产品原料、生产订单、BOM、排产和样品只读 | 模块范围及全部客户样品 |
| 财务 | 样品及费用查看、费用登记、财务确认、减免审批；销售订单、采购订单及供应商只读 | 全部客户；不开放库存、车间工价报工及外协 |
| 出纳 | 已确认范围与财务一致，保留为独立可调整角色 | 全部客户；同样不开放库存、车间工价报工及外协 |
| 金工打样 | 样品查看、金工参数维护及金工进度登记；产品原料只读 | 全部客户样品；不能改裁剪进度，不含车间报工权限 |
| 布面打样 | 样品查看、裁剪参数维护及裁剪进度登记；产品原料只读 | 全部客户样品；不能改金工进度，不含车间报工权限 |
| 喷塑收发料 | 喷塑收发、交接、退回及外发单新增、受限删除、作废、受限撤销、对账、完成；生产订单、BOM、产品原料、库存及出入库只读 | 外协写操作仅喷塑；独立资料读取按用户确认的全部范围 |
| 行政 | 保留角色，暂不配置 | 用户明确跳过 |

admin 继续保持超级管理员与权限管理能力，不列入上述普通角色模板。全部角色继续遵守业务状态、数量、库存、事务、并发和现有禁止自审规则；“没有授予”不作为覆盖其他角色的显式拒绝。

## 已核对的实现缺口

| 项目 | 当前代码事实 | 实施要求 |
| --- | --- | --- |
| 车间范围 | `RoleActionGrant` 只有 OWN、TEAM、ALL、MODULE；`allowed_workshop_ids` 遇到新模块授权会返回全部车间 | 授权项增加可配置车间选择，读取和写入都按当前操作过滤，避免只读全范围扩大其他操作范围 |
| 样品工序 | `report_production` 用统一权限写入金工与裁剪数量、完成状态；表单也有报工写入口 | 金工、裁剪报工分别授权，覆盖所有写入口；不能仅禁用前端输入框 |
| 喷塑范围 | 外协目录只有 MODULE，不能表达仅喷塑工艺 | 在授权项关联允许的工艺，校验单据及关联工艺；覆盖旧外发、统一外发及金工交接相关入口 |
| 报工删除 | `WorkReport.delete()` 拒绝物理删除；明细外键 PROTECT；新增按主记录 `client_request_id` 去重 | 新增受控物理删除服务、独立审计、原因必填、并发控制和删除后防重放机制 |
| 共享权限码 | 样品费用登记与财务确认复用旧权限码；部分其他动作也复用旧 change 权限 | 按已存在独立动作码优先映射，必要时拆分新动作；验证旧码兼容不会把未授权动作带入新角色 |
| 历史授权 | `has_permission` 仍检查 legacy_sources；角色授权也投影到 Django group permissions | 保留用户要求保留的旧授权，预检并展示实际来源；不能声称角色未勾选就必然禁止该员工操作 |

上述是本次读取源代码得到的事实；方案要求不代表功能已经实现。权限补充会涉及数据库前向迁移，具体迁移编号以实施时仓库最新状态为准，不预占或改写既有迁移。

## 实现方式

### 1. 生成可复核的授权清单

从真实权限目录及 API 动作映射生成“角色、资源、操作、范围、业务依据”的清单。将配置项分为已支持、需扩展、现有系统无此操作三类；无接口的操作不得创建空权限冒充交付。

“全部权限”只在用户已确认的模块和范围内展开；其余未授权项为空。模板只是初始配置数据，不参与运行时按角色名放行。重复应用模板须先输出增删差异，不能覆盖 admin 后续手工配置。

必须核对选项、下载、导出、汇总及关联记录读取。已授权动作需要的关联摘要按最小必要内容返回；不能为使页面可用而给跟单、金工主任等角色补发被拒绝的全模块权限。独立导出、下载等若未包含在明确全权内且未获授权，不擅自新增初始授权；已有隐含权限展开须在清单中明示并核对。

### 2. 增加授权项的可选资源范围

建议保留当前四类范围，增加仅适用于指定模块的车间/工艺范围；为授权项关联真实车间、工艺记录，避免在角色名或用户编号上写判断。受限范围为空即无可访问资源，不把空列表解释为全部。

按每项操作合并员工各角色范围。例如“查看全部车间报工”与“修改金工车间报工”同时存在时，修改仍只能金工。范围变更和角色复制均需携带并审计资源选择；数据库、API、前端类型、有效权限展示同步更新。

统一覆盖列表、详情、汇总、选项、附件以及新增/更新引用对象；不能凭另一个车间或工艺的 ID 越权。旧员工车间范围及历史宽授权保留语义，冲突在启用预检列明，不擅自删除旧授权或承诺它已被新角色收窄。

### 3. 拆分样品工序操作

金工报工、裁剪报工分别作为可配置动作，和各自参数维护分开。直接报工、完整表单编辑、明细修改等入口使用相同的后端操作判定。无权字段的值不得被更改；前端保留只读展示并只提交允许的变更，兼容处理必须避免默认值覆盖另一工序。

具备两项工序权限者可修改两项；只读者不能报工。厂长、总经理等已确认的生产全权按清单取得相应动作，而不是在服务内判断岗位名。材料齐备、生产阶段、报工数量上限及完成判定保持既有规则。

### 4. 实现报工物理删除

删除权限独立配置，范围跟随对应车间。服务先锁定记录及相关汇总依据，验证版本与删除原因；在同一事务中保存不可随原单删除的审计快照，再删除明细和主记录。失败必须整体回滚。

日志至少记录原 ID/单号、车间、工价版本、全部报工明细、数量和金额、操作员工、时间、原因。保留新增请求标识和载荷摘要的独立历史记录；旧请求重放必须识别已经删除，不能重建报工。

核对日汇总、工序累计、金额统计，以及工价方案因曾被报工使用而具有的历史限制，避免删除报工后意外开放工价历史修改。前端增加删除入口、原因输入、确认提示和处理中状态；删除日志不复活为有效报工。

### 5. 调整现有权限管理页面

沿用已经确认的管理原型及 ERP 现行设计规范，不重做整个页面。仅在相应授权项增加车间/工艺选择、工序动作、删除权限和变更前后差异；员工有效权限能解释每个来源及范围。

实施前重新读取 ERP 的现行设计规范及确认原型，核对控件高度、表格密度、边框、弹窗和滚动参数；不得采用独立财务系统规范。本轮未修改 UI，也未重新进行视觉验收。

## 实施顺序与验证

1. 固化授权清单及现有入口映射，校验 20 个角色都有明确处理结果（19 个配置、行政跳过）。
2. 扩展可配置范围、独立动作、管理 API 和页面，再接入车间、样品工序及喷塑查询/写入边界。
3. 实现报工删除、独立历史与防重放；增加新权限并纳入已确认的全权及三个主任配置。
4. 在隔离数据库和测试账号验证后端、管理页和业务页。按实际改动运行相关后端测试、前端类型检查/测试/构建、迁移漂移检查，以及真实 1920×1080 浏览器验收。
5. 输出正式配置预览：角色授权前后差异、员工与团队候选、旧授权影响、正式审批人缺口及开关切换影响。准备好可审阅结果后再安排真实迁移、授权和业务启用。

必须覆盖的负向验证：跨客户/团队、跨车间、跨工艺 ID 越权；只读用户直接调用写接口；金工与裁剪交叉修改；多角色读范围误用于写范围；共享旧码带入额外动作；空范围错误放大；自审、过期 ETag、空白删除原因、重复删除、删除后重放创建、事务失败审计与业务不一致。

启用前需要实际员工角色、销售团队和审批人配置。这些人员资料尚未指定，不能猜测或把历史测试账号直接作为正式审批人。优先用隔离账号完成开发验证，不以人员配置缺失阻塞已确认技术工作的准备。

## 正式启用边界

用户保留旧直授和旧分组的决定继续有效。先审阅员工有效权限差异；若旧宽授权使“仅某车间/工艺”不能成立，列出具体员工和权限来源，由用户决定对应旧授权处理，不能自动撤销，也不能报告隔离已生效。

角色授权会投影为 Django 权限；业务范围开关关闭时，这些投影可能增加旧模式操作能力。因此不提前向正式账号分配模板来试效果，也不把只配置角色当作范围限制已经启用。

正式启用前重新只读核对主库、运行配置、待迁移及备份情况，准备明确变更清单。业务范围启用沿用既有计划，销售和其他业务限制需一起校验；回退不能简单关闭开关并声称仍然保持新范围隔离。真实业务删除、撤销不作为验收手段。
