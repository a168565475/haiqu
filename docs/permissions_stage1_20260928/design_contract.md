## 1. 页面设计依据

使用 ERP 当前 DESIGN.md 第 10 章：1920×1080、230px 侧栏、64px 顶栏、单层 14px 页面边距、暖色背景 #f6f3ec、内容面 #fcfbf7、品牌色 #c84e28、深色侧栏 #1c1c1a。标题采用 Noto Serif SC 34/44px，正文采用 Noto Sans SC；模块与操作左对齐，表格与角色列表分别在面板内滚动，操作栏始终可见。

按钮和单行控件统一 32px；表头 44px、数据行 40px、复选框 14px、Strong 标签 24px。表格明确列宽，页面级新建操作放标题右侧，搜索按 Enter 生效。导航使用项目现有 IconPark 图标；业务弹窗直接复用 AppWindowDialog.vue，支持拖动、缩放、最小化、最大化及还原。样式源文件为 SCSS，使用 ERP 颜色和字体 token；旧 token 的 36/38/52px 尺寸与新规范冲突时，仅在预览采用规范尺寸，不修改全站 token。

具体对照及验收证据见 [设计规范优化记录](design_polish_review.md)。

设计取舍：权限页需要同时比较岗位和动作，采用左侧角色列表、右侧操作矩阵。颜色只用于选中、状态和主要操作，不增加无关统计卡。沿用现有 ERP 色彩体系；这是对既有系统的延续，不另立视觉风格。

可点击布局见 [management_preview.html](management_preview.html)。全部人员、团队、权限勾选均为明确标识的演示数据；不连接 ERP API、不保存到真实数据库、刷新即恢复。该 HTML 是审核原型，不替换现有 Vue 页面。未引用新的 Figma 节点，不声称像素级复刻。

## 2. 页面行为约定

| 页面 | 布局与行为 | 不得产生的误解 |
| --- | --- | --- |
| 角色与权限 | 左侧 20 个初始角色，可搜索、新建、复制；右侧按模块/操作配置，销售数据范围跟随具体操作 | 角色名称本身不授予权限；预览中客户经理的勾选仅演示，不代表角色已初始化 |
| 专项操作 | 单独展示当前模块存在的流程操作；按资源支持本人、团队或全部范围 | 不把所有流程动作都合并成“编辑”；列表里的删除、归档、作废明确区分 |
| 保存变更 | 显示操作、原值、新值、影响员工和并发冲突；修改后可撤销 | 正式页面不得仅前端勾选成功而未保存后端；预览只提示演示 |
| 员工与账号 | 关联现有员工档案，创建独立账号，重置密码、启停、分配多角色；展示有效授权来源 | 不重新建立同名员工，不把“已登录”当作有业务权限 |
| 销售团队 | 管理员指定经理和未分组成员；可跨部门；已分组员工不可重复加入 | 团队不是企业微信部门；当前不提供换团队或历史调动流程 |
| 授权记录 | 谁在何时修改了哪项权限，显示前后差异及对象 | 不记录密码、Session 或外部认证密钥，不提供任意修改历史审计的入口 |

正式角色页还应提供停用/归档和相应影响预览；员工页提供启停确认及成功/失败反馈。本次可点击原型重点验证矩阵、复制、团队成员筛选、合并解释和状态布局，未把每个 CRUD 操作做成完整交互流程。

加载中、空数据、加载失败、无权限四种状态均有布局。无权限状态不展示角色、员工或团队详情。前端路径直达也须验证页面权限。

## 3. 模型草案

### 3.1 复用

- User：现有登录主体，admin 保持超级管理员身份。
- Employee：现有业务员工主键和 User 一对一关联；所有业务审计继续引用它。
- RoleProfile + auth.Group：角色身份、稳定代码、展示名与归档状态。
- EmployeeRoleAssignment：员工多角色及分配有效期。
- AuditLog：复用审计基础，新增权限管理对象类型/动作，不建立第二套无关联日志。

### 3.2 拟新增

| 模型 | 关键字段 | 约束 |
| --- | --- | --- |
| RoleActionGrant | role、permission、scope、版本/更新时间 | role + permission + scope 唯一；仅允许权限目录声明的范围；同一动作可有多个范围并集 |
| SalesTeam | 稳定编号、名称、manager_employee、状态、版本 | 经理必须是有效员工；管理员选择；不从组织部门推断 |
| SalesTeamMembership | employee、team、创建者与时间 | employee 唯一，禁止一个业务员重复加入团队；本次不实现调动 API |

权限目录由服务端维护模块、动作、中文名称、对应权限码、适用数据范围与必要依赖。角色具体勾选及范围存数据库，随时可改。管理员配置的是授权，不是在后台任意创建没有业务实现的操作。

RoleActionGrant 为新业务范围的事实来源；auth.Group.permissions 作为兼容现有 has_perm() 的投影，在同一事务维护。只检查 has_perm() 仍不足以决定操作某条记录，必须同时使用本动作的范围过滤器。

阶段 2 需要给现有共用权限码的不同操作新增稳定权限码，例如把采购编辑与采购新增分开；使用前向迁移。不得为 Django 自动生成但没有实际入口的权限搭建虚假功能。

旧 User.user_permissions 和原生 Group 权限展示为旧授权来源，不能一面保留其生效，一面宣称新角色已经完全控制账号。用户已确认 8 个 QA/E2E 账号仍在使用并由其后续自行删除，本次保留账号与现有授权；不以这些旧账号验证“新建空角色无权限”，也不为旧用户名创建绕过后端检查的白名单。拆分权限码若影响旧账号能力，应在对应阶段列出影响后确认。

### 3.3 操作与范围算法

1. 验证登录、账号与员工状态。
2. admin 使用全部已实现操作与数据范围；仍执行审批人限制、自审禁止、状态、库存、ETag 等业务规则。
3. 普通员工读取当前有效且未归档角色，取目标操作对应的 grant。
4. 只合并此操作的范围。没有本操作 grant 则拒绝。
5. 列表、详情、统计、搜索、附件和关联对象使用同一个动作范围；写入时再次验证对象与所有关联 ID。
6. 接着执行现有业务服务、事务、状态机和并发校验。

范围拟为 OWN（本人）、TEAM（所管团队）、ALL（明确授予全部）、MODULE（非销售业务按模块）。TEAM 的数据来自管理员设定的团队成员；经理自己的业务可与 OWN 并集，不通过角色名字自动扩权。无团队关系时 TEAM 不产生他人数据。

典型结果：业务员角色 = 编辑 OWN，客户经理角色 = 查看 TEAM；组合后编辑仍为 OWN，查看为相应查看授权范围的并集。

已确认的关系型查看范围：客户协作人同时具备客户查看权限时，可读其被指定协作的客户；跟单同时具备订单查看权限时，可读分配给自己的订单及必要客户摘要。关系只增加已确认的对应读取范围，不自动扩展关联模块、编辑、删除或审批范围。有效权限页面应解释这些关系来源，不能把读范围复用于写范围。

新增操作同样要约束客户/负责人。不得通过提交其他团队的 customer_id、owner_employee_id 绕过本人范围；默认负责人沿用已确认的业务归属，不在权限阶段引入转移能力。

### 3.4 授权管理能力

建议拆为查看权限配置、维护角色、分配员工角色、管理账号、管理销售团队、查看授权日志等能力，初期只由 admin 持有。

后续委派管理权不等于授予超级管理员身份。普通管理 API 不接受 is_superuser/is_staff 或任意 Django 权限码；受委派人员只能在明确可管理的角色/权限集合中授予，不能通过修改自身角色获得新的管理能力。委派范围随首次实际使用进一步核验，初期不自动分配给任何业务角色。

## 4. API 草案

以下均为拟新增路径，尚未实现；正式命名在阶段 2 保持统一。

| 方法 / 路径 | 用途 | 权限与约束 |
| --- | --- | --- |
| GET /api/v1/access/catalog/ | 模块、操作、范围及依赖目录 | 仅权限管理者；只返回已实现或本轮明确接入的操作 |
| GET/POST /api/v1/access/roles/ | 列表、新建空角色 | 分别验证查看、维护权限 |
| GET/PATCH /api/v1/access/roles/{id}/ | 角色基础信息、状态 | ETag/If-Match；不能修改超级管理员身份 |
| GET/PUT /api/v1/access/roles/{id}/grants/ | 整体读取、保存操作与范围 | 版本检查、单事务、去重、权限码白名单、影响审计 |
| POST /api/v1/access/roles/{id}/copy/ | 复制为新角色 | 不复制成员、账号或管理员身份 |
| GET /api/v1/access/employees/ | 账号与员工状态 | 管理能力；按需返回，不泄露口令 |
| POST /api/v1/access/employees/{id}/account/ | 为现有员工创建账号 | 一对一约束；不自动授予角色 |
| PATCH /api/v1/access/employees/{id}/account/ | 启停等账号维护 | 单独管理能力；保护 admin 应急入口 |
| POST /api/v1/access/employees/{id}/reset-password/ | 重置口令 | 服务端安全处理与审计；正文不留存口令 |
| GET/PUT /api/v1/access/employees/{id}/roles/ | 读取、替换角色分配 | ETag/事务；不能分配越出委派边界的角色 |
| GET /api/v1/access/employees/{id}/effective-access/ | 查看最终权限及各来源 | 后端计算；区分直授、角色和超级管理员 |
| GET/POST /api/v1/access/sales-teams/ | 团队列表、新建 | 管理团队能力 |
| GET/PATCH /api/v1/access/sales-teams/{id}/ | 团队详情、基础资料 | 不借基础资料更新实现成员换组 |
| POST /api/v1/access/sales-teams/{id}/members/ | 添加未分组员工 | 数据库唯一约束，冲突返回明确错误 |
| GET /api/v1/access/audit-events/ | 查询授权变更记录 | 单独审计查看能力 |

现有 /api/auth/me/ 保留原契约并扩展有效权限摘要/授权版本，过渡兼容旧客户端；更改角色后服务端后续请求立即读取新权限。前端权限缓存只是展示优化，不能决定后端授权。

## 5. 错误与依赖处理

- 未登录返回认证错误；无操作权限拒绝；对象越界按现有接口风格返回不可访问/不存在，避免泄露存在性。
- 无数据范围不显示空白成功态来掩盖权限不足，页面说明无权限。
- 角色配置 ETag 过期时要求刷新差异，禁止静默覆盖其他管理员修改。
- 角色停用与权限撤销的影响预览包含受影响员工、可能失去的入口与审批能力。
- 产品、原料、单位等下拉可按已授权业务动作提供完成该业务所需的最小引用数据，不自动授予其管理模块写权限。
- 生产可以读取生产单据中已有的必要客户/订单摘要，不因此开放完整 CRM 客户档案。
- 个人邮箱、标准代码等既有有效员工公共入口须在清单中明确，不能把“空角色无业务权限”误写成所有个人配置都被禁止。
