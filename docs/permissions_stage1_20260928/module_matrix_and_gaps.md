## 4. 差异与推荐处理

### D01：旧账号与直授不能隐形保留

事实：除 admin 外，haiqu 也为超级管理员；5 个账号有直接权限。新角色的“空权限”不会取消旧直授或超级管理员资格。

用户后续确认：haiqu 是现在不用的测试/旧账号；其余 8 个账号全部在使用，用户后期自行删除。8 个账号为 cus01_e2e、wb_qa_sales、wb_qa_forbidden、sam_qa_e2e、sam_qa_alt、sam_qa_forbidden、inq01_qa、quo_qa_e2e。本任务保留这些账号及现有授权，不擅自停用、删除或清理。haiqu 也没有获得停用/降权授权。

实施边界：旧授权来源须可解释，不能将旧账号当作“新建空角色无权限”的验收账号；使用独立测试数据验证新规则。保留旧授权记录不等于给旧用户名增加绕过全部新权限检查的白名单。若拆分操作权限会改变旧账号既有能力，在对应阶段提供具体影响并确认，不静默增权或降权。

### D02：销售订单与采购申请缺少操作级门禁

证据：sales_orders/api/views.py 的 SalesOrderViewSet 继承 GenericViewSet，运行时权限为 IsAuthenticated、HasActiveEmployee；本轮扫描该 ViewSet 和 sales_orders/services.py 未见 has_perm 操作检查。采购申请 PurchaseRequestViewSet 只有 HasActiveEmployee，并依赖生产来源范围。不能声称无任何保护，但与“查看、编辑分别配置”的目标不符。

建议：补每动作的权限码、映射与服务端对象范围，再调整前端按钮。保留现有状态机、事务与 ETag。

### D03：共用权限码会让勾选失真

证据：采购订单 update/partial_update 当前使用 add_purchaseorder；采购合同模板 create/update/partial_update 当前使用 view_purchaseorder。样品取消使用查看权限并在方法内限制申请人；多个询盘流程动作沿用 change_inquiry。报价 export_quotation 与用户确认的“导出随查看”也不一致。

建议：已有写操作按真实含义拆分；导出/打印跟随查看，导入新增跟随新增，覆盖更新同时要求编辑。签发、发送、发布会改变业务状态或产生外部副作用，仍是独立动作，不因导出随查看就自动允许发送。

### D04：旧团队与新团队定义不同

证据：workflow/selectors.py 的 team_employee_ids 取经理当前主组织及下级组织；询盘指派候选也使用组织。用户已明确销售团队手工维护且可跨部门。

建议：新销售团队用于销售数据和相关团队工作台/任务范围，不把企业组织关系直接转换。组织继续用于原有组织资料；与转移/改派流程相交的部分只登记，不在权限任务中重写业务流程。

### D05：跟单/客户协作人访问口径已确认

事实：客户可见性当前接受任意有效客户分配，包含 PRIMARY_OWNER、MANAGER、COLLABORATOR；订单可见性包含客户可见、salesperson、merchandiser、created_by 任一条件。80 张订单全部有跟单员，78 张创建人不同于销售员。

影响：直接把“本人”解释为创建人会扩大范围；直接移除全部跟单关系可能让跟单岗位无法工作。旧客户 MANAGER 也不能自动等于新团队经理。

用户后续确认：跟单只在有对应操作权限时查看明确分配给自己的订单及必要客户信息，编辑等操作另行授权；客户协作人可以查看分配给自己协作的客户，但必须具有客户查看权限。

销售员继续按业务归属，客户经理按手工团队。协作身份本身不自动授予编辑、删除或全部关联订单/报价的访问；各关联模块仍校验其操作权限和已确认范围。跟单的客户摘要也不等于整个客户档案及其全部业务可见。旧客户 MANAGER 记录不能被直接导入为新团队名单；创建人不自动成为业务负责人。上述为后续实施规则，本阶段未改任何真实访问权限。

### D06：生产链依赖销售范围

事实：生产订单默认通过客户可见、销售员、关注人或创建人过滤，view_all_productiontask 可放宽；排产继承生产订单范围，委外再继承排产，领料也关联生产订单。

建议：按用户确认的生产模块职责授予模块范围，逐层修正依赖，避免仓管、车间主任因没有销售客户而看不到授权工作。生产摘要读取不能顺带开放完整客户/报价/销售页面。

### D07：自审校验分散，提交者信息需准确

事实：报价送审已有申请人不能为审批人检查；通用决定审批校验指定审批人；工价批准、厂长打样审核的所检查方法未见统一的提交人与审批人比较。局部未见校验不等于已通过可利用性测试。

建议：各审批入口在服务层共同阻止本轮提交者自审，不能仅禁前端按钮。用实际提交人而非创建人或当前负责人；数据若缺少提交人字段，则新增记录机制，旧记录无法可靠追溯时不凭猜测回填。保留指定审批人规则。收货、开工、发货等业务确认不因名称相似就自动套用“审批”规则。

客户转移审批属于用户明确排除的转移功能，本次只记录差异，后续销售转移改造时处理，不借自审统一擅自修改它。

### D08：权限页面不能只枚举 Django 权限表

事实：数据库共有 1,018 个权限记录；包含模型默认生成项。部分对应的删除、独立维护或业务页面并未实现。

建议：操作目录只展示实际 API/业务动作，基础资料的动态权限也纳入；关闭未实现动作而不是画可点击假功能。系统功能扩展时新增操作目录项，角色默认不自动获得它。

### D09：空角色与必要个人/参考能力分开

事实：标准代码读取、固定车间只读、个人邮箱与部分全局选项使用有效员工权限；保存视图有自己的模型权限。

建议：角色未授权业务模块时，不开放该模块单据；必要参考数据由合法业务上下文读取。个人邮箱现有自助策略与个人配置单列，不直接按“空角色”全部禁用，也不向团队经理开放别人的邮箱。

### D10：历史转移目标与当前查询契约相交

当前询盘/报价跟随客户可见范围，客户一旦变更归属，已完成单据的可见性也可能跟随改变。用户已明确未来只转未完成业务，但这项功能以后在销售修改。

本次不改客户转移服务、已完成判断、历史归属或业务数据；记录未来须分清单据负责人、客户当前负责人、历史归属。不会把“历史转移已经隔离”写成阶段 1 或本轮权限验收结果。

### D11：菜单与聚合读取

当前销售订单侧栏未声明权限，路由守卫主要校验登录；聚合 API、下拉、附件需按来源资源授权，不能只改角色页。

建议：后端新增权限先于公开按钮；所有直接 URL、批量 IDs、关联 customer_id、统计数量、搜索和下载都按相应操作范围验证，禁止读范围被用于写范围。

### D12：开发登录方式

后端开发自动登录实时启用；前端存在固定身份自动登录代码。员工权限上线前必须关闭这两条路径，继续保留 admin 正常账号密码登录。当前未改配置，不能将开启状态的开发环境当作完成多人身份隔离。

## 5. 跨模块依赖核对表

| 操作 | 所需引用 | 授权边界 |
| --- | --- | --- |
| 新增询盘/报价/订单 | 客户、联系人、地址、币种、产品 | 目标客户必须在新增操作范围内；产品选项不自动获得产品维护权 |
| 查看生产单据 | 来源订单、产品、必要客户摘要 | 仅完成生产所需信息；不从摘要跳转读取完整未授权销售单据 |
| 新增 BOM/采购申请/领料 | 生产订单、原料/单位、库存 | 来源生产任务应在其业务范围内；新增不等于有采购完成或发料权 |
| 收货与质检 | 采购明细、仓库、批次 | 接收角色仅查看工作所需来源，质量确认独立授权 |
| 委外/加工聚合 | 多种来源、排产、工序 | 每来源独立检查，不因其中一种来源有权而泄露全部 |
| 审批待办 | 被审批单据、提交人、当前审批人 | 查看待办不自动获得审批；有审批权也不能自审或替代指定审批人 |
| 导出与附件 | 当前可见记录集合、文件关联 | 与页面数据范围一致；不能凭文件 ID 绕过对象范围 |
