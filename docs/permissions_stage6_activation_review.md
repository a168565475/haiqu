## 启用业务权限前的具体缺口

目前以下审批操作，在有效账号及员工层面只有 admin 是候选人：样品厂长审核、样品仓库核对、生产订单确认、领料审核、工价审批。启用禁止自审后，admin 自己提交的这些单据需要其他符合条件的审批人。

报价审批及样品费用/财务/PMC 有历史非 admin 候选账号，名单见预检；候选仅代表账号、员工和操作权限满足，具体记录仍须符合范围、实际提交人和指定处理人要求。不能把历史测试名称账号擅自指定为正式审批人。

因此建议先启用权限管理，用于配置人员及审批权限，再启用销售和其他业务权限。一次性开启业务开关前，需要确定这些审批人的实际账号、角色和范围；本次不自动给 44 名员工分配权限。

1. 重新运行只读预检，确认角色、账号、待迁移和开关与批准清单一致；若范围变化，先报告差异。
2. 在短暂维护窗口暂停业务写入；执行 `pg_dump -Fc` 生成唯一时间戳备份，验证 `pg_restore --list` 成功并记录文件散列。不会把备份内容或凭据写到日志。
3. 在 ERP 根目录运行 `docker compose exec -T backend python manage.py migrate access_control 0005 --noinput`，留存实际结果。
4. 先预览 `initialize_access_roles`；无冲突后，仅对该命令进程临时传入 `ACCESS_MANAGEMENT_ENABLED=true`，执行 `initialize_access_roles --apply`。现有幂等命令只补缺、不会替换授权或员工。
5. 定点修改四个环境变量，并执行 `docker compose up -d --no-deps --force-recreate backend` 加载环境；不运行 down、清理卷或其他模块迁移。
6. 健康检查、只读计数及真实管理入口检查通过后，形成实际启用记录。不能仅凭容器启动成功宣称启用完成。

## 恢复方案

- 第一阶段仅启用管理且尚未向员工分配新角色时，可关闭 ACCESS_MANAGEMENT_ENABLED 并重建后端，隐藏管理入口；保留已创建表、空角色和审计，避免删除证据。
- 不逆向删除迁移、不删除旧账号或恢复整个数据库来处理普通配置问题。
- 如果已经开始分配角色、建立团队或启用销售/模块权限，需要先审阅实际授权变化。关闭业务开关会回到旧授权语义，不能保证新范围约束仍然有效；应先暂停普通员工操作再决定恢复措施。
- 只有确实发生数据损坏时才考虑从备份恢复；整库恢复会覆盖备份后写入，必须单独审阅并授权，不自动执行。

## 后续正式开启业务范围

通过管理页面确定审批人、员工角色和销售团队后，重新预检多角色组合、旧直授、缺归属客户和审批候选。确认清单后，将 SALES_ACCESS_ENABLED 与 MODULE_ACCESS_ENABLED 一起启用，保留管理开关开启。不要把只开其中一个业务开关当作已完成整体权限启用。

本步骤尚待人员配置及明确启用范围；不将新角色名称当作岗位授权模板，不自动发放“全部”或删除历史账号。
