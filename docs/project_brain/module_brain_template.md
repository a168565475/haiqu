# 模块知识卡模板

复制本模板建立具体模块知识卡前，先确认该模块确实有长期可复用的规则、流程、接口关系或验证经验。没有内容的模块不要创建空文件。

## 使用规则

- 只记录会影响以后判断、实现、验收或工作顺序的信息。
- 每条重要内容都写来源、日期和可信度。
- `confirmed` 表示用户明确确认；`verified` 表示已经由代码、Figma、API、数据库或浏览器证据验证；历史聊天不能默认是 `verified`。
- 不确定的内容写成 `draft` 或 `unknown`，不能为了完整而补猜。
- 与已有知识重复时引用原文；冲突时同时保留旧值、新值、来源和建议，不静默覆盖。

## 1. 模块基本信息

```yaml
module:
display_name:
status: draft
confidence: unknown
last_reviewed:
maintainer:
source_links: []
```

## 2. 模块目的

用几句话说明：

- 为什么需要这个模块
- 它服务哪些角色或业务对象
- 它解决什么问题

## 3. 负责范围

记录模块明确负责的功能、对象和流程。每条附来源。

## 4. 不负责范围

记录容易被误放进本模块、但实际属于其他模块或尚未确认的内容。

## 5. 业务规则

只记录已确认或已验证的规则。每条使用下面的格式：

```text
- 规则：
  类型：confirmed / verified / draft / unknown
  来源：
  日期：
  影响：
```

## 6. 业务流程

用文字或简单步骤说明：

1. 进入条件
2. 主要处理步骤
3. 成功结果
4. 失败、撤销、阻塞或异常结果

业务流程未确认时，标记为 `draft`，不要用页面按钮顺序代替业务流程。

## 7. 数据和接口地图

记录实际使用的模型、关键字段、API、权限和数据范围来源。只写已找到的路径或接口，不凭页面名称猜接口。

| 数据模型 |  |  |  |
| API |  |  |  |
| 权限 |  |  |  |
| 数据范围 |  |  |  |

## 8. 页面和设计地图

记录相关路由、组件、已确认 Figma 节点、`DESIGN.md` 规则和 QA 证据。页面源码现状不能直接替代正式设计规范。

## 9. 与其他模块的关系

说明上游、下游、共享对象、触发关系和边界。没有证据的关系写 `unknown`。

## 10. 已确认决定

记录会改变后续实现方向的决定，并保留日期、来源和被替代的旧方案。

## 11. 可复用经验

记录已经验证有效的组件、流程、验收方法或排错方法。未验证的建议放在研究或待办中。

## 12. 踩坑和失败方案

记录问题表现、原因、影响、解决办法和避免再次发生的检查点。不要只写“以后注意”。

## 13. 当前状态、问题和下一步

```text
已完成：
进行中：
待确认：
已知问题：
技术债：
下一步：
```

每条状态都要带日期和来源；状态过期后标记为 `superseded` 或 `archived`，不要删除历史。

## 14. 更新与淘汰

- 业务规则、模块边界、接口、权限、设计或状态发生变化时更新。
- 被新决定替代的内容保留原文，标记 `superseded` 并指向新内容。
- 没有长期价值、可以从代码重新生成或只有一次性调试过程的内容，不写入模块知识卡。
