## 1. 使用说明

本矩阵把用户已经确认的样品规则与当前代码、历史验收证据分开记录。它用于决定后续开发顺序，不把“用户已确认”误写成“代码已实现”。

完整的用户细化原文仍保留在 [`sample-flow-update-20260930-clarifications.json`](../sample-flow-update-20260930-clarifications.json)；本文件只保留分类统计和会改变开发方向的关键差异。

事实优先级：当前代码和模型 → 当前测试/API/浏览器证据 → 最新用户决定 → 历史报告 → 旧 PRD。历史报告中的“尚未接入”只代表报告当时的状态，不能覆盖后来已经存在的代码。

## 4. 暂不自动改代码的原因

- 材料提交后增删改会影响采购来源、到货行和领料快照，不能只开放前端控件。
- 无需用料撤销会影响参数阶段、材料状态和审计记录；D-086 已明确第一张参数图片是不可撤销的截止点，仍需设计无图片时的回退目标和审计字段。
- 入库上限按申请数量、报工数量和参数完成状态之间存在跨模块关系，必须先统一状态计算。
- 用户确认规则和当前代码不一致时，知识库先记录差异，不能静默把代码事实写成已符合规则。

## 5. 开发顺序

1. 材料需求版本、提交后编辑和采购单建立后的锁定边界已按 D-082 暂缓，不进入当前代码实施。
2. 后续若重新启动该块，再先确认材料版本、采购来源锁定和并发控制的完整范围。
3. 当前可转向无需用料撤销、部分到料和样品专用领料展示，或其他已确认的模块知识整理；是否开发仍需单独确认。
4. 每项改造单独确认代码范围，再运行后端测试、API 验证和 1920 浏览器验收。

## 6. 更新规则

- 新的用户决定写入 `decisions.md` 后，再更新本矩阵。
- 当前代码变化先更新“当前代码或证据”和状态，不自动改变用户确认规则。
- 被替代的规则保留原编号、来源和替代决定。
- 历史专项报告只作为对应日期的证据，不覆盖最新代码核对结果。
