## 3. 先确认业务资料与四张旧计划

2. 明确 HT26050 的 32 支厂内领料是否继续。旧外发 4,260 支包含同一批全额需求：保留厂内 32 支时，仓库原料外发至多 4,228 支；若全 4,260 支作为原料外发，就不再重建那 32 支厂内原料领料。普通原料六项共 7,350 PCS 另行逐行确认。
3. 明确 HT26001 草稿剩余 10、6 支是否继续领用；原已领合计 1,166 支额度必须继承，不得重置。

## 5. v2 解决了什么，旧期初契约仍有什么限制

新增启用备份校验会强制：备份版本为 2、绑定当前维护 ID 和开始时点、`维护开始 ≤ 备份开始 ≤ 备份完成 ≤ 恢复核验完成 ≤ 当前时间`；校验实际 PGDMP 文件 SHA/大小、恢复报告 SHA、源前/源后/恢复全表一致及当前表集合。缺少开始时点、错维护会话、文件被改、缺表、旧版本证据均阻断正式启用。

**这补上了启用入口的备份开始时点检查，未回写旧历史，也没有升级旧期初导入的 v1 契约。** `import_public_stock_opening` 仍只接受 v1 备份凭证、强制文件 SHA 与完成时点；其自身仍不能证明备份从本次停写之后开始。步骤 C 仍须以实际阶段日志补足该操作证据，并独立审阅后才应用期初。不要把 v2 文件直接传给只接受 v1 的期初命令，也不要给旧 v1 凭证补造一个历史开始时点。

本次 tools 库已经做过期初和接续，新 v2 是对其当前启用前状态的新备份；不是重做旧期初备份。步骤 C 与 E 是不同恢复节点，数量、时点和用途要分别保留。

## 6. 失败与恢复处理

- 资料缺失、旧待审/待发未处理、库存或额度对不上：保持 MAINTENANCE，修正方案后重做只读预检。不能靠环境开关、手动改 PUBLIC、降回 LEGACY 或排除阻断记录来继续。
- 备份/恢复失败、目标库已存在、文件摘要变化：停止，保留备份、日志和新验证库。不得自动删除、覆盖或换名盲重试；先查明已经执行到哪一步。
- 清单过期、锁超时、并发冲突：不沿用旧摘要；先核对实际控制状态和审计，重新生成现场清单并提交审阅。
- 应用命令超时或输出文件写入失败：不等于数据库没有提交。先只读核对控制状态、唯一审计、原请求与摘要；已成功时只能按原请求进行受控幂等核对，不能换新请求再次启用。
- 启用后发现问题：先停止新增业务并保存现场证据，不降低库存版本继续跑旧流程。主库恢复属于新的高风险动作，必须明确恢复点、影响范围和再次授权；本操作包不执行恢复主库。

验收边界：本轮完成的是隔离激活工具测试、实际 v2 备份恢复核验、tools 真实只读预检及其重复稳定性、最后库存不变核验；业务现场仍因 83 条记录被阻断，正式主源码还存在 1 处待联合整合的漂移。没有正式启用、主环境合入/迁移或新的 HTTP 与浏览器业务验收。
