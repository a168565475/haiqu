# 工价方案与计件报工开发方案 V1

日期：2026-09-17。执行方式：**连续开发**。正式入口：生产车间 → 工价方案、报工记录；内部作业计划行增加工价方案与报工入口。

本次交付开发方案、冻结依据和验收清单。正式业务代码开发、数据库迁移、真实接口联调和正式页面视觉验收尚未执行。连续开发方式已明确，实施时不再逐页或逐阶段询问是否继续。

## 1. 交付目标

实现真实链路：内部作业计划产品 → 建立订单产品工价方案 → 厂长批准 → 按生产日期取得适用版本 → 负责人逐行录入员工与工序产量 → 保存立即生效 → 按日期查询汇总及明细。

必须同时交付数据模型、前向迁移、真实接口、权限、前端、事务与重复提交保护、专项测试，以及使用 **Playwright** 的真实浏览器交互和视觉验收。禁止用原型演示数据、截图贴图、前端内存记录或“构建通过”代替正式功能完成。

一期范围：计件工价、厂长审批、历史引用、工价变更、员工独立报工、装配生产线、日期汇总、历史价格快照。本期不做计时、多人共同计件分摊、超报审批、工资结算、自动入库、报工扣料、质量返工模块。

## 3. 已确认业务规则

| 主题 | 开发规则 |
| --- | --- |
| 归属 | 工价关联生产任务单中的具体产品行、车间、工艺；不是销售订单，不用产品名字符串做关联 |
| 人员 | 车间负责人统一录入；每行选择所属车间员工；录入账号与计件员工分别保存 |
| 计价方式 | 仅计件；每道工序自身单位，不按套换算 |
| 数量上限 | **本期不设上限；报工数量须为有效数值且大于零。** 不拿订单数量限制工序产量，不移植领料不超领规则 |
| 共同计件 | **仅员工独立完成的产量；本期无共同产量分摊功能** |
| 工价字段 | 以往工价可引用或手填；修改工价只是填写项，不计算、不联动申报工价 |
| 工价合计 | 正常明细申报工价直接相加；作废明细排除；不是统一计件单价，不能再乘订单数量 |
| 工价审批 | 新增与变更均须厂长批准后可用于报工 |
| 历史引用 | 复制数据作当前方案参考，保留当前订单归属，重新审批，不继承旧订单审批或已报数量 |
| 调价取价 | **按生产日期匹配已批准的版本**；历史已生效报工保留原单价，不自动重算 |
| 报工布局 | 选定方案后生成工序列表；员工、生产线、工序、数量在同一行；增加行仍选该方案的工序 |
| 装配线 | 同行选择 1线、2线、3线；其他车间不要求生产线 |
| 保存 | 一次保存生成一笔报工记录，成功即生效，无报工审核环节 |
| 查询 | 列表按日期汇总，点击日期进入当日明细；保留每次保存的记录身份，不能只剩汇总数 |
| 累计 | 同一订单产品的同一实际工作项跨员工、日期、生产线和工价版本累计；调价和改名不重置数量 |
| 库存 | 报工不重复扣材料、不自动生成成品入库，不把工费当已支付工资 |

金额由后端用 Decimal 计算。行金额按数量×批准申报单价计算，四舍五入到分后再合计；数量和单价作为十进制字符串传输，拒绝 NaN、Infinity、负数和超出字段精度的值。数据库存储范围校验属于技术限制，不能伪装成业务数量上限。

旧 PRD 的“展开员工子表”“剩余可报量取决于上限”“共同计件待定”等内容已被本节对应规则替代。正式实现禁止恢复嵌套员工表。

### 5.1 必须保留的交互细节

- 切换订单或产品后清空失效候选；有已填写数据时提示将受影响的行，不能静默串单。
- 工艺多选；按当前原型单个工序品名输入位提供真实候选匹配，不任意比较“车间名称＝工序品名”。多选品名不在本次页面范围。
- 历史筛选可看其他数据，但不匹配当前车间/工艺时禁止直接引用，说明原因。引用以批准申报价作为参考，复制后仍需审批。
- 方案行有稳定主键。同一道目录工序可以用于不同名称部位、不同价格，报工按**方案明细 ID**取价，不用目录工序 ID 找第一条。
- 选定适用方案后每条正常工价明细生成一行；新增工序行只列出选定方案明细，选项显示足以区分部位的文字。
- 已报工数量是工作项整体累计，不因当前列表筛选日期变短而减少；当日报工数量只统计当日，两个口径分开。
- 原型示例数量与姓名不进入正式默认值；加载失败、无方案、单位未配置均明确显示原因。

## 6. 数据模型方案

建议在新的 Django 应用 `workshop_reporting` 中承载工价和生产报工，避免与样品报工混淆。以下为拟建模型，最终字段名遵循项目命名规范。

| 模型 | 主要字段及约束 |
| --- | --- |
| Operation 补充 | 可空 reporting_unit 外键指向 ProductionUnit；存量不自动填“件/套”，单位配置后才允许相关方案送审 |
| WorkshopReportingScope | 登录人员外键、车间外键、有效状态；仅在现有授权模型不能表达车间范围时新增；员工资料不等于账号权限 |
| WageScheme | 唯一编号、production_task/product_line/workshop、工序品名快照、类型、状态、版本号、parent_scheme、历史来源、批准人/时间、有效起止、revision、创建更新人 |
| WageSchemeCraft | 方案与工艺外键；唯一(方案,工艺)，验证厂内及车间归属 |
| WorkItem | production_task_product、workshop、craft、operation、稳定工作身份及单位；不同部位分别建项，方案变更沿用原项，不用可编辑名称作主键 |
| WageSchemeLine | 方案、WorkItem、序号、名称部位、工序/描述快照、单位、以往/修改/申报价、正常/作废、备注、source_line；所有行有独立主键 |
| WageSchemeEvent | 方案、动作、操作人、时间、意见、前后版本；与事务一起落库 |
| WorkReport | 唯一编号、production_date、production_task、product_line、schedule_product、workshop、scheme_version、负责人及录入账号、revision、最后修改人、saved_at、金额合计、client_request_id、payload_hash |
| WorkReportLine | report、scheme_line、WorkItem、WorkshopEmployee、装配线、数量、单位/工序/姓名/单价快照、金额、订单数量快照；保存后不随主数据改动 |

实施约束：

- 报工主表每次成功保存一笔，日期汇总通过查询聚合获得，不建一张可互相覆盖的“每日总单”；这保持原型每次保存明细可追溯。
- 数量建议 Decimal(18,4)，单价建议 Decimal(18,4)，金额 Decimal(24,2)，本单合计必须防溢出；业务数量大于零，不设置订单数上限。单位允许的小数位通过实际单位配置核对，拒绝静默截断。
- 单价不允许空；零单价仅在明确送审并批准时成立，不能以缺失转零。以往价/修改价无值保留 NULL。
- 单据编号唯一；`client_request_id` 唯一；(scheme,version/line_number) 等实际组合约束按模型归属设置；外键 PROTECT，不物理删除已引用记录。
- 一条方案明细关联一个工作项；同一工作项跨版本累计，同名不同部位不可合并。同方案同工作项不能重复建价，重复员工报工行仍可多行。
- 方案变更复制时保留原工作项 ID，引用其他订单历史时创建当前订单工作项；禁止把源订单累计数量带入。
- 查询索引覆盖 production_date、product_line/workshop、work_item、scheme_line、员工、状态与日期；工序行总数增加时仍批量查询，避免逐行额外请求。
- 方案适用范围、生效区间的最终唯一约束见第 8 节；不得擅自给同产品跨订单的价格建全局唯一约束。

## 7. API 与权限方案

接口前缀沿用项目现有 `/api/`。以下为拟建接口，不描述为已可调用。

| 接口 | 内容 |
| --- | --- |
| `GET /api/workshop-reporting/context/` | 按排产产品取任务产品、订单数量及单位、实际厂内工艺、车间、操作权限、状态原因 |
| `GET /api/workshop-reporting/operation-options/` | 按车间、所选工艺和品名返回有效工序及报工单位 |
| `GET/POST /api/workshop-reporting/wage-schemes/` | 列表/保存草稿 |
| `GET/PATCH /api/workshop-reporting/wage-schemes/{id}/` | 详情/修改草稿，返回 ETag |
| `POST .../{id}/submit/`、`approve/`、`return/` | 送审/厂长批准/退回；后端状态门禁 |
| `POST .../{id}/change/` | 基于已批准方案创建新版本草稿，保留原工作项映射 |
| `GET /api/workshop-reporting/history-schemes/` | 有权读取的批准历史及明细，不跨权限泄露价格 |
| `GET /api/workshop-reporting/price-context/` | 按产品行、车间、工艺、生产日期返回适用版本、正常明细与累计数；无唯一候选返回原因 |
| `POST /api/workshop-reporting/work-reports/` | 真实提交，后端重算价格与金额，原子生效 |
| `GET/PATCH /api/workshop-reporting/work-reports/{id}/` | 查看原始记录及直接编辑；PATCH 必须携带 If-Match，保持原单号和原录入人，重新校验并整单原子替换明细 |
| `GET /api/workshop-reporting/work-report-days/` | 权限过滤后按生产日期汇总及分页 |
| `GET /api/workshop-reporting/work-report-days/{date}/` | 日期汇总信息及逐行明细分页，保留所属报工记录编号 |
| `GET /api/workshop-reporting/work-reports/{id}/` | 一次保存的原始记录与价格快照，支撑追溯 |

生产日期使用 Asia/Shanghai 业务日期，保存/批准时间使用系统时区规范的时间戳；不能以浏览器 UTC 截日代替生产日期。所有范围字段服务端校验，不能信任 query 中带来的车间或产品。

权限建议：查看方案、编辑方案、送审、批准方案、查看报工、创建报工、修改报工、查看全部车间；厂长审批由后端明确权限决定，不依靠页面按钮或角色名称文本。列表、选项、详情和汇总必须使用一致的数据范围。没有对应权限的账号调用批准或修改接口应返回 403。

错误响应沿用项目统一格式。无权 403、不存在 404、字段不合法 400；状态变化、内容版本冲突和幂等请求冲突沿用项目既有冲突码及错误结构，不另造不一致约定。前端保留已填内容，提示具体原因，不将接口失败显示为空列表或成功。

## 8. 工价生效、并发与实施前需明确的细节

### 8.1 已确认的取价约束

报工按生产日期落入的批准版本取价，不直接取创建时间最新一份。比如 9月16日的生产，在9月18日补录，不能因为9月17日涨价就使用新价。若生产日期没有适用的批准版本，阻止保存并说明原因，不能猜价或填零。

已生效报工保存自己的价格快照；后来批准另一版本不能自动改历史金额。页面打开后适用版本发生变化，保存返回冲突并要求重新核对，禁止偷偷换价。

下列细节未在现有原型里定义，列为实施决策，不把建议冒充用户确认：

| ID | 需明确的细节 | 建议与影响 |
| --- | --- | --- |
| D01（已确认 A） | 版本具体生效日、同日多次批准如何取价 | 批准时必须明确生效日；新版生效日必须晚于上一批准版，禁止同日替换和倒序生效；批准新版时自动将旧版截止到新生效日的前一天，已保存报工不重算 |
| D02（已确认 A） | 同订单产品车间是否只允许一份当前方案，能否按工艺拆分 | 同一订单产品行＋车间只维护一条多工艺方案版本链；不允许按工艺建立同期并行方案；审批、数据库排他约束与报工取价共用同一范围键 |
| D03（已确认：暂不接入） | 敲布孔与四类内部计划的入口映射 | 敲布孔暂不接入金工、裁剪、车缝、装配四类计划，不映射到其中任何一类，也不增加第五个计划菜单；敲布孔车间及其基础资料继续保留，后续如需接入必须重新确认入口、权限和历史数据影响 |
| D04（已确认：允许补录和直接编辑） | 暂停/取消/完工后的补录、录入日期允许范围、已保存纠错 | 已接单、生产中、已暂停、已完成、已取消任务均允许按实际生产日期补录；已保存报工由具备修改权限的账号直接编辑。编辑保留报工单号、原录入人和创建时间，记录修订号及最后修改人；必须按编辑后的生产日期重新匹配批准工价并整单重算，使用 If-Match 防并发覆盖，不增加作废重报流程 |
| D05 | 原型草稿/历史引用中的细节 | 正式方案建议以历史批准申报价带入以往价；修改价只保留用户填写。草稿完整性和覆盖提醒按实际交互补齐，不能把所有原型演示限制当已定业务规则 |

这些事项只阻止依赖它们的行为定稿或正式启用，不阻止连续完成确定的页面、模型、查询、通用校验和验收脚本。遇到缺口一次说明选项并继续独立部分；不反复询问已确认的三个核心规则。未决项未关闭时，最终不得宣称全功能完成。

### 8.2 事务和重复提交

1. 前端生成一次操作的请求身份 UUID，网络重试复用，不因点击重试生成新 UUID。
2. 后端计算规范化业务内容哈希；相同 UUID＋相同内容返回原记录，相同 UUID＋不同内容返回冲突；同日同员工真实第二次做工用新 UUID，合法保留。
3. 工价批准、版本切换和报工保存采用一致锁顺序：任务/有效排产上下文 → 同任务产品/车间的稳定价格范围锁 → 方案版本 → 按 ID 排序的工作项。必要时用已存在任务产品行作范围锁，不能只锁“可能不存在的价格行”。
4. 在事务内复核方案适用日期、批准状态、工序/员工归属、单位和请求版本；后端重算每行金额，一次写入主表、所有员工行和审计。
5. 任一行失败整单回滚，不能部分员工先入账。已报数量按已生效记录实时汇总或采用有一致性保障的缓存；没有数量上限不等于可以丢失并发提交。
6. 草稿修改及审批用项目 ETag/If-Match 防覆盖；审批内容与审批人看到的版本必须相同。

## 10. Playwright 交互与视觉验收

### 10.1 环境和数据

- 原型 4188 只提供基准。正式应用使用项目开发环境，例如 `http://localhost:8080`；地址从验收环境变量配置，不硬编码成原型端口。
- 使用独立测试数据库和文件目录建立确定性数据：厂长账号、限定车间负责人、无权限账号、至少两个任务及同产品不同产品行、正常/作废工价、跨日变更版本、两名同工序不同工价员工记录。
- 浏览器权限检查必须真实登录各账号；默认成功链路不能用 `page.route().fulfill()` 伪造接口。模拟断网/500只用于专门失败场景，单独标记。
- 真实业务测试只写隔离测试环境；使用唯一测试标记和可追溯数据，不在用户正式订单上练习报工。
- 浏览器固定 Chromium、1920×1080、deviceScaleFactor=1、中文、Asia/Shanghai、字体版本；等待字体和业务数据加载完成，禁用过渡动画，保留相关控制台和请求日志。

### 10.2 九页与重点交互

- G01 搜索、筛选、分页、权限、空结果；不能把日期汇总行数当报工单数。
- G02/G04 以往价/修改价不联动申报价，正常合计、作废排除，任务产品联动、工艺/品名过滤、工序单位缺失、历史引用覆盖提醒。
- G03 打开、关闭、拖动、最大化、还原、键盘焦点；跨车间禁止引用，停用数据不冒充有效。
- G05 送审/批准/退回，非厂长 403，过期 ETag，变更不覆盖历史。
- B01 四类计划进入上下文正确，已批准新产品状态实时更新，保留生产领料和查看主计划。
- B02 平铺工序/员工行、方案明细唯一取价、追加已选方案工序、装配线、非本车间人员阻止、数量零/负/非法阻止；**数量高于订单量也允许**，不得遗留超报上限。
- 跨日期取价：旧生产日用旧批准版本、新生产日用新版；无版本阻止；生产日期变更重新加载并提示核对；保存中版本变化不静默换价。
- 相同请求重试一次入账，真实第二次保存两笔明细；单行失败无部分入账；多人并发记录不丢。
- B03/B04 按生产日期分组、真实分页、人数/订单数去重、金额从行汇总、同目录工序不同工作项不混淆、按日明细查看价格快照。
