# 订单产品工价方案与工序报工方案

版本：V0.3，更新于 2026-09-17。状态：业务方案草案。沿用已确认规则，补充操作流程、异常处理与纠错建议；数量上限、调价取价和共同计件等待本轮答复。

本文件承接《生产领料与每日报工 PRD》，以本次用户描述为工价方案和报工的最新依据。仅整理方案，未实施功能、迁移数据库或执行业务验收。

## 1. 目标与范围

主流程：内部作业计划的产品 → 制定订单产品工价方案 → 厂长批准 → 车间负责人按日期、员工和工序报工 → 统计工序产量与工费。

文字暂按以下意思整理：“几件”为“计件”，“生成一次报价记录”为“生成一张报工记录”。如果实际指报价业务，需要另行调整。

### 已明确的需求

- 报工入口设在内部作业计划，点击按钮进入报工。
- 工价方案关联生产任务单、该任务单中的产品、车间和工艺，可引用历史数据修改。
- 工价方案必须经厂长同意后才能用于报工。
- 车间负责人统一录入员工产量；工序使用各自的报工单位，此前已确认，本次没有变更。
- 本期只做计件，自动获取对应订单产品工价方案，从方案明细选择工序。计时继续留待后续单独讨论，不因日期变更自动纳入本期，本期不设计工时字段、小时单价或计时入口。
- 装配报工选择 1线、2线、3线；各工序选择所属车间员工。
- 工价明细支持正常、作废。
- 不按套计算或折算工序数量、单价和工价合计；按各工序自身单位记录。取消 V0.1 的每套工作量换算建议。
- 选择历史数据时自动带入历史工价；没有历史数据时允许自己填写，不强制先有历史方案，也不将缺失值默认为零。
- 修改工价只是填写项，不参与加减运算，也不自动联动申报工价。申报工价单独填写，厂长批准后作为报工单价。
- 工价合计直接相加正常明细的申报工价，作为方案单价汇总；不乘订单数量，不按套折算。
- 同一工作项跨员工、日期、生产线、工价版本累计报工；调价不重置累计数量，历史报工保留原单价。
- 多人共同完成的同一份产量不能重复累计；具体分配方式尚未明确。
- 报工不需要审核，负责人提交成功即生效，计入已报数量与金额。工价方案仍须厂长批准。

本次工价来源升级为“订单产品的已批准工价方案”。此前通用的“产品＋工序标准工价”可以成为历史参考，不应绕过订单方案审批直接用于报工。

报工不再次扣仓库库存；领料仍由仓库审核确认扣库存。工序产量、成品入库量和已支付工资是不同记录，本期不因报工自动生成入库或工资支付。

## 3. 入口与关联规则

建议在内部作业计划每条产品记录的操作区增加“报工”，并提供“工价方案”入口。进入时带入当前排产计划、生产任务单、任务产品、计划分类、对应厂内工艺及实际所属车间。

一张报工单建议限定一个生产任务单中的一个产品、一个车间和一个生产日期，本期为计件报工。可以记录多道工序、多名员工。是否采用该单据粒度为方案建议。

匹配工价时同时检查任务产品、车间、工艺、正常明细以及方案批准状态。不能只按产品名称或工序名称匹配，也不能直接取同产品另一订单的批准方案。

无可用方案时，报工入口仍可提示“请先建立工价方案并经厂长批准”，提供对应入口；不自动填零单价并提交。存在多个候选时显示各自适用范围，不能静默取最新一张。

### 4.2 工价明细

| 字段 | 来源与填写方式 |
| --- | --- |
| 名称－部位 | 手工填写，如椅面、靠背、支架；保留稳定明细身份，改文字不应重置已报产量 |
| 申报工序 | 按下方工序筛选规则选择 |
| 制作工序描述 | 可填写具体做法与计件边界；建议选工序后带入已有描述，允许补充方案说明 |
| 以往工价 | 选择历史数据时自动带入；没有历史数据时允许手工填写。自动带入记录来源，手工填写记录为手填参考值，不伪装成已批准历史价 |
| 修改工价 | 仅为手工填写记录项，不进行加减运算，不自动联动申报工价 |
| 申报工价 | 独立填写的送审单价，厂长批准后供报工使用；不由以往工价和修改工价计算得出 |
| 状态 | 正常、作废；作废明细不用于新报工，保留历史引用 |
| 备注 | 可选填写 |
| 报工单位／计价单位 | 沿用工序自身单位，如根、片、件等，并显示对应单价单位；不统一按套计算，不增加每套换算字段 |

工序筛选：

1. **裁剪工艺：此前指定申报工序为“整套”。** 不展开裁片明细。后续又明确不按套算，因此不能直接由“整套”推导计价单位。将它仅作为工序选项名称是当前方案解释，并非用户已明确确认；实际计件单位与所代表的工作内容仍待 Q5 明确。
2. **装配、车缝、金工：** 从工序资料选择，同时满足“工艺所属车间＝方案车间”“工艺属于方案已选工艺之一”“品名属于方案已选工序品名”。多项工艺之间是任一匹配，不是要求一个工序同时属于多个工艺。
3. **敲布孔：** 暂不从金工、裁剪、车缝、装配四类计划进入报工，也不增加第五入口；车间及其基础资料继续保留，未来接入时再单独确认工序筛选和权限规则。
4. 工艺与工序品名变化后重新校验已有明细，提示不匹配项，不静默保留或删除。
5. 同一道基础工序可用于不同部位；应区分实际加工对象，避免同一部位同一工作重复建价、重复计件。复制或变更后的同一工作需要继承原有累计口径。

### 4.3 历史引用、新增与变更

操作流程：选择当前任务产品与车间 → 有历史数据则选择并自动带入，没有则自行填写 → 完善明细 → 保存草稿或提交厂长审批。

- 借用其他订单的历史数据为当前订单首次建价，建议类型仍为“新增”，记录历史来源；对本订单已有方案调价才为“变更”。此类型判断为建议。
- 引用历史只带入可编辑的明细内容与参考价，不继承原订单、审批结果和报工数量。
- 当前订单的工艺、工序及适用范围重新检查；不适用或停用的历史工序标出，不自动提交。
- 已批准方案建议不能直接覆盖修改；生成新版本，经厂长批准后按约定时间生效。
- 新版审批期间旧版建议继续有效；新版被退回不影响旧版。是否允许立即停用旧版应单独明确。
- 历史报工保存当时方案版本、工序内容、单位和单价。新版本生效不改变既有报工的原单价，也不重置累计数量；追溯补差本期不默认加入。

建议方案状态：草稿 → 待审批 → 已批准；厂长不同意则退回修改。版本被替代、整份方案停用应单独表达，不能把“明细作废”误当作整份方案审批状态。

### 4.4 工价合计与单位

已确认：不按套计算工价合计，不维护每套工作量用于折算。

已确认算法：工价合计＝所有正常明细的申报工价直接相加。作废明细不参与；以往工价、修改工价也不参与。修改工价只是记录项，填入或修改该字段不会自动改变申报工价或工价合计；修改申报工价后才更新合计。

该数值只作为方案单价汇总展示，尤其不同工序存在元/根、元/片等不同单位时，不代表统一计价单价，不能再乘订单数量计算工费。报工金额始终按各员工明细的本次数量 × 对应批准申报工价计算，再汇总金额。缺失工价不默认为零。

例：两条正常明细申报工价分别为 0.50、0.60，方案工价合计为 1.10；另有作废行 0.20 不计入。将第一条修改工价填写为 0.80，只保存这一填写内容，不自动改变第一条申报工价 0.50 或合计 1.10。

### 4.5 审批与引用历史的操作细节（新增建议）

厂长审批检查的是整份方案及其正常明细。建议审批页突出订单产品、车间、工艺、工序、单位、最终申报工价；新增与变更均需要批准。修改工价只是填写内容，不能用它直接生成“涨价金额”；如展示调价前后对比，应比较旧版批准申报工价与本次申报工价。

| 场景 | 建议处理 |
| --- | --- |
| 草稿保存 | 允许资料尚未填写完整；不供报工选用 |
| 提交审批 | 至少一条正常明细；每条具有明确工作项、单位和申报工价；不允许关联不属于该车间和所选工艺的工序 |
| 待审批时修改 | 先撤回到草稿再修改，重新提交；不能在厂长查看后静默修改内容 |
| 厂长批准或退回 | 记录实际操作人、时间和意见；退回不产生可用价格，不增加多级审批 |
| 已批准方案变更 | 从原方案发起新版本，展示真实价格差异；旧版保留历史，不覆盖已生效报工 |
| 正常明细改作废 | 属于方案变更；作废不删除此前工费或累计产量。是否仍可补录作废前的工作，随取价时间规则一起确定 |
| 全部明细作废 | 不能作为可用工价方案提交审批；整份方案停用流程另定，不用空方案替代 |

历史引用建议明确到来源方案的具体版本。以往工价建议取所选历史明细的批准申报工价，不自动取源明细中更早的“以往工价”；此字段映射需定稿。源方案修改工价不复制为本次填写值，当前申报工价可以预填参考值供检查修改，但仍需当前订单的厂长审批。

无历史数据时允许手填，不要求伪造历史来源。历史引用后的手工修改需要保留来源和当前填写值，不能把修改后的价格标成原历史批准价。选择历史方案时保留当前任务产品归属；如果将覆盖已填写明细，先展示替换范围，避免丢失填写内容。

## 5. 工序报工

### 5.1 报工基本信息

| 字段 | 建议规则 |
| --- | --- |
| 报工编号 | 系统自动生成，唯一 |
| 报工类别 | 本期固定计件，不提供计时选择 |
| 生产任务单、产品、排产计划 | 从内部作业计划带入，不手填关联 |
| 车间、工艺范围 | 来自实际作业及方案适用范围，不能只根据计划标题推断车间 |
| 生产日期 | 实际做工日期；已接单、生产中、已暂停、已完成、已取消任务均允许补录，仍须存在该日期适用的批准工价 |
| 工价方案 | 对应订单产品的已批准可用版本，显示编号；实际用价需保留版本 |
| 报工负责人 | 实际录入人，与计件员工分别记录 |
| 记录时间、备注 | 系统记录提交时间；备注按需填写 |
| 本单数量与金额 | 数量按工序和单位分别统计；金额可汇总，不能把各工序数量相加作为成品数量 |

流程：点击产品“报工” → 自动带入上下文 → 填写生产日期 → 获取可用工价 → 选择工序 → 展开录入员工产量 → 检查合计 → 提交成功即生效，无报工审核环节。

### 5.2 工序主行与员工展开行

建议每一工价明细为主行，展开后录入该工序各员工的工作量。同一工作项的已报数量统一汇总，剩余可报量是否展示取决于上限规则的后续确认。

| 层级 | 显示与填写内容 |
| --- | --- |
| 工序主行 | 名称－部位、工序、工序描述、计价单位、单价、订单数量、已报工数量、本次报工数量、合计金额 |
| 员工展开行 | 本车间员工、该员工本次报工数量、单价、金额；装配增加 1线/2线/3线选择 |

用户明确的列全部保留，并显示实际计价单位。撤回 V0.1 按每套换算增加工序计划量的建议，不在本期表单添加工时字段；具体版式待设计阶段确认。

装配线建议在员工展开行选择，同一张报工单可以包含不同线的员工。已确认切换生产线不重置同一工作项的累计报工，也不将一份产量复制成三份。

员工候选来自实际车间员工资料，建议只允许在职员工用于当期报工。跨车间支援、离职员工历史补录需要单独规则，不能随意选择其他车间员工或用系统登录账号替代生产员工。

### 5.3 计件金额

计件金额：员工金额＝该员工本次有效报工数量 × 本行批准的申报工价；工序金额＝员工行金额之和；本单金额＝工序金额之和。以往工价、修改工价不参与报工金额计算。

建议单价最多 4 位小数、金额按员工明细行四舍五入到分后汇总；数量精度按工序单位约定，禁止负数及非数值。零单价如允许，必须是明确批准的零价，不将未配置工价解释为零价。

每个员工独立完成的产量可以求和。若几人共同完成一批，例如两人合做 100 件，则不能每人各填 100 件而统计成 200 件；不重复累计原则已确认。团队共同计件需另外确定分配数量或分摊金额的方式，不能擅自采用均分，也不能用重复产量发放工费。

### 5.4 已报工数量和上限

已确认不按套折算，撤回 V0.1 的“排产数量 × 每套工作量”公式。

- 已报工数量＝同一任务产品、同一实际工作项的所有生效报工数量，按该工序自身单位跨员工、日期、生产线与工价版本累计；有效撤销的记录不计入。
- 本次合计＝本单该工作项所有员工行数量之和，排除同一共同产量的重复记录。
- 提交成功后，累计量增加本次合计；价格变更不重置已报数量，也不改变已生效记录的原单价。
- 同一工作项单位需要保持一致；不得通过变更版本把“根”换成“片”后直接相加。单位纠错如何处理需保留明确依据，不自动换算。

订单数量保留为来源信息，不能因名称相同就直接当成工序数量上限。当前尚未确认是否禁止超报，以及各工序上限取订单数量、独立填写数量还是其他来源；不默认无限报，也不把领料的“不超领”沿用为报工规则。

例如同一切管工作项已报 120 根，本次报 30 根，生效后累计为 150 根；无须折算成套。是否超过该工作项允许数量，需按后续确认的上限来源判断，不能凭此示例推定允许提交。

### 5.5 提交、纠错与历史

已确认：报工不需要审核。负责人提交并通过必要校验后直接生效，计入已报数量和金额；工价方案的厂长审批继续保留。

- 草稿 → 负责人提交后生效。草稿不计已报数量与金额，不设置待审核、审核通过、审核驳回等报工状态或操作。
- 生效记录建议只读。纠错通过留痕撤销并重新登记，保留原因、原记录和替代关系；谁有撤销权限、已结算记录能否撤销尚待确定。
- 重复点击和网络重试不应生成两份生效记录；同员工同日同工序存在两次实际做工则可以合法分开记录。
- 提交生效时，重新检查方案有效性、员工、计划、单位、价格和累计量，并按最终确定的数量上限规则处理。页面打开后价格已变更应提示刷新核对，不能偷偷换价保存。
- 生效时间建议与实际生产日期匹配，便于补录历史工作；具体按生产日期还是提交时间取价、可补录日期范围待确认。

### 5.6 工作项与员工行的识别（新增建议）

一个工作项表达“该生产任务产品、该车间、该工艺下，对某个部位做某道工序”。每个工作项使用稳定关联，不把名称文字、价格、员工或方案版本当作唯一依据。

- 椅面车缝和靠背车缝即使工序名称相同，也分别累计。
- 原有工作项改名称、改描述、调价，仍沿用原工作项；跨版本继续累计。
- 真正新增另一部位或另一道加工工作，才建立新工作项；不能通过复制同一行获取新的已报数量起点。
- 从另一订单引用历史工价，只引用内容；新订单的工作项和累计量独立，不继承旧订单产量。
- 相同员工、工序、日期可以多次合法报工；禁止的是同一提交重复入账，不是禁止员工一天做两次。
- 同一单据内同工作项、同员工、同生产线的重复行建议提示合并或核对；不同线不能直接合并，防止丢失线别信息。

工序基础资料改名或停用后，历史报工仍显示当时保存的名称、单位和单价；新报工如何使用停用前的历史工序，应与补录规则一起定稿。

### 5.7 提交与并发处理（新增建议）

报工不审核，但仍需在提交时校验。建议整张报工单一次成功或全部不生效，避免一部分员工入账、另一部分报错。

1. 检查实际录入人有该车间的报工权限；按员工身份保存，不能用名字猜关联。
2. 检查生产任务产品、计划、工艺、工作项匹配，工价经过厂长批准，明细单位与价格完整。
3. 至少一条员工明细，数量大于零，符合单位精度；装配行有 1线、2线、3线中的有效选择。
4. 按实际生产日期取价；已接单、生产中、已暂停、已完成、已取消任务允许补录，草稿和待校验任务不允许报工。
5. 同时有人报同一工作项时，按最新累计量检查；若最终选择数量上限，校验和累计必须一起完成，不能两张单都使用同一份旧余额。
6. 成功后返回同一张报工单及其结果；网络重试不重复增加数量和金额。失败不增加任何员工的正式工费，保留本次输入供修正。
7. 提交过程中工价、单位或适用规则发生变化，明确提示哪一项变化，重新核对后提交，不能保存时悄悄替换单价。

### 5.8 已生效报工纠错（已确认：直接编辑）

已保存报工允许具备修改权限的负责人直接编辑，不增加作废、修正草稿或重新审核流程。编辑保留原报工单号、原录入人和创建时间，增加修订号并记录最后修改人。

可编辑生产日期、员工、工序明细、装配线和数量，但不能更换原排产产品或车间。保存时按编辑后的生产日期重新匹配已批准工价，后端重算每行金额和整单金额；任一行不合法则整单回滚。修改请求必须携带 If-Match，旧页面提交返回冲突，避免两名负责人互相覆盖。

直接编辑会改变该报工单的有效数量和金额统计；普通工价版本更新仍不会自动改历史报工。当前系统没有工资结算或关账状态，因此本期没有“已结算后锁单”门禁，未来接入工资结算时必须重新定义锁定规则。

### 5.9 列表、详情与统计的落地口径（新增建议）

- 报工记录列表建议包含报工单号、生产日期、生产任务单、产品、车间、报工负责人、工序数量、金额、状态、提交时间；可按日期、订单产品、车间、员工、工序、状态筛选。
- “已报工数量”默认表示该工作项在所有生产日期的有效累计，不随列表日期筛选变成当期量；当期数量单独标为“本期报工数量”。
- 详情保留工价方案编号与版本，展开到员工行，显示原单、作废原因及修正单关联。
- 员工金额统计使用有效员工明细金额；单据总额仅汇总一次，不能每展开一个员工就重复计算整单金额。
- 数量按工作项、工序和单位分别展示，即使两道不同工序都使用“件”，也不能相加当作产品完工件数。
- 本期称“计件工费”，不称实发工资；不引入工资支付、扣款、考勤或计时功能。

### 5.10 生产状态与补录边界

| 边界 | 为什么要明确 | 本期定稿方向 |
| --- | --- | --- |
| 尚未领料 | 厂内生产可能领取原料或委外半成品，不能仅检查原材料领料数量 | 明确是否必须有该订单产品的有效领料记录；不按报工数反扣料、不推算配齐套数 |
| 任务暂停、取消或完成 | 当前不能开工与过去实际做过的工作不是同一件事 | 已确认允许历史补录，按填写的实际生产日期匹配批准工价；不代表允许恢复生产或改变任务状态 |
| 员工转车间或离职 | 今天不在该车间，不代表过去没有在该车间做工 | 当期按在职和所属车间选择；历史补录如需开放，应有当时归属依据与权限 |
