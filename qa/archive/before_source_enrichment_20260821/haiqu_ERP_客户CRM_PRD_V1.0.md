### 关键待确认项

以下信息未在原始需求中给出，不能当作既定公司制度。系统应先做成可配置项，实施前由业务负责人确认：

1. 客户编号规则、客户等级定义、销售团队层级与公海规则。
2. 公司标准销售流程、询盘与报价超时口径、样品流程归属。
3. 本位币、汇率来源、成本口径、毛利是否含运费/佣金/退税/赔偿。
4. 客户历史数据迁移范围，以及联系人、邮件、WhatsApp 等数据接入方式。
5. 信用额度审批人、账期定义、超额度和逾期下单政策。
6. 不同国家与客户类型的正常采购周期、季节性和客户流失确认规则。
7. 客户隐私、跨境数据、附件保存年限与删除政策。

### 产品经理先行判断

- 原需求把“线索、成交客户、沉睡、流失”混在一条生命周期中。实际应拆为：生命周期阶段、经营活跃度、信用风险三套独立状态，否则一个“已成交但逾期且暂时沉睡”的客户无法准确表达。
- “客户×产品关系”必须存在持久化汇总，但不能成为新的交易事实源。它应由询盘、报价、订单事件自动更新，并可重算。
- CRM 可以展示订单、应收和客诉数据，但订单履约、核销和完整售后流程应由未来专属模块负责，否则重复建设且账实不一致。
- 毛利和销售额必须保存订单时点的币种、汇率、成本快照；只用当前成本回算历史毛利会造成严重管理误判。

# 1. 项目背景

haiqu ERP 服务于户外用品外贸公司，主营行军床、折叠椅、扶手椅、户外桌椅、露营用品及其他户外家具。客户以海外 B2B 客户为主，包括进口商、批发商、经销商、连锁商超、电商、品牌客户和 OEM/ODM 客户。

系统采用模块化建设。第一阶段只建设客户 CRM，但数据模型必须为询盘、报价、产品、订单、财务、售后等未来模块预留稳定关联。CRM 不是通讯录，而是围绕“识别机会—持续跟进—促成成交—推动复购—控制风险—挽回流失”的客户经营工作台。

# 2. CRM 产品目标

## 2.1 核心目标

1. 建立唯一、可信、可追溯的客户主数据。
2. 让业务员每天清楚知道“今天跟进谁、为什么跟、下一步做什么”。
3. 在客户详情页一眼看懂客户价值、交易历史、机会、风险和待办。
4. 将客户、联系人、沟通、询盘、报价、订单、产品、信用和售后串成完整时间轴。
5. 用规则识别交叉销售机会、沉睡和流失风险，不依赖第一阶段的复杂 AI。
6. 为主管提供团队过程与结果视图，同时避免只用“沟通次数”制造无效内卷。

## 2.2 成功指标

| 指标 | 定义 | 建议目标（上线后 3 个月评估） |
|---|---|---|
| 客户主数据完整率 | 必填字段完整且通过格式校验的客户占比 | ≥ 95% |
| 疑似重复处理率 | 已处理疑似重复数 / 新增疑似重复数 | ≥ 90% |
| 有效客户跟进覆盖率 | 到期客户中按时完成有效跟进的占比 | ≥ 85% |
| 询盘首次响应及时率 | SLA 内完成首次有效处理的询盘占比 | 由公司配置目标 |
| 报价后跟进及时率 | 报价后在规则期限内完成跟进的占比 | ≥ 85% |
| 数据关联率 | 询盘、报价、订单可追溯到客户与联系人的占比 | ≥ 98% |
| 360° 页面使用率 | 活跃销售人员每周访问客户详情页的占比 | ≥ 80% |

> 指标目标是产品建议，不是公司既定 KPI。正式上线前必须结合历史基线确认，且不得单独以沟通数量评价业务员。

## 2.3 非目标

- 第一阶段不承担采购、库存、生产、完整订单履约和财务核算。
- 不承诺自动抓取所有邮件、WhatsApp 或微信聊天；无正式接口时只支持人工记录或合法导入。
- 不使用黑盒 AI 自动决定客户等级、信用和流失；系统只给出可解释建议，最终责任人可复核。

# 3. 用户角色

| 角色 | 核心任务 | 默认数据范围 | 特殊关注 |
|---|---|---|---|
| 业务员 | 建客户、维护联系人、处理询盘、报价后跟进、管理任务 | 本人负责及协同客户 | 快速录入、移动端、今日待办 |
| 协同业务员 | 在授权范围内协作跟进 | 被协同客户 | 权限与贡献留痕 |
| 销售主管 | 分配客户、查看团队机会和风险、督导跟进 | 本团队 | 过程质量、客户分布、人员负载 |
| 销售经理/总监 | 管理部门客户与业绩 | 销售部门 | 销售额、毛利、结构、流失风险 |
| 管理层 | 查看公司级经营视图 | 全公司汇总或明细授权 | 趋势、利润、风险与预测 |
| 财务/信用人员 | 维护或同步信用政策、查看应收风险 | 授权客户 | 信用额度、账期、逾期 |
| 售后人员 | 处理客诉并反馈进度 | 被分配客诉及相关客户 | 问题闭环、责任和赔偿 |
| 系统管理员 | 组织、角色、字典、自动化和审计配置 | 全部管理数据 | 不默认拥有成本等业务数据读取权 |
| 数据/实施人员 | 导入、清洗、校验、重算汇总 | 临时授权 | 数据质量、幂等、可回滚 |

# 4. CRM 信息架构

## 4.1 一级导航

1. **工作台**：我的待办、超时询盘、待跟进报价、风险客户、近期机会。
2. **客户**：客户列表、客户 360°、公海（若启用）、重复客户中心。
3. **联系人**：跨客户联系人检索、离职联系人、关键联系人缺失检查。
4. **询盘**：询盘列表、待处理队列、状态看板。
5. **报价**：报价历史、版本、待跟进报价、价格趋势。
6. **任务**：我的任务、团队任务、逾期任务、自动提醒。
7. **分析**：销售/毛利、客户结构、产品关系、流失与沉睡。
8. **客诉**：客诉只读或轻量登记入口，未来切换到售后模块。
9. **配置与审计**：字典、规则、权限、自动化、操作日志。

## 4.2 数据分层

- **主数据层**：客户、联系人、员工、组织、产品、地区、币种。
- **业务事实层**：沟通、询盘、报价及版本、订单快照、回款/应收快照、客诉、任务。
- **关系与汇总层**：客户×产品、客户年度销售、客户健康度、信用占用、仪表盘指标。
- **检索层**：面向高级筛选的搜索索引与分析宽表；索引不是事实源，可重建。
- **审计层**：字段变更、分配、合并、导入、自动化执行和权限访问日志。

# 5. 客户生命周期

## 5.1 三套状态模型

### A. 生命周期阶段（人工决策为主）

`线索 → 已验证 → 机会客户 → 成交客户 → 流失客户`

- 线索：仅有初步信息，尚未确认主体和有效需求。
- 已验证：客户主体、国家、至少一名有效联系人已确认。
- 机会客户：存在有效询盘、样品或明确采购计划。
- 成交客户：存在已确认的有效订单。
- 流失客户：经人工确认不再合作，或长期无交易且满足规则后由负责人确认。
- 已成交客户即使暂时沉睡，生命周期仍可保持“成交客户”；沉睡属于活跃度，不应覆盖成交事实。

### B. 经营活跃度（系统计算）

`活跃 / 待跟进 / 高流失风险 / 沉睡 / 暂无足够数据`

根据最近有效沟通、询盘、报价、订单、历史采购周期和季节性计算，允许责任人提出调整但必须填写原因。

### C. 信用风险（财务数据驱动）

`正常 / 接近额度 / 超额度 / 逾期 / 严重逾期 / 未评估`

由未来财务/应收模块提供，CRM 不自行修改应收事实。

## 5.2 生命周期状态变化

| 事件 | 建议变化 | 自动/人工 | 说明 |
|---|---|---|---|
| 新建最小客户档案 | 进入线索 | 自动 | 不要求首次录入全部资料 |
| 完成主体、国家、有效联系人验证 | 线索→已验证 | 人工确认，系统校验 | 防止脏数据自动晋级 |
| 创建有效询盘或明确商机 | 已验证→机会客户 | 自动建议，人工可确认 | 记录触发依据 |
| 首个订单生效 | →成交客户 | 自动 | 以订单模块“已确认/生效”为准 |
| 客户明确拒绝、主体注销或长期失联 | →流失客户 | 人工确认 | 必填流失原因与证据 |
| 流失后出现新有效询盘/订单 | →机会/成交客户 | 自动建议+人工确认 | 记录重新激活时间 |

# 6. 功能模块地图与统一规格模板

## 6.1 模块地图

| 领域 | 模块 | 第一阶段定位 |
|---|---|---|
| 客户主数据 | 客户档案、联系人、归属、去重合并 | CRM 主责 |
| 销售活动 | 沟通、时间轴、跟进任务、提醒 | CRM 主责 |
| 销售机会 | 询盘、报价历史与状态 | 询盘主责；报价可先做轻量或只读集成 |
| 交易分析 | 订单、销售额、毛利、客户×产品 | 读取事实、维护汇总 |
| 风险与服务 | 信用、应收、客诉、售后 | 只读/轻量关联，未来模块主责 |
| 管理能力 | Dashboard、搜索、权限、日志、自动化 | CRM 平台能力 |

## 6.2 所有功能的通用要求

后续每个模块均按“目的、角色、场景、字段、规则、状态、自动化、异常、权限、关系、验收”说明。通用规则如下：

- 所有业务对象使用不可变内部 ID；显示编号可以按规则生成，但不得作为外键。
- 删除默认采用逻辑删除；存在交易关系的客户不允许物理删除。
- 时间统一保存 UTC，界面按用户时区显示；同时保存业务发生日。
- 金额保存原币、原币金额、本位币金额、汇率、汇率日期和来源。
- 关键字段变更必须写审计日志；自动化动作要记录规则版本和执行结果。
- 附件应关联业务对象并进行病毒扫描、大小/类型限制和权限继承。

# 7. 客户档案

## 7.1 功能规格

**功能目的：** 建立唯一可信的客户主体，支撑所有后续业务关联。  
**使用角色：** 业务员、主管、管理员、实施人员。  
**使用场景：** 展会获客、网站询盘、转介绍、历史客户导入、客户主体信息补全。  
**状态变化：** 新建为线索；验证后进入已验证；由询盘/订单触发生命周期建议。  
**与其他模块关系：** 是联系人、询盘、报价、订单、信用、客诉、任务的主关联对象。

## 7.2 字段设计

| 字段 | 录入/来源 | 必填性 | 规则与说明 |
|---|---|---|---|
| 客户内部 ID | 系统生成 | 系统 | UUID/分布式 ID，不展示为业务编号 |
| 客户编号 | 系统生成 | 系统 | 按公司配置生成，创建后原则上不变 |
| 公司名称 | 人工/导入 | 必填 | 原始注册或常用公司名；去除首尾空格后校验 |
| 英文名称 | 人工/导入 | 条件必填 | 海外客户原则上必填；可与公司名称相同 |
| 客户简称 | 人工 | 选填 | 用于列表和内部称呼，不参与唯一判断 |
| 国家/地区 | 人工/识别建议 | 必填 | ISO 国家码；不允许自由文本 |
| 省/州、城市、地址、邮编 | 人工 | 选填 | 地址可保存多条，区分注册地址、账单、收货地址 |
| 官网 | 人工/识别 | 选填 | 规范化域名，用于去重 |
| 客户类型 | 人工 | 必填 | 进口商、批发商、经销商、零售、商超、电商、品牌、OEM/ODM 等可配置多选 |
| 来源渠道 | 人工/系统 | 必填 | 展会、官网、平台、开发信、转介绍等；保存首次来源和最近来源 |
| 客户等级 | 人工审批/规则建议 | 选填 | 建议 A/B/C/D；规则可配置，变更需留痕 |
| 生命周期阶段 | 系统建议+人工 | 必填 | 见第 5 章；禁止把信用或沉睡塞入该字段 |
| 经营活跃度 | 系统计算 | 统计 | 活跃、待跟进、高风险、沉睡、数据不足 |
| 客户标签 | 人工/规则 | 选填 | 标签带创建人、来源和有效期，防止无限堆积 |
| 主要市场、销售渠道 | 人工 | 选填 | 多选字典；反映客户经营市场与渠道 |
| 公司规模、年采购规模 | 人工估计 | 选填 | 保存区间、币种、来源、估计日期，不要求伪精确值 |
| 主营业务 | 人工 | 选填 | 简短结构化标签+补充说明 |
| 主要采购产品 | 统计 | 统计 | 来自客户×产品关系，禁止重复手填 |
| 潜在采购产品 | 规则建议+人工确认 | 统计/选填 | 来自推荐结果，人工可标记重点或不感兴趣 |
| 首次联系时间 | 沟通记录统计 | 统计 | 最早有效沟通时间 |
| 建档时间 | 系统生成 | 系统 | 创建时间，不可手改 |
| 首次成交时间 | 订单统计 | 统计 | 首个生效订单日期 |
| 最近成交时间 | 订单统计 | 统计 | 最近生效订单日期 |
| 最近跟进时间 | 沟通统计 | 统计 | 最近一次有效沟通，不含纯系统提醒 |
| 主负责人 | 分配 | 必填 | 一个当前主负责人；历史另表保存 |
| 协同业务员 | 分配 | 选填 | 多人，可设置有效期和权限范围 |
| 所属团队 | 组织/负责人 | 系统建议 | 默认随负责人，可配置跨团队归属 |
| 创建人 | 系统 | 系统 | 不随客户转移变化 |
| 备注 | 人工 | 选填 | 不得存放密码、卡号等敏感秘密 |

## 7.3 业务与自动化规则

1. 支持“快速建档”：公司名、国家、来源、负责人四项即可创建线索；其他字段通过任务逐步补全。
2. 创建前实时进行重复检测；高相似度时提示选择已有客户或提交主管确认。
3. 国家、客户类型、来源等采用字典；字典停用不影响历史数据。
4. 系统根据订单与沟通自动维护首次/最近时间、累计指标和经营活跃度。
5. 客户等级变更、负责人转移、合并、删除恢复必须记录原因。

## 7.4 异常、权限与验收

- **异常：** 同名不同国家允许存在；同集团不同法人可分别建档并关联集团；网站缺失不阻止创建；导入冲突进入待处理队列。
- **权限：** 业务员编辑本人客户；主管可按数据范围编辑；成本、毛利、信用等字段不在客户基础编辑权限内。
- **验收：** 可在 30 秒内完成最小建档；必填和格式校验有效；系统统计字段不可手改；所有关键变更可在日志中追溯。

# 8. 联系人管理

## 8.1 功能规格

**目的：** 表达一个客户内采购、决策、产品、财务、物流等多角色联系人，并保存任职历史。  
**角色与场景：** 业务员建档和跟进；财务查找付款联系人；售后联系质量或物流负责人。  
**关系：** 联系人必须属于一个客户；沟通、询盘、报价可关联具体联系人。

## 8.2 核心字段

| 字段组 | 字段 | 规则 |
|---|---|---|
| 身份 | 姓名、英文姓名、职位、部门 | 姓名或英文姓名至少一项必填 |
| 联系方式 | 邮箱、电话、手机、WhatsApp、微信、LinkedIn、其他账号 | 至少一个有效联系方式；支持多值与主联系方式 |
| 业务角色 | 决策人、采购负责人、财务联系人、收货联系人、产品经理、老板 | 多选；“关键联系人”是经营判断，不等同于决策人 |
| 状态 | 在职、离职、未知；有效/退订/不可联系 | 离职后不删除历史记录，不再作为默认收件人 |
| 偏好 | 语言、时区、首选渠道、可联系时段 | 用于提醒与沟通体验 |
| 合规 | 营销同意、退订时间、来源 | 按适用法律和公司政策配置 |
| 审计 | 创建人、创建时间、更新时间、备注 | 系统字段自动生成 |

## 8.3 规则、自动化与异常

- 同一客户下邮箱或手机号重复时提示；跨客户同邮箱域名只提示，不自动合并。
- 关键联系人离职后自动生成“补充关键联系人”任务。
- 联系人被标记离职时，未完成任务与未来提醒仍保留，但提示更换联系人。
- 允许联系人在集团关联客户间转任，通过“任职记录”保留旧关系，禁止简单改写导致历史沟通错位。
- 权限继承客户数据范围；个人手机号等敏感字段可单独控制导出权限。
- 验收：一个客户可维护多个联系人及角色；离职不丢历史；沟通/询盘/报价能定位联系人；重复提示可解释。

# 9. 客户沟通记录

## 9.1 功能规格

**目的：** 保存能影响销售判断的有效沟通，而不是堆积无意义打卡。  
**角色：** 业务员、协同人员、主管；其他角色按权限查看。  
**场景：** 电话、邮件、WhatsApp、微信、视频会议、面谈、展会、拜访及其他渠道。

## 9.2 核心字段与规则

| 字段 | 要求 |
|---|---|
| 沟通时间、方式 | 必填；允许补录但记录实际录入时间 |
| 客户、联系人 | 客户必填；联系人可空但需说明“未识别联系人” |
| 沟通人员 | 系统默认当前用户，可添加内部参与者 |
| 主题、内容摘要 | 主题必填；内容应支持结构化摘要和全文附件 |
| 客户反馈 | 选填；建议用意向、顾虑、决策、竞品等标签辅助 |
| 下一步动作、下次跟进时间 | 若沟通结果需要后续动作则条件必填 |
| 关联对象 | 可关联询盘、报价、订单、样品、客诉，允许多选但须同一客户 |
| 附件 | 权限继承、病毒扫描、版本和下载日志 |
| 有效沟通标记 | 系统规则+人工确认；纯群发、发送失败不算有效沟通 |

## 9.3 自动化、异常、权限与验收

- 保存“下一步动作+日期”时自动创建跟进任务；修改沟通记录同步更新未完成任务，完成任务不反向篡改历史沟通。
- 邮件或消息接入时按消息唯一 ID 去重；发送失败标记失败，不更新最近有效沟通时间。
- 允许补录离线展会/拜访，但超过配置天数补录需注明原因。
- 沟通内容默认仅客户数据范围内可见；含成本或信用附件时按更高字段权限控制。
- 验收：记录可在客户时间轴实时看到；关联对象可跳转；失败消息不计入跟进；自动任务不重复创建。

# 10. 客户时间轴 Timeline

## 10.1 功能规格

**目的：** 用一条可筛选的事件流还原客户从建档到交易、回款、客诉和复购的历史。  
**使用角色：** 所有拥有客户查看权的角色。  
**核心事件：** 建档、联系人变化、沟通、询盘、报价、样品、订单、发货、回款、信用变化、客诉、售后、任务、客户转移、合并。

## 10.2 业务规则

1. 时间轴事件采用统一事件模型：事件 ID、客户 ID、事件类型、发生时间、创建时间、发起人、摘要、来源模块、来源对象 ID、可见级别。
2. 业务发生时间与系统记录时间同时保留；补录记录显示“补录”标识。
3. 时间轴只展示摘要，点击后查看源对象；不得把时间轴副本当作事实源。
4. 支持按事件类型、时间、联系人、产品、负责人筛选，默认倒序并分页加载。
5. 自动事件可折叠，人工沟通和风险事件优先显示。

## 10.3 异常、权限与验收

- 源对象逻辑删除时，时间轴保留“已删除/已合并”占位和审计入口。
- 不同权限角色看到的摘要需脱敏，例如无毛利权限者不能从事件摘要推断毛利。
- 百万级事件下使用游标分页和独立事件索引，不允许每次打开页面跨十多个业务表实时拼接。
- 验收：关键业务事件完整、有来源跳转、权限一致；筛选响应在约定性能指标内。

# 11. 客户询盘

## 11.1 功能规格

**目的：** 将客户需求结构化，推动分析、报价、跟进和转订单。  
**角色：** 业务员、报价人员、主管。  
**场景：** 单产品、多产品、图片找款、定制/OEM、补货、展会询价。  
**关系：** 询盘头关联客户、联系人、负责人；询盘行关联产品/SKU，未知产品可用临时需求项并待匹配。

## 11.2 核心字段

| 层级 | 字段 | 规则 |
|---|---|---|
| 询盘头 | 询盘 ID、编号、客户、联系人、业务员、来源、询盘时间、状态 | 编号系统生成；客户必填；联系人可后补 |
| 需求行 | 产品、SKU、图片、数量、单位、目标价、币种 | 可多行；产品未知时保存客户原始描述 |
| 技术要求 | 规格、材质、颜色、包装、认证、特殊要求 | 结构化属性+原文，避免只存备注 |
| 贸易要求 | 交期、目的港、贸易条款、付款偏好 | 贸易条款需保存 Incoterms 版本与地点 |
| 管理字段 | 优先级、首次响应时间、负责人、丢单原因、附件 | 首次响应由有效处理动作统计 |

## 11.3 询盘状态机

`新询盘 → 分析中 → 待报价 → 报价中 → 已报价 → 跟进中 → 已转订单 / 丢单 / 已关闭`

| 当前状态 | 进入条件 | 自动变化 | 允许回退/例外 |
|---|---|---|---|
| 新询盘 | 新建或渠道导入 | 首次领取并填写处理动作→分析中 | 重复/垃圾可关闭 |
| 分析中 | 正在澄清需求或产品匹配 | 需求完整且需报价→待报价 | 信息不足保持并设任务 |
| 待报价 | 已具备报价条件 | 创建报价草稿→报价中 | 客户取消→关闭 |
| 报价中 | 存在草稿报价 | 首个报价版本正式发送→已报价 | 草稿作废→待报价 |
| 已报价 | 已发送有效报价 | 建立跟进动作→跟进中 | 新版本发送仍保持或回到已报价 |
| 跟进中 | 报价后持续沟通 | 订单行引用询盘→已转订单 | 明确失败→丢单；无效需求→关闭 |
| 已转订单 | 订单生效 | 终态 | 订单取消不自动回退，生成复核提示 |
| 丢单 | 明确竞争失败 | 终态，可重新开启为新机会 | 必填原因、竞品/价格等 |
| 已关闭 | 重复、垃圾、取消、无法处理 | 终态，可主管重开 | 必填关闭原因 |

## 11.4 自动化、异常、权限与验收

- 新询盘创建后按来源、国家、产品线、客户归属自动分配；分配失败进入待分配队列。
- 超过首次响应 SLA、分析 SLA 或报价 SLA 自动提醒并升级主管；SLA 按工作日、时区和优先级配置。
- 同一询盘允许多次报价；不能因创建草稿就标记“已报价”。只有正式发送的版本才触发。
- 一个订单可引用多个询盘，一条询盘也可部分转订单；状态按“至少一条有效订单关联”并结合未完需求判断。
- 验收：多行需求、图片找款、未知 SKU、部分转单、丢单原因、SLA 和状态自动变化均可验证。

# 12. 客户历史报价

## 12.1 功能规格

**目的：** 保存每次对外报价的完整版本和成本依据，为再次报价、成交分析和价格趋势提供可信历史。  
**角色：** 业务员、报价人员、主管；成本和毛利受独立权限控制。  
**关系：** 报价关联客户、联系人、询盘；报价行关联产品/SKU；成交后关联订单行。

## 12.2 核心字段与版本规则

| 字段组 | 字段 | 规则 |
|---|---|---|
| 报价头 | 报价编号、日期、客户、联系人、币种、贸易条款、地点、有效期、状态 | 编号系统生成；Incoterms 必须带版本/地点 |
| 报价行 | 产品、SKU、数量阶梯、单价、MOQ、包装、运费/附加费 | 支持一个产品多个数量阶梯 |
| 成本快照 | 材料/采购成本、包装、运费、佣金、其他成本、汇率 | 保存报价时点快照与口径版本 |
| 利润 | 单位毛利、总毛利、毛利率 | 系统计算；计算公式按公司配置 |
| 版本 | 版本号、父版本、创建人、变更说明、发送时间 | 正式发送后不可直接改，必须新建版本 |
| 结果 | 报价状态、失效原因、是否成交、对应订单/订单行 | 是否成交由订单关联统计，不手填 |

## 12.3 报价状态

`草稿 → 待审批（可选）→ 已批准 → 已发送 → 客户反馈中 → 已接受 / 已拒绝 / 已过期 / 已撤回`

- 草稿可编辑；提交审批后锁定关键金额字段。
- 已发送版本不可覆盖，修改必须复制为新版本。
- 有效期到达且未接受时自动转“已过期”；若已关联有效订单则转“已接受”。
- 撤回必须记录原因，并明确是否已通知客户。

## 12.4 历史价格趋势

价格趋势的比较口径必须可比，默认维度为：`客户 + SKU + 币种 + 贸易条款 + 目的地/地点 + 数量区间 + 包装口径`。不能只按“客户+产品”直接画线，否则 FOB 与 CIF、不同数量和包装的价格会产生误导。

趋势展示原币报价、折算本位币报价、成交价、数量、版本、有效期和毛利率，并允许切换“只看正式发送”“只看成交”。

## 12.5 自动化、异常、权限与验收

- 报价发送后自动生成跟进任务；客户回复或产生新版本可调整提醒。
- 汇率缺失、成本过期、毛利低于阈值时阻止发送或触发审批，策略可配置。
- 无成本权限者只看对外价格；无毛利权限者不得通过导出或接口获得成本反推字段。
- 验收：版本不可覆盖；历史趋势口径可筛选；过期、成交、审批与权限规则正确；报价可追溯到询盘和订单行。

# 13. 客户历史订单数据

## 13.1 功能规格

**目的：** 在 CRM 内提供客户交易全貌，不复制订单履约流程。  
**角色：** 业务员、主管、管理层；金额、毛利按字段权限控制。  
**数据来源：** 未来订单模块的订单头、订单行和状态事件；第一阶段可通过历史导入形成只读订单快照。

## 13.2 展示指标

| 指标 | 统计口径 |
|---|---|
| 历史订单数 | 按有效订单去重；取消/作废默认排除，可切换查看 |
| 历史订单金额 | 原币与本位币均保留；默认按订单确认日及当时汇率 |
| 历史销量 | 按 SKU 基础单位换算；无法换算的单位分开展示 |
| 历史毛利/毛利率 | 使用订单成本快照和公司配置公式，不用当前成本回算 |
| 产品分布 | 产品分类、SKU、销量、销售额、毛利贡献 |
| 年度销售趋势 | 按公司财年或自然年配置；可选 1 年、3 年、全部 |
| 最近/最大订单 | 最近按订单确认日；最大按本位币订单金额 |
| 最近购买产品 | 最近有效订单行，显示 SKU、数量、价格和日期 |

## 13.3 业务规则与异常

1. 订单归属保存订单时点业务员、团队和客户 ID 快照；客户后来转移不改变历史订单归属。
2. 退款、取消、补单、赔偿、信用单必须有明确统计口径，不能简单覆盖原订单。
3. 同一订单多币种原则上禁止；若存在，订单行分别折算并标记特殊数据。
4. 订单模块延迟或失败时显示“数据更新时间”和“可能不完整”，禁止静默展示旧数。
5. 指标支持过去 12 个月、过去 3 年、全部历史，并显示时间区间和时区。

## 13.4 权限、关系与验收

- 无毛利权限时隐藏成本、毛利和可反推毛利的导出字段；管理层汇总权限不自动等于明细客户权限。
- 订单行关联客户×产品关系、报价行、询盘行和客诉。
- 验收：能回答“过去 3 年买了什么、数量多少、金额多少、毛利多少”；客户转移不改变历史归属；取消订单不计有效销售。

# 14. 客户×产品关系

## 14.1 设计定位

**目的：** 将客户对每个产品的交易、兴趣、偏好与机会形成可搜索、可解释的关系模型，回答“这个客户还可以卖什么”。  
**关键原则：** 关系表是自动汇总和经营标注的结合体，交易统计可重算；订单仍是成交事实源。

## 14.2 数据模型

主键建议为 `customer_id + product_id`，必要时增加规格维度；主要字段如下：

| 字段组 | 字段 | 来源 |
|---|---|---|
| 购买事实 | 是否购买、首次/最近购买时间、累计销量、累计销售额、累计毛利、订单数 | 订单汇总 |
| 价格事实 | 最近成交价、加权平均成交价、最近报价、最低/最高成交价、币种与贸易口径 | 订单/报价汇总 |
| 兴趣事实 | 首次/最近询盘、询盘次数、报价次数、样品次数 | 询盘/报价/样品事件 |
| 经营标记 | 重点产品、潜在产品、不感兴趣、不感兴趣原因、偏好说明 | 人工，可审计 |
| 推荐结果 | 推荐分、推荐等级、推荐原因、规则版本、生成时间 | 规则引擎 |
| 数据维护 | 最近重算时间、数据版本、异常标记 | 系统 |

“当前报价”不能脱离版本与有效期保存为裸字段。页面应显示最近一个仍有效的正式报价；不存在时显示最近历史报价并标记已过期。

## 14.3 第一阶段交叉销售规则

对客户未购买且未标记“不感兴趣”的产品计算推荐分。示例权重可配置：

1. 历史询盘/报价过但未购买：+35。
2. 同客户类型购买率高：最高 +20。
3. 同国家或区域购买率高：最高 +15。
4. 与已购产品为关联/配套产品：+20。
5. 所属分类为公司近 12 个月热销：+10。
6. 与客户主营渠道、认证或价格带匹配：+10。
7. 最近被客户明确拒绝：-50；永久不感兴趣：排除。
8. 无库存/停产/认证不满足：排除或强提示，不直接推荐。

最终分数归一化为 0–100，按分值取 TOP 5/10。每条必须展示 1–3 个可读原因，例如“您所在德国市场的同类商超客户中有 42% 购买该系列；该产品与已购折叠椅属于配套组合”。不得只显示“系统推荐”。

## 14.4 自动化、异常、权限与验收

- 询盘、报价、订单生效或取消后通过事件增量更新；每日进行差异校验，支持全量重算。
- 产品合并、SKU 替换或分类调整时重新归并，保留原产品映射。
- 样本少于设定数量时不使用“同类客户购买率”，改用热销/关联产品并提示样本不足。
- 不感兴趣标记需保存原因、记录人、日期和复核日期，防止永久屏蔽过时判断。
- 验收：订单改变后关系数据正确更新；推荐可解释、可排除；高级搜索可直接按是否购买/未购买筛选。

# 15. 销售与毛利分析

## 15.1 功能规格

**目的：** 从客户、产品、国家、渠道、业务员等维度分析销售质量，而不只看销售额。  
**角色：** 业务员查看本人范围；主管看团队；管理层看授权范围；毛利和成本单独授权。

## 15.2 指标口径

| 指标 | 推荐定义 |
|---|---|
| 销售额 | 有效订单确认金额；是否含税、运费按公司配置并显示口径 |
| 毛利 | 销售净额 - 订单成本快照 - 计入毛利的费用；具体费用清单版本化 |
| 毛利率 | 毛利 / 销售净额；分母为 0 时显示不适用，不显示 0% |
| 平均订单金额 | 有效订单销售额 / 有效订单数 |
| 客户贡献度 | 客户销售额或毛利 / 当前数据范围内总额 |
| 复购率 | 在观察窗口内达到第二次有效订单的成交客户占比 |
| 产品渗透率 | 购买该产品的目标客户数 / 目标客户总数 |

## 15.3 规则与验收

- 每张图表必须展示时间范围、币种、本位币、时区、订单状态和数据更新时间。
- 业务员绩效既可按订单时点归属，也可按当前客户归属查看，两种口径必须明确命名，默认采用订单时点归属。
- 订单成本未完成时毛利显示“待核算”，不能当作 0。
- 验收：同一筛选条件下列表合计与图表一致；原币和本位币可追溯；无权限者无法从接口/导出获取毛利。

# 16. 信用额度与账期

## 16.1 功能规格

**目的：** 在销售跟进和下单前展示信用与回款风险。CRM 第一阶段原则上只读，信用审批与应收事实由未来财务模块负责。  
**角色：** 财务/信用人员、授权销售、主管、管理层。

## 16.2 核心字段

| 字段 | 来源与规则 |
|---|---|
| 信用额度、币种 | 财务/信用模块；保存批准额度和生效区间 |
| 已使用额度 | 未结应收 + 已确认未开票/未收款占用，具体公式可配置 |
| 剩余额度 | 信用额度 - 已使用额度；系统计算 |
| 账期 | 例如发票日后 30 天、提单日后 60 天；必须包含起算事件和天数 |
| 付款方式 | TT、LC、OA 等字典，可多方案但有当前有效方案 |
| 信用等级 | 财务评定；保存模型/人工、日期、评定人 |
| 超额度/逾期下单策略 | 财务审批策略，只读展示 |
| 当前应收、逾期金额、最大逾期天数 | 财务实时或准实时汇总 |
| 数据更新时间 | 必须展示；超出时效阈值时警告 |

## 16.3 规则、异常、权限与验收

- 信用占用按原币和集团/法人维度处理；多币种统一折算时保存汇率来源。
- 超额度或严重逾期只产生风险提示/审批要求，CRM 不直接替订单模块决定能否下单。
- 财务接口不可用时显示最后更新时间和“不可作为最新授信依据”。
- 信用额度变更、临时额度、超限审批必须全量审计。
- 验收：剩余额度计算正确；账期含起算点；数据过期有警告；无信用权限者不见金额明细。

# 17. 客诉与售后

## 17.1 功能规格

**目的：** 让销售在客户 360° 中看见影响关系和复购的质量问题，并推动责任闭环。第一阶段可轻量登记，未来由售后模块主责。  
**角色：** 业务员、售后、质量、主管、授权管理层。

## 17.2 核心字段

| 字段组 | 字段 |
|---|---|
| 识别 | 客诉 ID/编号、客户、联系人、订单/订单行、产品、SKU |
| 问题 | 类型、描述、图片/视频、问题数量、严重程度、发现时间 |
| 金额 | 客诉金额、赔偿金额、补货数量、币种 |
| 处理 | 初步原因、根因、处理方案、责任部门、责任人、期限 |
| 结果 | 客户满意度、完成时间、复发标记、状态 |
| 审计 | 创建人、更新时间、状态历史、附件下载日志 |

## 17.3 状态与规则

`新建 → 已受理 → 调查中 → 方案待确认 → 执行中 → 待客户确认 → 已关闭`，另有`已驳回/已取消`。

- 严重程度建议分为一般、重要、严重、重大；重大客诉即时通知主管和管理层授权角色。
- 关闭必须具备根因、处理结果、责任归属、客户确认或无法确认说明。
- 客诉率必须明确分母：可按问题数量/出货数量或客诉订单数/出货订单数，页面显示口径。
- 客诉赔偿影响毛利时，订单或财务模块以调整单入账；CRM 不直接改历史订单毛利。

## 17.4 异常、权限与验收

- 无订单的售前质量反馈允许建档，但不能计入订单客诉率。
- 视频过大时使用对象存储与受控链接；删除附件需审计。
- 根因和责任可能敏感，销售可看客户沟通结果，内部责任按角色控制。
- 验收：可统计历史客诉次数、主要类型、客诉率和累计赔偿；重大客诉有升级；关闭条件有效。

# 18. 跟进任务和提醒

## 18.1 功能规格

**目的：** 把下一步行动变成可执行待办，避免“有记录、无动作”。  
**角色：** 业务员、协同人员、主管、自动化系统。  
**来源：** 人工、沟通记录、报价、样品、长期无联系、采购周期、客诉、应收逾期。

## 18.2 核心字段与状态

字段包括任务类型、客户、联系人、关联对象、标题、内容、原因、负责人、协同人、计划完成时间、提醒时间、优先级、状态、完成结果、创建来源和规则版本。

状态：`待处理 → 进行中 → 已完成`；辅状态包括`已逾期、已取消、已忽略、等待客户`。已忽略必须填写原因，等待客户需要下次检查日期。

## 18.3 自动提醒规则（默认建议，可配置）

| 触发源 | 默认规则 | 去重/停止条件 |
|---|---|---|
| 新询盘 | 创建后按优先级在 SLA 前提醒 | 首次有效处理后停止 |
| 报价发送 | 2 个工作日后提醒首次跟进 | 客户已回复、已成交或报价撤回 |
| 样品寄出 | 预计签收日+1 天确认收货，签收后 3 天收反馈 | 已收到反馈或样品取消 |
| 长期未联系 | 超过客户沟通节奏或分层阈值 | 有新有效沟通 |
| 临近采购周期 | 预计采购日前 14/7 天提醒 | 新订单或负责人调整日期 |
| 客诉 | 临近处理时限、超时、重大客诉即时升级 | 客诉关闭 |
| 应收逾期 | 逾期 1/7/15/30 天分级提醒 | 已核销或财务豁免 |

## 18.4 规则、异常、权限与验收

- 同一客户、同一来源对象、同一规则周期只创建一条活动任务，避免提醒风暴。
- 负责人休假、离职或转岗时任务进入重新分配队列；客户转移时未完成任务按配置转移或保留。
- 自动任务允许用户改期，但必须记录原因；连续改期达到阈值提示主管。
- 验收：今日、未来、逾期清晰；规则不重复创建；完成结果可回写关联对象；超时升级可验证。

# 19. 沉睡客户识别

## 19.1 设计目标

沉睡不使用统一固定 90 天，而根据客户自身采购周期、客户分层、季节性和近期互动判断。第一阶段使用可解释规则，不使用机器学习。

## 19.2 采购周期算法

当客户有至少 3 个有效订单、至少 2 个采购间隔时：

1. 取最近 24 个月最多 8 个有效订单间隔天数。
2. 使用中位数作为基础采购周期，降低异常大单或漏单影响。
3. 若间隔波动很大，记录稳定性为低，并降低自动判断置信度。
4. 计算 `周期比 = 距最近订单天数 / 基础采购周期`。
5. 户外用品存在季节性时，用客户过去下单月份窗口修正预计日期；第一阶段可由业务员配置旺季月份。

建议阈值：

| 状态 | 周期比 | 附加条件 |
|---|---|---|
| 活跃 | < 0.8 | 或近期存在有效询盘/报价/沟通 |
| 待跟进 | 0.8–1.2 | 接近常规采购时间 |
| 高流失风险 | 1.2–1.8 | 且无近期有效机会 |
| 沉睡 | 1.8–3.0 | 且无有效询盘/报价/沟通缓解信号 |
| 建议确认流失 | ≥ 3.0 | 满足最低静默天数后由人工确认 |

例：平均约 60 天采购一次，90 天未下单，周期比为 1.5，应进入高流失风险，而不是等固定 180 天。

## 19.3 数据不足与异常

- 少于 3 个订单：使用“国家+客户类型+等级”分群默认周期；分群样本不足时使用公司配置阈值，并标记低置信度。
- 项目型、一次性客户或年度招标客户：允许设置采购模式和人工预计采购日，不能套用普通周期。
- 大促备货、疫情/战争/港口异常等外部事件可能造成周期失真，允许设置异常事件窗口。
- 订单取消不计周期；样品单、赠品单是否计入由订单类型配置。

## 19.4 权限与验收

- 系统每天批量重算；结果保存规则版本、输入时间点、置信度和触发原因。
- 业务员可提出延期/误报反馈，主管可审批规则例外；任何手动覆盖必须有到期日。
- 验收：能用历史周期识别 60→90 天示例；数据不足明确标记；季节性/一次性客户可豁免；可解释计算过程。

# 20. 流失预警与重新激活

## 20.1 风险评分

第一阶段建议采用 100 分可解释风险分，分值越高风险越大：

- 采购周期超期：0–45 分。
- 有效沟通超期：0–15 分。
- 报价多次无回复或连续丢单：0–10 分。
- 销售额/毛利较过去同期明显下降：0–10 分。
- 客诉未闭环或满意度低：0–10 分。
- 逾期应收/信用受限：0–10 分。
- 新询盘、有效回复、近期订单可抵扣风险分。

阈值建议：0–29 正常，30–49 关注，50–69 高风险，70–100 建议重点挽回。阈值必须用历史数据回测后调整。

## 20.2 业务规则

- 风险分不自动把客户改为“已流失”；已流失需要明确业务判断和原因。
- 预警必须展示贡献因素、最近变化和建议动作，例如“已超过常规采购周期 47%，且最近 60 天无有效沟通”。
- 重新出现有效询盘、客户回复或订单后自动降低风险并生成“重新激活”事件。
- 重新激活活动记录方案、负责人、触达渠道、结果和下一步，便于评估挽回策略。

## 20.3 验收

同一客户风险分可追溯；业务员知道为什么预警；有缓解事件后分值变化；已流失确认和重新激活完整留痕。

# 21. 客户归属

## 21.1 功能规格

**目的：** 管理客户当前负责人、协作关系和完整转移历史，同时保证历史交易归属不被改写。  
**角色：** 主管、经理、管理员；业务员可发起申请但不一定可直接转移。

## 21.2 数据模型与规则

1. 当前主负责人唯一；协同人员可多名，均有角色、权限范围、生效/失效时间。
2. 分配记录保存客户、原负责人、新负责人、原/新团队、原因、发起人、审批人、生效时间、任务处理策略。
3. 客户转移只改变未来默认负责人；历史订单、报价、沟通保存发生时点人员快照。
4. 转移时必须处理未完成询盘、报价、任务、客诉和临时授权，系统展示影响清单后确认。
5. 批量转移设置数量阈值和二次确认，生成批次 ID 与结果报告。

## 21.3 异常、权限与验收

- 新负责人离职/停用时不允许生效；跨部门转移按审批流配置。
- 订单历史归属不可随客户转移；管理报表允许在“历史归属/当前归属”间切换并明确口径。
- 验收：A→B→C 历史完整；转移影响项可控；无权限人员不能绕过审批；历史订单业务员不变。

# 22. 客户重复检测与合并

## 22.1 重复检测

**目的：** 在不误合并不同法人的前提下，减少重复客户和数据割裂。  
**识别时点：** 新建实时、导入批处理、定期扫描、客户关键字段变更后。

建议采用可解释加权分：

| 特征 | 示例权重 | 说明 |
|---|---:|---|
| 官网/邮箱主域名完全相同 | 35 | 公共邮箱域名不计 |
| 规范化公司英文名高度相似 | 25 | 去公司后缀、标点、大小写后比较 |
| 电话规范化后相同 | 20 | 含国家码处理 |
| 国家相同 | 8 | 只作辅助，不能单独判断 |
| 地址高度相似 | 12 | 同一园区可能误报 |
| 税号/注册号相同（未来） | 60 | 强证据；不同则强烈反对合并 |

分值阈值例如：≥70 高疑似，50–69 中疑似，低于 50 仅在后台观察。阈值需根据真实数据校准。

## 22.2 合并规则

1. 合并前选择主客户，并逐字段确认保留值；空值可补齐，冲突值不能静默覆盖。
2. 联系人、沟通、询盘、报价、订单、任务、附件、客诉全部重新指向主客户，同时保存原客户 ID。
3. 被合并客户进入“已合并”只读状态，保留别名、原编号和跳转关系，不物理删除。
4. 客户×产品和统计指标合并后全量重算，不能简单相加导致重复订单。
5. 合并属于高风险操作，需主管权限、二次确认、审计批次和可在限定期内由管理员回滚。

## 22.3 异常、权限与验收

- 同集团不同法人、同名不同国家、共享邮箱域名等只能建立集团关系，不能强制合并。
- 存在不同信用主体或不同开票主体时必须阻止自动合并并交财务复核。
- 验收：实时提醒可用；合并不丢任何关联记录；冲突值人工确认；主/从客户和回滚过程可追溯。

# 23. CRM Dashboard

## 23.1 业务员首页

页面顺序围绕行动而非装饰性统计：

- 默认查询预聚合数据，显示最近更新时间；关键卡片支持刷新但有频率限制。
- 主管只能看到本团队；管理层汇总权限与明细权限分离。
- 验收：业务员能在首页完成主要日常动作；主管能定位异常人员/客户；所有指标口径可查看。

# 24. 客户 360° 详情页

## 24.1 页面目标与布局

目标是“一眼看懂客户”，首屏不堆满所有字段。推荐布局：

### 固定页头

公司名称、国家/地区、客户等级、生命周期阶段、经营活跃度、信用风险、主负责人、协同人员；右侧提供记录沟通、建任务、新建询盘、新建报价、发起转移等快捷动作。

### 首屏摘要

- 最近联系、最近询盘、最近报价、最近订单及距今天数。
- 下一次跟进、未完成询盘/报价/任务、未关闭客诉。
- 累计销售额、过去 12 个月销售额、过去 3 年销售额、累计毛利、毛利率。
- 历史订单数、累计销量、平均订单金额、当前应收、逾期金额。
- 高优先级风险和推荐动作置顶展示；无权限指标显示“无权限”，而不是误显示 0。

### 标签页

`概览 | 时间轴 | 联系人 | 询盘 | 报价 | 订单 | 产品分析 | 销售趋势 | 信用 | 客诉 | 任务 | 附件 | 操作记录`

## 24.2 交互规则

1. 默认打开概览并记忆用户最近标签；移动端优先显示摘要、联系人和任务。
2. 每个 KPI 可点击查看组成明细和口径；不能只显示不可解释数字。
3. 时间范围统一控制订单、趋势和产品分析；时间轴使用独立筛选。
4. 风险提示包含原因、影响和建议动作，可创建任务或反馈误报。
5. 页面区块按权限动态隐藏，但布局不留下误导性空白。

## 24.3 异常、性能与验收

- 数据接口局部失败时单区块降级并显示重试，不让整页白屏。
- 首屏核心数据使用客户汇总快照，明细标签按需加载；目标 P95 首屏响应不高于 2 秒（在约定基础设施和数据量下）。
- 验收：首屏能回答客户是谁、负责人、最近互动、价值、风险和下一步；任一 KPI 可追溯；局部失败可用。

# 25. 搜索与高级筛选

## 25.1 功能规格

**目的：** 支持业务员处理几十至几百客户，也支持管理层在几十万客户和百万订单规模下组合筛选。  
**场景：** 查找“德国、过去 12 个月销售额 > USD 100,000、最近 60 天无订单、买过折叠椅但未买行军床”的客户。

## 25.2 筛选能力

- 基础：公司名、编号、国家/地区、负责人、团队、等级、来源、类型、标签、生命周期、活跃度。
- 交易：最近订单日、订单数、销售额、毛利、平均订单金额、币种与时间窗口。
- 产品：买过/未买过某产品或分类、询盘过未购买、最近购买时间、累计销量。
- 活动：最后有效跟进、下次跟进、逾期任务、未完成询盘/报价。
- 风险：信用等级、额度占用、逾期金额、沉睡、流失风险、客诉严重度。
- 逻辑：支持 AND/OR 分组、包含/不包含、范围、为空/不为空；保存视图并可设为首页快捷入口。

## 25.3 数据结构与执行方案

1. 客户基础条件查询客户主表和授权范围。
2. 交易条件查询按客户预聚合的日/月事实表，而不是每次扫描全部订单。
3. 买过/未买过产品查询客户×产品关系表；“买 A 未买 B”分别用存在与不存在条件。
4. 模糊名称、域名、地址使用搜索索引；索引异步更新并显示延迟状态。
5. 查询计划先应用数据权限和高选择性条件，再做聚合；大结果集采用游标分页。

## 25.4 异常、权限与验收

- 不同币种金额条件必须明确按原币还是本位币；默认按本位币和汇率快照。
- “没有购买”要区分全历史未购买和所选时间范围未购买。
- 保存筛选视图不固化用户无权访问的数据；共享视图执行时重新校验接收者权限。
- 验收：示例复杂条件可正确返回；筛选条件可保存/分享；列表、导出与统计口径一致；性能达到约定 SLA。

# 26. 权限体系

## 26.1 权限模型

采用“四层组合权限”，避免只做简单角色菜单权限：

1. **功能权限（RBAC）**：能否查看、创建、编辑、删除、合并、转移、导出、审批。
2. **数据范围**：本人、协同、团队、部门、公司、指定客户集合。
3. **字段权限**：销售额、成本、毛利、信用、个人联系方式、内部责任等字段单独控制查看/编辑/导出。
4. **临时授权（ACL）**：对特定客户、对象、字段授予指定人员，有生效/失效时间和原因。

## 26.2 组织与企业微信同步

- 组织对象包括公司、部门、团队、员工、岗位；外部组织 ID 与 ERP 内部 ID 分离。
- 企业微信是组织来源之一，不作为业务数据主键；同步失败不应删除业务记录。
- 员工停用后立即禁止登录并触发客户/任务交接，不物理删除员工。
- 组织调整应保留生效时间，历史订单归属仍按时点快照统计。

## 26.3 默认权限建议

| 角色 | 客户范围 | 关键限制 |
|---|---|---|
| 业务员 | 本人负责+协同授权 | 默认不看成本；导出受限 |
| 主管 | 本团队 | 可分配/转移；毛利需单独授权 |
| 销售经理 | 销售部门 | 可看部门汇总和授权明细 |
| 管理层 | 公司级汇总，明细另授权 | 不因管理层身份默认看个人联系方式 |
| 财务/信用 | 授权客户信用与应收 | 不默认编辑销售沟通 |
| 管理员 | 系统配置 | 不默认拥有全部业务敏感字段 |

## 26.4 特殊场景、审计与验收

- 客户转移后旧负责人访问权按配置立即收回或保留只读过渡期。
- 协同权限可限定为查看、沟通、询盘、报价或附件，不必获得全部客户权限。
- 临时授权必须有期限，过期自动回收并通知；批量导出、查看毛利和信用可记录访问日志。
- 所有接口、导出、搜索索引和 Dashboard 均执行同一权限策略，禁止只在前端隐藏。
- 验收：本人/团队/部门/全公司范围正确；字段权限不可绕过；临时授权自动失效；员工停用触发交接。

# 27. 操作日志

## 27.1 记录范围

客户创建/修改/删除/恢复、负责人和团队变化、等级与状态变化、信用变化、报价版本与审批、客户合并/回滚、批量导入导出、权限配置、自动化规则修改、登录与高敏感数据访问。

每条审计事件至少保存：事件 ID、对象类型/ID、操作者、代理操作者（如系统）、时间、请求来源、动作、修改前、修改后、原因、规则版本、关联批次、IP/设备信息（按合规要求）。

## 27.2 业务规则

- 审计日志只追加、不允许普通用户修改或删除；敏感值按策略脱敏或加密。
- 大文本和附件不复制全文，只保存哈希、版本和安全引用。
- 自动化执行既记录触发条件，也记录执行结果、跳过原因和重试次数。
- 日志留存期限、访问权限和归档策略可配置，并满足适用法律及公司制度。

## 27.3 验收

可按客户、对象、操作者、时间和动作查询；字段级前后值可读；合并、转移和规则执行可完整还原；无权限人员不可访问敏感日志。

# 28. 系统自动化规则

## 28.1 规则引擎最小能力

规则由“触发器—条件—动作—限制”构成：

- 触发器：对象创建/更新、状态变化、到期时间、每日批处理、外部事件。
- 条件：客户属性、负责人、金额、状态、时间差、是否存在关联对象。
- 动作：建任务、发站内提醒、调整系统计算状态、通知主管、写时间轴事件、调用接口。
- 限制：作用范围、工作日/时区、冷却期、最大次数、去重键、启停时间。

每条规则有名称、版本、优先级、所有者、测试模式、生效日期、回滚版本和运行日志。

## 28.2 核心规则清单

| 编号 | 规则 | 触发 | 动作 |
|---|---|---|---|
| A01 | 新询盘首次响应 | 创建询盘 | 分配、建任务、SLA 提醒 |
| A02 | 报价后跟进 | 正式发送报价 | 按工作日建跟进任务 |
| A03 | 报价到期 | 到有效期 | 标记过期、提醒负责人 |
| A04 | 样品反馈 | 预计签收/签收事件 | 确认收货和反馈任务 |
| A05 | 采购周期预警 | 每日重算 | 更新活跃度、生成预警任务 |
| A06 | 长期无有效沟通 | 每日重算 | 提醒或升级主管 |
| A07 | 客诉超时 | 截止时间 | 通知责任人并分级升级 |
| A08 | 应收逾期 | 财务事件/每日同步 | 风险提示、通知授权角色 |
| A09 | 联系人离职 | 联系人状态变化 | 建补充关键联系人任务 |
| A10 | 客户转移 | 转移生效 | 调整权限、处理未完成事项 |

## 28.3 防错与验收

- 规则必须有幂等键，同一事件重放不重复创建任务。
- 多条规则冲突时按优先级执行；状态更新采用乐观锁，失败可重试。
- 上线前支持测试模式，只记录“将执行什么”而不真正执行。
- 验收：规则可启停、版本化、测试、回滚；重复事件不产生重复动作；失败有告警和重试记录。

# 29. 状态机设计汇总

## 29.1 通用要求

所有状态机需明确：允许的前后状态、触发角色、前置条件、自动动作、回退规则、终态重开权限和审计。禁止前端任意写状态字符串。

## 29.2 状态机总表

| 对象 | 主状态 | 关键自动变化 |
|---|---|---|
| 客户生命周期 | 线索→已验证→机会→成交→流失 | 首单生效→成交；流失需人工确认 |
| 经营活跃度 | 数据不足/活跃/待跟进/高风险/沉睡 | 每日按周期与活动重算 |
| 询盘 | 新→分析→待报价→报价中→已报价→跟进→转单/丢单/关闭 | 正式发报价、订单关联、SLA |
| 报价 | 草稿→待审批→批准→已发送→反馈→接受/拒绝/过期/撤回 | 正式发送、有效期、订单关联 |
| 任务 | 待处理→进行中→完成；取消/忽略/等待客户 | 到期标逾期、完成写回结果 |
| 客诉 | 新建→受理→调查→方案→执行→客户确认→关闭 | SLA、严重度升级、关闭校验 |
| 合并申请 | 草稿→待审核→执行中→完成/失败→可回滚期结束 | 审批、迁移、重算、审计 |

## 29.3 并发与异常规则

- 状态变更携带当前版本号，防止两人同时处理覆盖。
- 外部模块事件乱序时按事件时间和版本处理，旧事件不能回滚新状态。
- 自动变化失败进入重试队列；超过阈值通知管理员，不静默失败。
- 终态重开必须产生新事件并记录理由，不能删除终态历史。

# 30. 数据字段设计

## 30.1 字段通用规范

| 类型 | 规范 |
|---|---|
| ID | 内部不可变 ID 与业务编号分离；外部 ID 单独保存并标来源 |
| 字典 | 保存代码，不保存展示中文作为事实；字典支持停用和国际化 |
| 时间 | UTC 时间戳+业务日期+用户时区；禁止只存本地字符串 |
| 金额 | Decimal 定点数；币种 ISO 4217；禁止浮点金额 |
| 数量 | 数值+单位；单位换算记录版本 |
| 百分比 | 明确存 0–1 或 0–100，系统统一 |
| 地址 | 结构化国家/省州/城市/邮编+原始地址；支持多地址 |
| 电话 | 原文+规范化 E.164；无法规范化保留原文并标记 |
| 域名 | 规范化主域名；排除 gmail 等公共邮箱域 |
| 多语言 | 客户原文与内部翻译分开，不覆盖原始内容 |
| 软删除 | deleted_at、deleted_by、reason；关联事实不物理删除 |
| 版本 | version、created_at/by、updated_at/by；关键对象保存历史版本 |

## 30.2 建议核心数据表

| 领域 | 数据对象 |
|---|---|
| 客户 | customer、customer_address、customer_tag_relation、customer_group_relation |
| 联系人 | contact、contact_channel、contact_employment_history、contact_role |
| 归属权限 | customer_assignment、customer_collaborator、temporary_grant |
| 活动 | communication、task、timeline_event、attachment_link |
| 询盘报价 | inquiry、inquiry_line、quotation、quotation_version、quotation_line |
| 交易只读 | order_snapshot、order_line_snapshot、receivable_snapshot、payment_summary |
| 产品经营 | customer_product_relation、product_recommendation、customer_annual_metric |
| 风险服务 | customer_health_snapshot、credit_snapshot、complaint_snapshot |
| 治理 | duplicate_candidate、merge_batch、audit_event、automation_rule/run |

## 30.3 客户汇总字段

客户列表需要快速展示最近联系、最近订单、12 个月销售额等，可在 customer_summary 或分析库中保存派生值。每个派生值必须带更新时间和来源版本，支持按事实表重算；禁止业务人员直接编辑汇总值。

# 31. 数据对象关系

## 31.1 核心关系

- 一个客户有多个联系人、地址、负责人历史、协同人员、沟通、任务、询盘、报价、订单、客诉。
- 一个询盘包含多条询盘行；一条询盘可对应多个报价版本，也可部分转入多个订单行。
- 一个报价有多个不可变版本，每个版本含多条报价行；订单行可追溯到具体报价版本行。
- 一个订单包含多条订单行；订单行关联客户、产品、历史负责人快照和可选报价/询盘来源。
- 客户与产品为多对多，通过 customer_product_relation 持久化汇总。
- 时间轴通过来源对象类型+来源对象 ID 引用业务事件，不复制业务明细。
- 客户合并通过 canonical_customer_id 和 merge_batch 维护主从关系及原 ID。

## 31.2 一致性原则

1. 订单、回款、应收、客诉各自由所属模块维护事实，CRM 只保存可更新快照或读取接口。
2. 跨模块采用事件 ID、对象版本和幂等键，避免重复消费。
3. 汇总数据最终一致；关键交易展示必须能下钻到事实对象。
4. 客户合并、产品合并后通过映射表重算，不能直接改写不可追溯的历史文本。

# 32. 与未来 ERP 模块的接口边界

## 32.1 模块职责

| 模块 | 主责数据 | CRM 使用方式 |
|---|---|---|
| 产品/PIM | 产品、SKU、分类、属性、图片、认证、状态 | 搜索选择、客户×产品、推荐 |
| 报价 | 报价计算、审批、版本、对外文件 | CRM 展示、跟进和趋势；早期可由 CRM 轻量承载 |
| 订单 | 订单确认、履约、取消、订单行 | CRM 只读汇总与追溯 |
| 库存 | 可售库存、交期、批次 | 推荐/报价时提示，CRM 不维护 |
| 采购/生产 | 成本、采购、排产、交期 | 报价成本/交期参考，CRM 不维护 |
| 财务/应收 | 发票、回款、核销、信用、逾期、汇率 | CRM 展示信用与风险 |
| 售后/质量 | 客诉、调查、责任、赔偿、闭环 | CRM 展示客户影响和时间轴 |
| 组织/企业微信 | 员工、部门、状态 | 权限范围与交接 |

## 32.2 接口与事件

建议事件包括：ProductUpdated、QuotationSent、OrderConfirmed、OrderCancelled、ShipmentCompleted、ReceivableChanged、PaymentReceived、CreditChanged、ComplaintOpened/Closed、EmployeeDisabled。

每个事件至少包含 event_id、event_type、occurred_at、producer、object_id、object_version、customer_id、payload_version。消费方以 event_id 幂等；接口失败可重放并保留死信队列。

## 32.3 边界验收

- CRM 不可直接改订单、应收和财务事实。
- 外部模块数据均显示来源与更新时间。
- 接口重复、乱序、延迟和暂时失败不会造成重复任务或错误状态。
- 所有外部对象有内部映射 ID，不依赖可变业务编号。

# 33. MVP 范围

## 33.1 MVP 必须包含

1. 客户主档、快速建档、联系人、多地址、客户归属历史。
2. 客户列表、基础/高级筛选、保存视图、数据权限。
3. 沟通记录、跟进任务、基础提醒、客户统一时间轴。
4. 客户 360° 首屏、联系人/沟通/询盘/报价/订单只读标签。
5. 询盘多行、状态机、SLA、丢单原因和报价关联。
6. 历史报价版本、正式发送锁定、基础价格趋势。
7. 历史订单导入/接口、1 年/3 年/全部统计与订单时点归属。
8. 客户×产品汇总、规则型推荐 TOP 5 和推荐原因。
9. 基于采购周期的活跃度/沉睡/流失预警基础版。
10. 重复检测、人工审核合并、操作日志。
11. 角色+数据范围+敏感字段权限。
12. 业务员首页和主管基础首页。

## 33.2 MVP 交付切片建议

- **切片 A：可信客户底座**——客户、联系人、归属、权限、去重、导入。
- **切片 B：每天可用**——沟通、任务、提醒、时间轴、业务员首页。
- **切片 C：机会与交易视图**——询盘、报价、订单只读、360°。
- **切片 D：经营与风险**——客户×产品、分析、沉睡/流失、主管首页。

每个切片均需完成权限、审计、数据迁移与性能验收，不把这些推到最后补。

# 34. 第二阶段功能

- 邮件、WhatsApp、企业微信等合规渠道自动同步与去重。
- 完整报价计算/审批/模板/对外 PDF 能力，样品全流程。
- 公海客户、自动回收、线索评分与市场活动归因。
- 集团客户、母子公司、全球账户管理和跨法人信用。
- 更完善的销售预测、机会金额与概率管理。
- 售后模块深度集成、质量成本与客诉复发分析。
- 规则效果 A/B 评估和推荐反馈闭环。
- 多语言、多时区、移动端离线录入和批量语音摘要。

# 35. 暂不开发功能

1. 采购、库存、生产、完整订单履约和总账/核销。
2. 黑盒 AI 自动推荐、自动定价、自动判定信用或强制客户流失。
3. 未经官方接口许可的微信/WhatsApp 抓取。
4. 复杂营销自动化、群发邮件平台和广告投放归因。
5. 过度可配置的低代码页面/流程设计器。
6. 完整 CPQ（配置、定价、报价）引擎；第一阶段只保留接口和轻量规则。
7. 为 Demo 制作但没有真实业务价值的大屏动画与装饰性图表。

# 36. 验收标准

## 36.1 业务验收场景

| 编号 | 场景 | 通过标准 |
|---|---|---|
| AC01 | 展会线索快速建档 | 30 秒内完成最小建档；重复客户实时提示 |
| AC02 | 一个客户多联系人 | 可区分采购、决策、财务、物流；离职不丢历史 |
| AC03 | 沟通后创建下一步 | 保存沟通自动建唯一任务并进入时间轴 |
| AC04 | 多产品询盘到报价 | 多行询盘可生成报价；正式发送后状态正确 |
| AC05 | 报价修订 | 已发送版本不可覆盖，新版本保留差异和父版本 |
| AC06 | 价格趋势 | 可按 SKU、币种、贸易条款、数量区间正确比较 |
| AC07 | 3 年采购分析 | 能回答产品、数量、销售额、毛利并下钻订单行 |
| AC08 | 客户转移 | A→B 后历史订单仍归 A；未完事项按策略处理 |
| AC09 | 60 天周期客户 | 90 天无订单进入高风险并展示周期比与原因 |
| AC10 | 交叉销售 | 输出未购产品 TOP 5，展示可解释原因和排除条件 |
| AC11 | 信用风险 | 展示额度、占用、逾期和更新时间；过期数据有警告 |
| AC12 | 重复合并 | 联系人、沟通、询盘、报价、订单、任务完整保留并可审计 |
| AC13 | 复杂搜索 | 德国+销售额+无订单+买 A 未买 B 条件返回正确 |
| AC14 | 权限 | 业务员/主管/经理/管理员数据范围和字段权限不可绕过 |
| AC15 | 自动化幂等 | 同一外部事件重复发送不重复建任务或改变状态 |

## 36.2 非功能验收

- **性能：** 在约定的 10 万客户、100 万订单行、500 万时间轴事件测试数据下，客户列表普通筛选 P95 ≤ 2 秒，复杂聚合筛选 P95 ≤ 5 秒，360° 首屏 P95 ≤ 2 秒。
- **可靠性：** 跨模块事件可重试、可重放、幂等；失败有告警；关键数据可每日对账。
- **安全：** 后端执行行级和字段级权限；敏感导出审计；附件受控；常见越权场景测试通过。
- **可追溯：** 客户、报价、归属、合并、信用与规则变更均可还原前后值。
- **可用性：** 业务员关键任务不超过 3 次主要点击；批量操作有预览、数量和结果报告。
- **数据质量：** 必填、格式、字典、重复、关联完整性校验通过；统计字段可重算并与事实抽样一致。
- **兼容与可访问性：** 主流桌面浏览器可用；键盘可操作核心流程；颜色不是唯一状态表达方式。

# 37. 产品经理 Review

## 37.1 是否遗漏关键业务场景

原始需求覆盖度高，但仍缺少以下关键场景：

1. **集团/多法人客户：** 海外集团可能多个采购主体、付款主体和收货地址，不能简单合并。
2. **联系人任职变化：** 联系人可能在集团内部转岗，直接改客户会破坏历史。
3. **样品流程：** 生命周期与提醒多次提及样品，但未定义样品申请、费用、寄送、签收和反馈归属。MVP 可仅做关联事件，第二阶段完整建设。
4. **多币种与汇率：** 没有明确本位币和历史汇率口径，会直接影响销售额和毛利可信度。
5. **数据迁移和数据治理：** 旧 Excel/邮件/系统如何导入、去重、验收尚未定义，应作为实施子项目。
6. **合规与数据保留：** 海外联系人数据、营销退订、附件及聊天记录可能涉及 GDPR 等要求，应由法务确认。
7. **客户公海与回收：** 原需求未明确是否需要公海。若公司实际采用公海机制，需先确认回收规则与撞单处理。

## 37.2 重复功能与不必要字段

- “主要采购产品”不应在客户档案手填，应由客户×产品与订单统计得出。
- “首次联系、首次成交、最近成交、最近跟进”均应系统统计，不应人工维护。
- “是否最终成交”应由订单关联计算，不能在报价中手工勾选。
- “客户状态”不能同时表达生命周期、活跃度、流失和信用；本 PRD 已拆分。
- “当前报价”必须是带有效期的报价版本视图，不能成为客户×产品关系中的孤立裸值。

## 37.3 可能导致业务员操作复杂的地方

- 建档字段过多会让业务员绕开 CRM。应采用四字段快速建档+渐进补全任务。
- 每次沟通都要求长篇记录会制造假数据。应提供短摘要、结构化反馈和下一步动作。
- 标签无限自由创建会变成垃圾场。需要标签治理、同义词合并和停用机制。
- 自动提醒过多会形成提醒疲劳。必须做去重、冷却期、优先级和一键改期/忽略原因。
- 360° 将所有模块平铺会使首屏过载。应只显示价值、风险、最近动态和下一步，明细按需加载。

## 37.4 哪些字段应自动计算

首次/最近联系、首次/最近询盘、首次/最近报价、首次/最近订单、累计销售额、年度销售额、订单数、销量、毛利、毛利率、平均订单额、订单距今天数、未完成对象数量、信用占用、剩余额度、客诉率、采购周期、经营活跃度、流失风险、主要采购产品、推荐产品。

人工只维护系统无法可靠推导的判断，例如客户类型、主营业务、关键联系人、采购偏好、流失原因、不感兴趣原因和例外说明。

## 37.5 不应进入第一阶段的功能

- 全渠道自动抓取、复杂 AI 推荐、完整 CPQ、营销自动化、复杂预测、完整售后/财务流程、可视化低代码引擎。
- 原因不是这些功能无价值，而是它们依赖更稳定的主数据、交易事实、官方接口、合规和流程口径。提前做只会把脏数据自动化。

## 37.6 可能产生技术债的设计

1. 用一个 customer 表堆所有实时统计字段，并在页面请求时跨模块实时计算。
2. 用可变客户编号、SKU 或员工编号做跨模块外键。
3. 报价已发送后允许覆盖修改，导致无法复盘客户看到的版本。
4. 用当前成本与当前汇率回算历史毛利。
5. 把客户转移写成直接覆盖负责人，不保存订单时点归属。
6. 搜索只依赖关系数据库模糊查询，后期难以支撑复杂组合筛选。
7. 自动化没有幂等、版本、冷却期和执行日志。
8. 合并客户直接删除从客户，失去原始 ID 和回滚能力。

## 37.7 必须现在设计好的数据关系

- 客户—联系人—任职历史。
- 客户—询盘行—报价版本行—订单行的端到端追溯。
- 客户—产品的汇总关系与事实来源。
- 客户当前归属、历史归属、订单时点归属三者分离。
- 客户合并主从映射与原始 ID。
- 原币金额、本位币金额、汇率与成本快照。
- 时间轴统一事件模型与跨模块事件幂等键。
- 权限的数据范围、字段权限和临时授权。

## 37.8 分级结论

### MVP 必做

客户/联系人主数据、归属、去重、权限、沟通、任务、时间轴、询盘、报价版本、订单只读、客户 360°、客户×产品基础汇总、采购周期预警、基础 Dashboard、审计与自动化幂等。

### 建议做

集团客户、样品轻量事件、规则型交叉销售、价格趋势可比口径、信用/客诉只读集成、保存高级筛选、管理层下钻、规则测试模式。

### 以后做

全渠道自动同步、完整 CPQ、完整售后、营销自动化、复杂销售预测、AI 推荐/摘要/评分、多法人全球账户与高级数据仓库。

# 38. 实施前决策清单

以下决策如果不先确认，研发即使按 PRD 完成也可能无法落地：

1. 确认本位币、汇率来源、销售额与毛利公式。
2. 确认客户等级、来源、类型、流失原因等字典初始值及维护人。
3. 提供真实销售流程样本：至少 10 个询盘、10 份报价、10 个订单、5 个客诉。
4. 确认客户公海、撞单、转移和离职交接制度。
5. 确认各产品线、国家和客户类型的默认采购周期。
6. 确认第一阶段报价是 CRM 原生轻量能力，还是从独立报价模块读取。
7. 确认历史数据迁移范围、质量负责人和验收抽样标准。
8. 确认企业微信同步边界、敏感字段和数据导出审批要求。

---

**文档结论：** haiqu ERP CRM 第一阶段应先建立可信客户主数据、可执行销售跟进与完整交易追溯，再叠加规则型经营洞察。产品成功的核心不是字段数量，而是业务员每天愿意使用、主管看得懂、关键数字能追到事实、未来模块接入时不推翻现有数据关系。
